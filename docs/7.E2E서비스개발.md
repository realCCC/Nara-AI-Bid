## 1. 최종 아키텍처 요약

* **완성된 아키텍처 핵심:** 규칙 기반 Supervisor가 제어하는 LangGraph 단일 그래프에 추천 Worker 서브그래프, RAG 순위, 검증 서브에이전트, 제안서 작성을 연결했습니다. 자격 판단은 룰이, 의미 검색·근거 작성은 LLM과 하이브리드 검색이, 최종 판단은 담당자가 맡습니다.

* **최종 산출물 형태:** 로컬에서 실행하는 웹 서비스 `입찰에이전트`입니다(FastAPI + 단일 HTML). 업체로 로그인해 맞춤 공고 상위 10건을 근거·출처와 함께 받고, 체크리스트 확인 후 제안서 초안을 만들어 대화로 보완하고 HTML로 내려받습니다.

* **Agent 구조:**

```
[브라우저] ── REST·SSE ──▶ [FastAPI] ──▶ [LangGraph: Supervisor가 비어 있는 단계로 라우팅]

 ⓪ 맞춤 인터뷰 (HITL)
 ① 마스터키·검색 프롬프트 확인 (HITL)
 ② 추천 Worker 서브그래프: 자격 필터·소프트 점수 → 하이브리드 검색 → 리랭크 → 상위 10건
 ③ RAG 순위·근거: 공고서 청크 검색 → LLM 순위 작성 → 인용 원문 대조
 ④ 검증 서브에이전트: 상위 5건 재평가, 자격 불충족 공고를 뒤로 이동
 ⑤ 확인 체크리스트·공고 확정 (HITL)
 ⑥ 제안서 초안: 평가항목·배점 추출 → 섹션별 LLM 작성 → 대화형 보완
```

| 구성 요소 | 역할 |
| --- | --- |
| Azure OpenAI | 인터뷰 문항, 마스터키 후보, 순위·근거, 검증, 체크리스트, 제안서 작성 (structured output) |
| 임베딩 | Azure text-embedding-3-large 1024차원 (로컬 BGE-M3로 교체 가능) |
| pgvector (Docker) | 공고서·업체 문서 청크 벡터, HNSW 인덱스 |
| `emb_cache.npz` | 1단계 공고 검색 벡터 캐시 |
| SQLite | 업체, 실행 이력, 추천, 체크리스트, 제안서 |
| 나라장터 | 추천에 오른 공고의 공고서 PDF를 그때그때 내려받음 |
| LangSmith, 실행 로그 팝업 | 노드·LLM·검색 추적, 화면에서 호출·폴백·오류 확인 |

**계획 대비 변경**

| --- | --- | --- |

**측정 조건**

* 추천 정확도와 부적격 건수는 저장된 스냅샷과 정답셋(`data/eval/`)으로 계산했습니다. 업체 10곳의 상위 5건, 총 50건입니다. 라벨 분포는 추천 23건, 적격-비추천 14건, 부적격 13건입니다.
* 라벨은 AI 초안을 2차 검토한 상태이고, 담당자 최종 확인 전입니다.
* 스냅샷은 마스터키 도입 전 흐름이고, 평가 당시 모델은 gpt-4.1입니다. 현재 `.env`의 배포는 gpt-5.4라서 재측정이 필요합니다.
* 계획의 측정 범위는 상위 10건 100조합이지만, 현재 정답셋은 상위 5건 50건입니다.
* 검증 플래그 정밀도·재현율은 1.00 / 0.92입니다. 측정 방법은 6번 문서 1-3절을 따릅니다.
* 처리 시간 68초는 인터뷰 3.8초, 추천·RAG·검증 61.8초, 초안 2.0초의 합입니다. 제안서 LLM 작성을 도입하기 전 수치입니다.
* 자동 테스트는 `uv run pytest` 기준 105건 모두 통과했습니다(실제 LLM 호출 없음).

## 3. 창출된 핵심 가치

아래 비즈니스 가치는 기능 기준의 기대 효과이며, 절감 시간은 Phase 4에 측정합니다.

### 3-1. 비즈니스 가치

* 유효 공고 443건을 업체별 상위 10건으로 줄여 담당자의 검토 범위를 좁힙니다.

* 추천마다 공고서 인용과 필드 값을 함께 보여 줘서, 담당자가 추천 이유를 원문으로 바로 확인할 수 있습니다.

* 자격·서류·일정 체크리스트를 전부 확인해야 공고를 확정할 수 있어 필수 항목 누락을 줄입니다.

* 평가항목·배점을 목차로 삼은 제안서 초안을 제공해 빈 문서에서 시작하지 않아도 됩니다.

* 마스터키로 이번에 가장 원하는 사업을 지정해, 같은 업체도 입찰 전략에 따라 다른 추천을 받습니다.

### 3-2. 기술적 가치

* **역할 분리:** 정형 자격은 룰(H1~H6), 의미 판단은 LLM이 맡고, 사람의 판단이 필요한 세 지점에서 그래프가 멈췄다가 재개합니다.

* **하이브리드 검색 + 2단계 RAG:** dense, BM25, 룰 순위를 RRF로 합치고 리랭크한 뒤, 후보 공고의 PDF 청크만 근거로 사용합니다.

* **환각 억제:** LLM의 인용은 PDF 원문과, 필드 근거는 실제 값과 대조해 일치하지 않으면 버립니다. 근거 없는 제안서 칸은 `[확인 필요]`, `[AI 초안·검토 필요]`로 남깁니다.

* **검증 서브에이전트:** 룰이 못 보는 공고서 속 자격 조건을 찾아 부적격 공고를 뒤로 보냅니다.

* **단계별 폴백과 관측성:** LLM, 임베딩, 벡터 DB가 실패해도 룰·BM25로 이어 가고, 대체 여부를 실행 로그에 표시합니다.

* **측정 기반 결정:** 1단계 PDF 본문 검색은 구현 후 효과가 작아(nDCG 0.904 → 0.908) 기본값을 껐습니다.

## 4. 운영 및 보안 고려 사항

* 인증 방식: 업체 ID·비밀번호 로그인, PBKDF2-SHA256 해시 저장, 서버 메모리의 세션 토큰. 데모 계정 비밀번호가 `1`이라 실제 서비스용 인증은 아닙니다.

* 권한 통제: 작업(`thread_id`)과 제안서는 소유 업체만 접근할 수 있고, 다른 업체가 요청하면 404를 반환합니다. 실행 로그도 업체별로 분리합니다.

* 입력 검증: 인터뷰 답변은 화이트리스트로 거르고, 이미 끝난 인터뷰 재요청은 409, 미확인 체크리스트와 추천 목록에 없는 공고는 400으로 막습니다.

* LLM 출력 통제: structured output으로 받고, 없는 공고 ID·근거·issue는 스키마와 원문 대조 후 폐기합니다.

* XSS 대응: 제안서는 Jinja2 autoescape로 렌더링하고, 화면 출력 값은 이스케이프합니다.

* 개인정보: 공고의 발주처 담당자 정보는 로드할 때 제거하고, 원본 데이터와 `.env`는 git에서 제외합니다. 업체는 가상 데이터입니다.

* 장애 대응: LLM 실패 시 룰 모드, 임베딩 실패 시 BM25, 벡터 DB 실패 시 BM25·키워드로 대체(30초마다 재연결), 리랭커 실패 시 리랭크를 생략합니다.

* 미완료 항목: 프롬프트 인젝션 테스트가 없고, `/api/select` 재호출에 대한 409 처리가 없습니다. 세션과 진행 중인 작업이 서버 메모리에 있어 재시작하면 사라집니다.

## 5. 회고 및 향후 확장

### 기술적 한계

**① 임베딩해야 하는 공고 데이터가 많음**

PoC는 2026-05 공고 조회 결과 16,573건 중 첫 페이지 500건만 다룹니다. 이 500건은 5/1~5/5 공고분이므로 5월 전체의 약 3%입니다. 서비스로 넓히면 임베딩 대상이 크게 늘어납니다.

| 항목 | 현재 PoC (실측) | 5월 전체 환산 (단순 비례 추정, 약 33배) |
| --- | --- | --- |
| 공고 | 500건 (유효 443건) | 16,573건 |
| 청크 임베딩 공고 | 406건 (PDF 보유 410건 중) | 약 13,000건 |
| 청크 벡터 | 약 10,000개 (공고당 약 25개) | 약 33만 개 |
| 임베딩 텍스트 | 약 487만 자 | 약 1.6억 자 |
| pgvector 용량 (인덱스 포함) | 262MB | 약 8.7GB |
| 공고서 PDF | 240MB | 약 8GB |
| BGE-M3 CPU 일괄 계산 | 2~3시간 | 약 66~99시간 |

* 비례 추정을 1년으로 늘리면 청크 벡터 약 400만 개, pgvector 약 100GB 규모입니다.
* 공고는 매일 새로 올라오고 정정 공고도 있어, 한 번 임베딩하고 끝나지 않습니다. 임베딩 모델이나 청킹 규칙을 바꾸면 전체를 다시 계산해야 합니다.
* 현재는 추천 상위 공고의 청크만 계산하고, 이미 저장한 벡터는 재사용하며, 데모 전에 미리 계산해 둡니다. 다만 처음 추천되는 공고는 임베딩 시간만큼 응답이 늦어집니다.
* 1단계 공고 검색 벡터는 DB가 아니라 메모리와 `emb_cache.npz`에 있어, 공고 수가 늘면 이 방식을 유지하기 어렵습니다.
* HWP 공고서는 파싱하지 않아 위 추정에 포함되지 않았습니다. 지원하면 대상이 더 늘어납니다.

**② 룰만으로 자격을 완전히 거르지 못함**

* 상위 5건의 부적격 13건 중 9건이 지역 제한이고, 나머지는 업종 등록과 중소기업 조건입니다. 정형 필드에 없고 공고서 PDF에만 적힌 조건이 많습니다.
* 지역 제한 매핑표(`data/region_limits.csv`)가 비어 있습니다. 그래서 지역 제한 필드가 있는 공고 44건은 업체 소재지와 상관없이 전부 제외되어, 맞는 공고를 놓칠 수 있습니다.
* 검증 서브에이전트는 부적격 공고를 뒤로 보낼 뿐 목록에서 제거하지 않습니다.

**③ 평가 규모와 신뢰도**

* 정답셋이 50건으로 작고 담당자 최종 확인 전입니다. 마스터키 흐름과 현재 모델로는 재측정하지 않았습니다.

**④ 기능 범위**

* 데이터가 고정 파일이라 실시간 공고와 마감일 필터를 지원하지 않습니다.
* 마스터키 일치는 공고명·분류명의 단어로 판정하므로, 표현이 다른 공고는 의미 검색과 LLM 판단에 의존합니다.
* LLM이 필드 접두어(`tender.`)를 빼면 맞는 근거도 대조에 실패해 버려집니다.

**⑤ 운영**

* 동시 접속 부하 테스트를 하지 않았습니다. 단일 프로세스의 메모리 상태에 의존해 서버를 여러 대로 늘릴 수 없습니다.
