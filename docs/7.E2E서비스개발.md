## 0. 대표 사용자 성공 경로

**로그인 → 맞춤 인터뷰(HITL) → 핵심 사업·검색 프롬프트 확인(HITL) → 추천 상위 10건 확인 → 체크리스트 검토·공고 확정(HITL) → 제안서 초안 생성·대화형 보완 → HTML 다운로드**

## 1. 최종 아키텍처 요약

* **핵심:** 규칙 기반 Supervisor가 제어하는 LangGraph 단일 그래프입니다. 자격 판단은 룰, 의미 검색·근거 작성은 LLM과 하이브리드 검색, 최종 판단은 담당자가 맡습니다.
* **산출물:** 로컬 웹 서비스 `입찰에이전트`(FastAPI + 단일 HTML).

```
[브라우저] ── REST·SSE ──▶ [FastAPI] ──▶ [LangGraph Supervisor]

 ⓪ 맞춤 인터뷰 (HITL)
 ① 핵심 사업·검색 프롬프트 확인 (HITL)
 ② 추천 Worker: 자격 필터·소프트 점수 → 하이브리드 검색 → 리랭크 → 상위 10건
 ③ RAG 순위·근거: 공고서 청크 검색 → LLM 순위 → 인용 원문 대조
 ④ 검증 서브에이전트: 상위 10건 재평가, 자격 불충족 공고를 맨 뒤로
 ⑤ 확인 체크리스트·공고 확정 (HITL)
 ⑥ 제안서 초안: 평가항목·배점 추출 → 섹션별 LLM 작성 → 대화형 보완
```

| 구성 요소 | 역할 |
| --- | --- |
| Azure OpenAI | 인터뷰, 핵심 사업, 순위·근거, 검증, 체크리스트, 제안서 (structured output) |
| 임베딩 | Azure text-embedding-3-large (로컬 BGE-M3로 교체 가능) |
| pgvector / SQLite | 공고서·업체 문서 청크 벡터 / 업체·이력·추천·제안서 |
| LangSmith, 실행 로그 팝업 | 노드·LLM·검색 추적, 화면에서 폴백·오류 확인 |

**계획 대비 변경:** React → 단일 HTML(일정), 가상 업체 50곳 → 10곳, 제안서 템플릿 → 섹션별 LLM 작성 + 대화형 보완, 인터뷰·핵심 사업 추가, 검증 범위 상위 5건 → 10건.

### 2-1. 현재 버전 E2E 측정 (Ⓔ, 11/11)

서버 API로 업체 10곳의 추천을 끝까지 실행하고, C001은 체크리스트·제안서 다운로드까지 2회 실행했습니다.

**처리 시간 (사람 시간 제외)**

| 구간 | 시간 |
| --- | --- |
| 인터뷰 문항 생성 | 15~19초 (8곳) |
| 핵심 사업 후보 | 3~5초 |
| 추천 (필터 → 검색·리랭크 → RAG → 검증) | 평균 **121초** (79~170초) |
| C001 전체 (핵심 사업 ~ 제안서 다운로드) | 1회차 **124초**, 2회차 **139초** (제안서 17초 / 41초) |
| 처음 처리하는 공고서 추가 시간 | 공고 1건당 0.5~7.2초 (다운로드·청킹·임베딩, 5건 실측) → 상위 10건 약 +20초 추정 |

* 기존 68초는 제안서 LLM 작성 도입 **전** 값이라 이 표와 분리합니다.
* 측정 시점에 공고서 PDF·벡터는 미리 계산돼 있어(데모 설정), 위 추천 시간은 반복 요청 조건입니다. 처음 처리는 마지막 행만큼 늘어납니다.
* 같은 요청을 반복해도 LLM 순위 판단이 달라 C001의 1위가 바뀌었습니다(1회차 막창축제, 2회차 한미친선축제).

**추천 품질·근거**

| 항목 | 결과 |
| --- | --- |
| LLM 근거 대조 | 380개 중 374개 통과 (**98.4%**), 6개 폐기. 이전 측정 40~85%에서 개선 |
| 근거 부족 추천 | 룰 근거로 보충된 추천 **0건**, LLM 근거 0개 **0건**, 공고서 PDF 근거 없음 **1건** / 99건 |
| 검증 | 10곳 중 9곳 수행, 89건 재평가, **35건 자격 의심** (참가자격 25 · 지역제한 18 issue). C002는 LLM 출력 형식 오류로 검증 생략 → 원순위 유지 (수정 후 3회 재실행 모두 수행, 2-3) |
| 플래그 일치 (라벨 있는 25건) | 플래그 4건 모두 라벨 '부적격', 미플래그 21건에 부적격 0건 |
| 최종 상위 3건 | 라벨 있는 15건(30건 중) 모두 '추천', 부적격 0건. 나머지 15건은 새 후보라 라벨 없음 |

* **C008(비중소기업)은 상위 10건이 모두 자격 의심**입니다. 공고서마다 "중소기업·소상공인 확인서 소지자"로 제한돼 있어 플래그 자체는 맞지만, 룰(H4)이 쓰는 정형 필드에는 이 제한이 없어 필터를 통과했습니다. 담당자에게 적격 공고 0건을 10건처럼 보여 주는 문제라, 노출 기준(아래)을 정하는 근거가 됩니다.

**제안서 초안 근거성 (C001 1회차 초안, 4,676자)**

* 업체 사실(PCO 등록, ISO 20121, PM 경력 15년, 관람객 12만 명·부스 80개·사고 0건 등)은 모두 업체 프로필·회사소개서에 있었고, 근거 없는 업체 사실은 0건입니다.
* 공고서에서 못 찾은 칸 10곳은 `[확인 필요]`, LLM이 짠 일정·인력 배치 2곳은 `[AI 초안·검토 필요]`로 표시됐습니다.
* 대조는 Claude가 했고, 담당자의 사실 확인·수정 시간은 아직 재지 않았습니다.

| 항목 | 다음 액션 | 판정 기준 |

## 3. 창출된 핵심 가치

시스템 처리 시간은 2-1에서 실측했고, 수작업 대비 절감률은 담당자 측정이 남았습니다.

* **검토 범위 축소:** 유효 공고 443건 → 업체별 상위 10건, 추천마다 공고서 인용·필드 값 제시
* **누락 방지:** 자격·서류·일정 체크리스트를 모두 확인해야 확정
* **초안 제공:** 평가항목·배점 목차의 제안서 초안, 근거 없는 칸은 `[확인 필요]`
* **전략 반영:** 핵심 사업으로 같은 업체도 입찰 전략에 따라 다른 추천
* **단계별 신뢰:** 화면에 필터 제외·검색 발굴·원문 대조·검증 하위 배치 수와 공고별 순위 변화 표시
* **검증 사례:** 「제3회 대전 중구 북페스티벌」(룰 점수 3위)을 공고서의 "주된 영업소 대전" 조건으로 최종 10위로 내리고 `자격 확인 필요` 표시
* **측정 기반 결정:** 효과 없는 본문 검색은 기본값 끔(nDCG 0.904 → 0.908), LangSmith 진단으로 검색 개선

**② 룰만으로 자격을 거르지 못함:** 지역·중소기업 조건이 정형 필드에 없고 공고서에만 있는 경우가 많습니다. 지역 매핑표가 비어 적격 공고 2쌍이 잘못 제외됐고(2-2), 반대로 공고서에만 조건이 있는 공고는 필터를 통과해 검증 단계에서야 잡힙니다(C008 10건, C005 6건).

**③ LLM 출력 편차:** 같은 요청에도 1위가 바뀝니다. 검증 출력의 누락·중복은 보정하도록 고쳤지만, 재평가에서 빠진 공고는 검증 없이 남습니다.

**④ 기능 범위:** 실시간 공고·마감일 필터 미지원, 핵심 사업 일치는 단어 기준.
