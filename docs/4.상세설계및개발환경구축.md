# Part 1. 상세 설계

## 1. Agent 페르소나 및 시스템 프롬프트

### 1.1 Agent 정의

| 항목 | 정의 |
|-----|------|
| Agent 이름 | 나라장터 입찰 어시스턴트 (Proposal Assistant) |
| 주요 역할 | 입찰 담당자를 위한 공고 추천·의사결정 지원(메인). 선택한 공고의 제안서 초안 템플릿은 템플릿 모듈이 생성 |
| 핵심 목표 | 1) 정확한 추천 (Hit Rate@3 80%·Precision@3 0.67, '부적격' 추천 0건) 2) 출처가 확인되는 추천 근거 제시 (95%) 3) 공고 검토 + 제안서 골격 작성 시간 50% 이상 단축 4) 기업 프로필에 없는 사실 기재 0건 |
| 기본 전제 | 최종 의사결정(공고 선택, 제안서 최종 작성)은 반드시 담당자가 한다. Agent는 판단에 필요한 정보와 분석 근거만 제공 |
| 톤앤매너 | 전문가형 조력자: 공식적, 근거 기반, 신뢰감 중심. 추천 시 판단 근거를 3-4가지로 명시 |
| 제약사항 | 추측·불확실한 정보 금지, 의사결정 주도 금지, 과장된 표현 금지, 근거 제시 필수 |

### 1.2 System Prompt (공통)

```text
당신은 나라장터 입찰을 지원하는 전문가형 의사결정 조력자입니다.

[역할과 책임]
- 입찰 담당자의 공고 검토, 선별, 제안서 작성을 돕는 조력자 역할
- 업체 역량과 공고 요구사항을 객관적으로 분석하고 연결
- 최종 의사결정은 담당자가 하도록 필요한 정보와 근거만 제공

[의사결정 원칙]
- 항상 입력된 데이터와 객관적 근거로 판단 (추측 금지)
- 점수 제시 시 계산 항목(기술/경험/인력)과 근거를 함께 설명
- 입력 데이터에 없는 정보는 "확인 필요"로 표시
- 수치를 쓸 때는 출처(입력 데이터의 어느 항목인지)를 함께 표시

[답변 구조]
1. 추천 이유 3-4가지 명시 (기술, 실적, 예산, 인력 등)
2. 충족 항목과 부족 항목을 명확히 구분 표시
3. 최종 판단은 담당자가 하도록 안내
4. 근거마다 출처(기업 프로필 또는 공고의 어느 필드 값인지)를 함께 표시

[금지사항]
- 실제 낙찰 확률·평가 점수 예측 (정부 입찰 결과는 예측 불가)
- "적합하지 않습니다"처럼 일방적 거절 (대신 부족한 자격 분석 제시)
- 최종 입찰 여부 결정 (담당자만 가능)
- 공고 신뢰성 판단 (담당자 책임)
```

### 1.3 Agent별 역할 프롬프트 요약

공통 System Prompt 위에 Agent별 역할 지시를 추가합니다.

| Agent | 역할 지시 요약 | 출력 형식 |
|-------|-------------|---------|
| Supervisor | 요청을 하위 작업으로 분해하고 Agent 호출 순서·병렬 여부 결정, 결과 취합 | 다음 실행 노드 이름 |
| 공고 분석 Agent | 공고 원문에서 과업내용·필수자격·평가기준·예산·기간 추출 | `TenderInfo` (JSON) |
| 매칭 Agent | 기업 정보와 공고 요구사항 비교, 적합도 점수와 근거 생성 | `MatchResult` (JSON) |
| 제안서 템플릿 모듈 (Agent 아님) | 고정 템플릿에 공고·기업·매칭 결과 값을 삽입. LLM을 호출하지 않으므로 프롬프트 없음 | HTML (`<section>` 4개 + 대응표) |

**제안서 섹션 ID** (3.시나리오수립 SC-002 기대 출력과 동일)

| 섹션 | section id | 삽입하는 입력값 | `[확인 필요]`로 남기는 자리 |
|------|-----------|--------------|-----------------------|
| 1. 회사소개 | `company` | 회사명, 설립연도, 보유 기술, 인증, 과거 실적 | 회사 비전·차별화 포인트 |
| 2. 수행방안 | `approach` | 과업내용, 공고 기술 평가항목(목차), 항목별 관련 기업 근거 | 항목별 수행 방안 본문 |
| 3. 추진일정 | `schedule` | 고정 단계(분석·설계 / 개발·테스트 / 운영·이관) | 단계별 기간 |
| 4. 조직구성 | `organization` | 역할별 보유 인원 | 투입 인력·역할 분담 |
| 5. 평가기준 대응표 | `criteria` | 평가항목·배점, 대응 섹션, 관련 기업 근거 | 근거가 없는 항목 |

**템플릿 규칙**

```text
- 템플릿 파일은 허용 태그만 사용한다: section, h2, h3, p, ul, ol, li, table, thead, tbody, tr, th, td, strong, em, br
- 삽입하는 값은 모두 HTML 이스케이프한다 (Jinja2 autoescape=True. 공고 원문은 외부 데이터이므로 태그로 해석되지 않게 함)
- 입력 데이터에 값이 없으면 추측하지 않고 "[확인 필요]"를 넣는다.
```

## 2. Agent 아키텍처 및 오케스트레이션

### 2.1 전체 구조 (Supervisor 패턴)

```
    React 화면  ──(LangGraph SDK: 실행 · 스트리밍 · 재개)──▶  LangGraph Server
                                                                 │
                                                          ┌──────┴───────┐
                                                          │  Supervisor  │
                                                          └──────┬───────┘
                                       ┌─────────────────────────┼──────────────────┐
                                       ▼                         ▼                  ▼
                                ┌─────────────┐           ┌─────────────┐   ┌──────────────────┐
                                │ 공고 분석   │           │  매칭       │   │ 제안서 템플릿     │
                                │ Agent       │           │  Agent      │   │ 모듈 (LLM 미사용) │
                                └─────────────┘           │  (메인)     │   │ 고정 템플릿+삽입  │
                                                          └─────────────┘   └──────────────────┘
                                                 [HITL ①] 공고 선택
```

| 구성 요소 | PoC 범위 | 비고 |
|---------|---------|------|
| Supervisor | **필수** | LangGraph 조건 분기로 흐름 제어 |
| 공고 분석 Agent | **필수** | SC-001, SC-002 공통 사용 |
| 매칭 Agent | **필수 (메인)** | SC-001 추천. 품질 투자를 집중하는 구성 요소 |
| 제안서 템플릿 모듈 | **필수 (축소)** | SC-002 초안 템플릿 + 평가기준 대응표, 고정 템플릿 + 입력값 삽입 |
| HITL ① 공고 선택 | **필수** | `interrupt` → React에서 응답 → `Command(resume=...)`로 재개 |
| HITL ② 제안서 확정 | **확장** | 템플릿 삽입 결과는 입력이 같으면 항상 같으므로 생략. LLM 문장 생성을 도입할 때 추가 |
| 검증 Agent (자기 검증·재작성 루프) | **확장 (2차 목표)** | 2.문제정의및서비스계획 기능 4. 재작성 최대 2회 상한 (근거: 2.문제정의및서비스계획 보조 지표) |

> **선택 근거 (Supervisor 패턴 + HITL 1곳)**: 작업 노드가 모두 Supervisor로 돌아오는 구조라, 이후 검증 Agent를 추가할 때 분기 하나만 더하면 됩니다. PoC에서는 흐름이 고정 순서라 Supervisor를 규칙 기반으로 두고(7장), 사람의 판단이 반드시 필요한 공고 선택 한 곳에만 HITL을 둡니다. 전체 결정과 재검토 조건은 14.1절에 모았습니다.

### 2.2 공고 추천 워크플로우 (SC-001)

| 단계 | 담당 | 처리 내용 |
|------|-----|---------|
| 1. 입력 | 담당자 + System | React에서 기업 프로필 JSON 업로드, 스키마 검증 |
| 2. 공고 분석 | 공고 분석 Agent | 공고 30건 병렬 파싱 → 과업내용·필수자격·평가기준 구조화 |
| 3. 필터링 | 매칭 Agent (규칙) | 필수 자격 미충족 공고 제외, 기업 선호 조건(예산 범위·지역) 밖 공고 제외 |
| 4. 적합도 계산 | 매칭 Agent | 하이브리드 점수 계산 (2.4절) → 상위 5건 **[초기 설정값]** + 추천 근거 3-4가지 (근거마다 출처 필드·값 포함) |
| 5. **[HITL ①] 공고 선택** | 담당자 | React 화면에서 상위 5건 검토 후 1건 선택 → 승인 |
| 6. 저장 및 전환 | System | 선택 결과를 같은 thread의 State에 저장, SC-002로 진행 |

선호 조건 필터는 2.문제정의및서비스계획 적합성 기준의 '선호 조건 불일치'(적격-비추천 라벨)에 대응하므로 PoC 필수로 둡니다. 규칙 비교만 하므로 구현 부담이 작습니다.

### 2.3 제안서 초안 템플릿 워크플로우 (SC-002)

| 단계 | 담당 | 처리 내용 |
|------|-----|---------|
| 1. 입력 | System | 선택 공고 `TenderInfo` + 기업 프로필 + 해당 공고의 매칭 결과를 State에서 로드 |
| 2. 초안 템플릿 생성 | 제안서 템플릿 모듈 | 섹션 4개 템플릿에 입력값 삽입. 수행방안의 평가항목별 관련 기업 근거는 SC-001에서 계산한 BGE-M3 유사도로 선택(임계값 미만이면 `[확인 필요]`) |
| 3. 평가기준 대응표 | 제안서 템플릿 모듈 | 공고 평가항목·배점 + 대응 섹션 + 관련 기업 근거를 표 템플릿에 삽입 |
| 4. 조립·미리보기 | System + React | 단일 HTML 문서로 조립 → sanitize 후 미리보기 |
| 5. 다운로드 | 담당자 | `.html` 다운로드 후 `[확인 필요]` 자리 작성 |

> **선택 근거 (LLM 생성 → 템플릿 삽입으로 축소)**: LLM을 호출하지 않으므로 같은 입력이면 결과가 항상 같고, 실패 지점은 데이터 누락뿐입니다. 프로필 값만 삽입하므로 '기업 프로필에 없는 사실 기재 0건'(근거성 KPI)을 구조적으로 지킬 수 있습니다. SC-002의 구현·테스트 부담이 작아지고, 남는 시간은 메인인 SC-001에 씁니다.

### 2.4 적합도 점수 계산 방식 (하이브리드)

2.문제정의및서비스계획 '적합 공고 정의'의 세 단계를 그대로 처리 순서로 사용합니다: **입찰 자격(Eligibility)** 은 규칙 필터, **기업 적합도(Suitability)** 는 아래 점수, **추천 순위(Ranking)** 는 점수 내림차순 상위 5건. 적합도 점수는 3.시나리오수립에서 정의한 가중치(기술 40% + 경험 40% + 인력 20%)를 유지하되, 항목 특성에 따라 계산 방식을 나눕니다.

| 항목 | 가중치 | 계산 방식 | 근거 |
|------|------|---------|------|
| 기술 적합도 | 40% | BGE-M3 임베딩 코사인 유사도 (기업 보유 기술 ↔ 공고 요구 기술) | 표현이 달라도 의미가 같은 기술 매칭 (예: "벡터 검색" ↔ "벡터DB") |
| 경험 적합도 | 40% | BGE-M3 임베딩 코사인 유사도 (기업 과거 실적 ↔ 공고 과업내용) | 유사 프로젝트 경험을 의미 단위로 비교 |
| 인력 적합도 | 20% | 규칙 기반: 요구 인원 대비 보유 인원 충족 비율 | 숫자 비교라 규칙이 더 정확 |
| 필수 자격 | 필터 | 규칙 기반: 하나라도 미충족 시 추천 제외 (부족 항목은 별도 표시) | 자격 미달 공고는 점수와 무관하게 제외 |

**최종 점수** = (기술 × 0.4 + 경험 × 0.4 + 인력 × 0.2) × 100 → 0-100점  
가중치는 **[초기 설정값]**이며, Phase 4에 조정용 기업 01-05의 Precision@3이 가장 높아지도록 조정한 뒤, 평가용 기업 06-10에서 한 번만 측정합니다 (12.3절).

> **선택 근거 (규칙 + 유사도 하이브리드)**: 자격·인원처럼 '충족/미충족'이 분명한 항목은 규칙이 정확하고 설명하기 쉬우며, LLM 판정과 달리 '부적격 추천 0건'을 보장할 수 있습니다. 기술·실적은 같은 의미를 다르게 표현하는 경우가 많아 키워드 일치로는 놓치므로 임베딩 유사도를 씁니다. 점수 계산에 LLM을 쓰지 않으므로 결과를 재현할 수 있고, 항목별 점수가 그대로 추천 근거가 됩니다.

### 2.5 상태(State) 관리

LangGraph의 공유 State 하나로 SC-001과 SC-002를 연결합니다. LangGraph Server의 **thread** 1개가 담당자 작업 세션 1개에 대응합니다.

| State 필드 | 내용 | 생성 시점 | 사용처 |
|-----------|------|---------|------|
| `company_profile` | 기업 프로필 (파싱 완료) | SC-001 1단계 | 전 단계 |
| `tenders` | 구조화된 공고 목록 | SC-001 2단계 | 매칭, 제안서 템플릿 |
| `recommendations` | 상위 5건 + 점수 + 근거(출처 포함) + 평가항목별 관련 기업 근거 | SC-001 4단계 | HITL ①, 제안서 템플릿 |
| `selected_tender_id` | 담당자가 선택한 공고 ID | HITL ① | SC-002 전체 |
| `draft_sections` | 초안 템플릿 섹션 HTML 4개 (`{section_id: html}`) | SC-002 2단계 | 조립 |
| `criteria_table` | 평가기준 대응표 (HTML 표) | SC-002 3단계 | 조립 |
| `proposal_html` | 최종 조립된 HTML 문서 | SC-002 5단계 | 다운로드 |

**Checkpoint**: LangGraph Server가 thread별 checkpoint를 자동 저장하므로, 담당자가 화면을 닫았다가 돌아와도 HITL 대기 지점부터 이어서 실행합니다. 서버용 그래프는 checkpointer를 지정하지 않고, 서버 없이 그래프를 실행하는 스크립트(`evaluate.py`)만 `InMemorySaver`를 붙여 compile합니다 (`interrupt`는 checkpointer가 있어야 동작, 7장).

> **선택 근거 (서버 내장 checkpoint)**: HITL ①은 '실행 중단 → 화면에서 선택 → 같은 지점에서 재개'가 핵심이며, 서버가 이 동작을 thread 단위로 기본 제공하므로 저장소 코드를 따로 작성하지 않아도 됩니다. PoC 세션은 하루 안에 끝나므로 장기 보존(SqliteSaver·Postgres)은 필요해질 때 추가합니다.

## 4. 지식 베이스 및 메모리 전략

### 4.1 RAG (검색 증강 생성) 전략

RAG는 목표 자체가 아니라 Agent가 호출하는 도구 중 하나로 구성합니다 (1.역량및기술스택확인 하네스 원칙).

| 항목 | 결정 |
|------|------|
| 데이터 소스 | IT 용역 공고 30건 (조달청 API 수집 + 수동 보완), 가상 기업 프로필 10개사 |
| 청킹 방식 | 공고: 섹션별 (공고명 / 과업내용 / 필수자격 / 평가기준), 기업: 영역별 (회사정보 / 기술 / 실적 / 인력) |
| 임베딩 모델 | BGE-M3 (오픈소스, 한국어 지원) |
| Vector DB | Chroma (로컬 실행) |
| 활용처 | 매칭 Agent의 기술·경험 유사도 계산, 평가항목별 관련 기업 근거 선택 (같은 유사도를 제안서 템플릿에서 재사용) |

> **선택 근거 (BGE-M3)**: 한국어 공고·실적 문장을 다국어 임베딩으로 비교할 수 있고, 오픈소스라 2번 문서 제약(외부 의존성 최소화)을 충족합니다. 로컬에서 실행하므로 Azure 키 없이도 추천 점수를 검증할 수 있어, 13장 최소 실행 경로를 LLM 없이 돌릴 수 있습니다.  
> **선택 근거 (Chroma)**: 공고 30건 × 기업 10개사 규모에서는 별도 서버 없이 로컬 파일 저장으로 충분하고, 공고 ID·섹션 같은 메타데이터 필터를 기본 제공합니다.

### 4.2 대화 메모리

| 항목 | 결정 |
|------|------|
| 메모리 유형 | LangGraph State + Server 내장 checkpoint (대화 이력이 아닌 작업 상태 중심) |
| 세션 단위 | LangGraph Server thread 1개 = 담당자 작업 1건 (SC-001 → SC-002) |
| 세션 시작 | 기업 프로필 로드 (기본 컨텍스트) |
| SC-001 | 추천 결과, 선택 공고 저장 |
| SC-002 | 초안 템플릿 섹션 HTML |
| 세션 종료 | 최종 HTML 초안 템플릿과 선택 이력만 보존, 나머지 중간 상태 삭제 |
| 개인정보 | 발주처 담당자 연락처 등 PII는 저장하지 않거나 마스킹 (2.문제정의및서비스계획 제약사항) |

## 7. LangGraph 구조 예시

상세 설계 단계의 출발점이 되는 그래프 골격입니다. (의사코드 수준, 모델명은 설정값으로 분리)

```python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt


class ProposalState(TypedDict):
    company_profile: dict
    tenders: list[dict]
    recommendations: list[dict]      # 상위 5건 + 점수 + 근거(출처 포함) + 평가항목별 관련 근거
    selected_tender_id: str | None
    draft_sections: dict[str, str]   # {section_id: "<section>...</section>"}
    criteria_table: str              # "<table>...</table>"
    proposal_html: str


def analyze_tenders(state: ProposalState) -> dict:
    # 공고 분석 Agent: 공고 원문 → TenderInfo 구조화 (LLM)
    ...

def match_tenders(state: ProposalState) -> dict:
    # 매칭 Agent: 자격·선호 필터 → 하이브리드 점수 → 상위 5건 + 근거(출처 포함)
    ...

def select_tender(state: ProposalState) -> dict:
    # HITL ①: React에서 공고 1건 선택할 때까지 대기
    tender_id = interrupt({"recommendations": state["recommendations"]})
    return {"selected_tender_id": tender_id}

def build_proposal_template(state: ProposalState) -> dict:
    # 제안서 템플릿 모듈 (LLM 미사용): 섹션 4개 + 대응표에 입력값 삽입 → 단일 HTML 조립
    ...


def supervisor(state: ProposalState) -> dict:
    # Supervisor: 작업 노드 결과를 받아 다음 작업을 결정 (실제 분기는 route에서 수행)
    return {}

def route(state: ProposalState) -> str:
    # PoC 1차: State에 비어 있는 단계를 찾아 다음 노드로 보내는 규칙 기반 라우팅
    if not state.get("tenders"):
        return "analyze_tenders"
    if not state.get("recommendations"):
        return "match_tenders"
    if not state.get("selected_tender_id"):
        return "select_tender"
    if not state.get("proposal_html"):
        return "build_proposal_template"
    return END


WORKERS = {
    "analyze_tenders": analyze_tenders,
    "match_tenders": match_tenders,
    "select_tender": select_tender,
    "build_proposal_template": build_proposal_template,
}

builder = StateGraph(ProposalState)
builder.add_node("supervisor", supervisor)
for name, fn in WORKERS.items():
    builder.add_node(name, fn)
    builder.add_edge(name, "supervisor")   # 작업이 끝나면 Supervisor로 복귀

builder.add_edge(START, "supervisor")
builder.add_conditional_edges("supervisor", route, [*WORKERS, END])

# LangGraph Server가 checkpointer를 주입하므로 compile 시 지정하지 않음
graph = builder.compile()


# 서버 없이 실행하는 스크립트(evaluate.py)용: interrupt를 쓰려면 checkpointer 필요
def build_local_graph():
    from langgraph.checkpoint.memory import InMemorySaver
    return builder.compile(checkpointer=InMemorySaver())
```

`evaluate.py`는 `build_local_graph()`로 실행하다가 HITL ①에서 멈추면 `Command(resume=<1순위 tender_id>)`로 자동 재개합니다.

서버 진입점 설정(`langgraph.json`)과 코드 위치는 10.3절에 있습니다.

**React 측 호출 흐름 (개념)**

| 동작 | SDK 호출 |
|------|---------|
| 작업 시작 | thread 생성 → `proposal` 그래프 실행 (진행 상태 스트리밍) |
| HITL ① 공고 선택 | interrupt 데이터(추천 5건) 표시 → 선택한 `tender_id`로 재개 |
| 초안 템플릿 미리보기 | 실행 종료 후 State의 `proposal_html`을 sanitize해 표시 |
| 다운로드 | State의 `proposal_html`을 `.html` 파일로 저장 |

**설계 포인트**
- Supervisor는 모든 작업 노드의 결과를 받아 다음 노드를 정하는 허브 역할. PoC 1차는 규칙 기반 라우팅으로 흐름을 고정하고, LLM 기반 작업 분해는 검증 Agent와 함께 2차 목표에서 적용
- `interrupt`로 HITL ①에서 실행을 멈추고, LangGraph Server의 thread checkpoint가 State를 보존해 React에서 재개 요청 시 같은 지점부터 이어서 실행
- `build_proposal_template`는 LLM 없이 템플릿에 값을 삽입하는 단일 노드 (2.3절). 프로필 값만 삽입하므로 근거성 KPI를 구조적으로 지킴
- 확장 단계에서 LLM 문장 생성을 도입하면 `build_proposal_template` 뒤에 HITL ②(`review_proposal`) 노드를 추가
- 검증 Agent(2차 목표)는 `route`에 `build_proposal_template` 다음 분기로 추가 예정

## 11. Azure OpenAI 설정

### 11.1 설정 고정표

생성은 Azure OpenAI, 임베딩은 로컬 BGE-M3로 나눕니다. 임베딩을 오픈소스로 두는 이유는 2.문제정의및서비스계획 제약사항(외부 의존성 최소화)이며, 필요하면 환경변수만 바꿔 Azure Embedding으로 전환합니다.

| 사용 목적 | 사용 리소스 / 배포명 | 환경변수 | 참조 모듈 |
|---------|-----------------|--------|---------|
| Generation | 과정 제공 Azure OpenAI 리소스 / 배포명 **`gpt-4.1`** (과정 안내 배포명으로 확정) | `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_API_KEY`, `OPENAI_API_VERSION`, `AZURE_OPENAI_CHAT_DEPLOYMENT` | `app/config.py`의 `get_chat_model()` → `app/agents/*`, `scripts/check_env.py` |
| Embedding (PoC) | 로컬 BGE-M3 `BAAI/bge-m3` (Azure 리소스 사용 안 함) | `EMBEDDING_PROVIDER=local`, `EMBEDDING_MODEL` | `app/config.py`의 `get_embeddings()` → `app/tools/embedding.py`, `scripts/ingest.py` |
| Embedding (대체안) | 같은 Azure 리소스 / `text-embedding-3-small` 배포 | `EMBEDDING_PROVIDER=azure`, `AZURE_OPENAI_EMBEDDING_DEPLOYMENT` | 위와 동일 (코드 변경 없음) |
| Vector DB | 로컬 Chroma | `CHROMA_DIR` | `app/tools/embedding.py`, `scripts/ingest.py` |

코드에는 모델명을 쓰지 않고 `app/config.py`만 환경변수를 읽습니다. 나머지 모듈은 `get_chat_model()`, `get_embeddings()`를 호출하므로 배포명이 바뀌어도 `.env`만 수정하면 됩니다. `langchain-openai`의 `AzureChatOpenAI`는 `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_API_KEY`, `OPENAI_API_VERSION`을 환경변수에서 바로 읽습니다.

### 11.2 Agent별 모델 매핑 ([초기 설정값])

PoC에서는 생성 배포 1개(`gpt-4.1`)를 모든 Agent가 공유하고, Agent별로 temperature와 출력 형식만 다르게 둡니다. 배포가 하나면 할당량과 설정 관리가 단순하고, 비용이나 속도 문제가 실측으로 확인된 Agent만 별도 배포로 분리합니다.

| Agent / 처리 | 모델 | temperature | 출력 형식 | 분리 검토 조건 |
|------------|-----|-------------|---------|-------------|
| Supervisor | 사용 안 함 (규칙 기반 라우팅, 7장) | - | - | - |
| 공고 분석 Agent | gpt-4.1 | 0 | 구조화 출력 JSON (`TenderInfo`) | 30건 반복 호출 비용이 크면 `gpt-4.1-mini`로 분리 |
| 매칭 Agent: 자격 판정·적합도 점수 | 사용 안 함 (규칙 + BGE-M3 유사도, 2.4절) | - | JSON | - |
| 매칭 Agent: 추천 근거 | gpt-4.1 | 0 | JSON (근거마다 출처 필드·값 포함) | - |
| 제안서 템플릿 모듈 | 사용 안 함 (고정 템플릿 + 입력값 삽입) | - | HTML | 확장 단계에서 섹션별 문장 생성 도입 시 gpt-4.1 |
| `check_env.py` 연결 확인 | gpt-4.1 | 0 | 텍스트 | - |
| 임베딩 (유사도·Chroma 적재·실적 검색) | BGE-M3 (로컬) | - | 벡터 | 처리 속도가 부족하면 Azure Embedding으로 전환 |

### 11.4 비밀값 관리

- `.env`는 `.gitignore`에 넣어 커밋하지 않고, 변수 이름만 적은 `.env.example`을 커밋합니다.
- LangGraph Server는 `langgraph.json`의 `"env": ".env"`로 실행 시 자동으로 읽고, `scripts/`는 `python-dotenv`로 읽습니다.
- React 쪽에는 Azure 키를 두지 않습니다. `VITE_`로 시작하는 값은 브라우저에 노출되므로 서버 주소만 넣고, 모든 LLM 호출은 LangGraph Server에서 수행합니다.

### 12.3 평가 스크립트 실행

평가는 두 단계로 나눕니다. ① `--run`으로 평가용 결과를 만들고 ② `--kpi`로 그 결과를 정답 데이터와 대조합니다. `--run` 없이 실행하면 `outputs/`에 이미 있는 결과만 채점하므로, LLM을 다시 호출하지 않고 채점 로직만 반복 확인할 수 있습니다.

| 단계 | 명령 | 입력 | 출력 |
|------|-----|-----|-----|
| ① 결과 생성 | `uv run python scripts/evaluate.py --run` | `data/companies/*.json`, `data/tenders/*.json` | `outputs/recommendations/{company_id}.json` (기업별 상위 5건), `outputs/drafts/{tender_id}_{company_id}.html` (공고별 추천 1순위 기업 초안 템플릿 30건) |
| ② 채점 | `uv run python scripts/evaluate.py --kpi accuracy,eligibility,evidence,template,groundedness` | ①의 결과 + 아래 표의 정답 데이터 | 콘솔 요약 + `outputs/eval/report_YYYYMMDD.json` |

`--run`은 그래프를 서버 없이 직접 실행하며, HITL ①은 1순위 공고를 자동 선택합니다. `--company company_01`처럼 기업을 지정하면 1개사만 평가합니다.

**평가 대상 선택 (`--split`)**: 가중치를 맞춘 데이터로 성능을 재면 과대평가되므로 기업을 둘로 나눕니다 (3.시나리오수립 KPI 1 '정답셋 구성 원칙').

| `--split` | 대상 | 용도 | 사용 KPI |
|-----------|-----|-----|---------|
| `tune` | 기업 01-05 | 가중치 조정. 여러 번 실행해도 됨 | `accuracy`, `eligibility`, `evidence` |
| `test` | 기업 06-10 | **최종 KPI 판정**. 가중치 확정 후 1회만 실행 | `accuracy`, `eligibility`, `evidence` |
| `all` (기본값) | 기업 01-10 | 라벨이 필요 없는 초안 템플릿 KPI | `template`, `groundedness` |

**Phase 4 실행 순서**

```powershell
# 1. 라벨 점검 (기업별 '추천' 3건 이상, 체크리스트 c1-c4와 라벨 일치)
uv run python scripts/evaluate.py --check-labels
# 2. 가중치 조정: 조정용으로 반복 실행 (가중치 순서: 기술,경험,인력)
uv run python scripts/evaluate.py --split tune --run --kpi accuracy --weights 0.4,0.4,0.2
# 3. Precision@3이 가장 높은 가중치를 .env의 SCORE_WEIGHTS에 확정한 뒤 평가용으로 1회 측정
uv run python scripts/evaluate.py --split test --run --kpi accuracy,eligibility,evidence
# 4. 초안 템플릿 KPI
uv run python scripts/evaluate.py --split all --run --kpi template,groundedness
```

`--kpi all`은 위 3·4단계를 한 번에 실행합니다(라벨 KPI는 `test`, 템플릿 KPI는 `all` 대상). 리포트에는 조정용 결과도 참고로 함께 남기지만 KPI 판정에는 평가용 결과만 씁니다.

**자동 판정 범위** (3.시나리오수립 KPI 측정 종합표 기준)

| KPI (`--kpi` 값) | 입력 | 스크립트 출력 | 사람이 하는 일 |
|-----|-----|------------|-------------|
| 추천 정확도 (`accuracy`, 1순위) | `outputs/recommendations/`, `data/labels/labels.csv` | 기업별 상위 3건과 정답 라벨 대조 → **Hit Rate@3** (판정, 목표 80%), **Precision@3** (품질, 목표 0.67), 오류 유형(자격 필터 / 적합도 점수)과 어긋난 체크리스트 조건(c1-c4) | 체크리스트 기준 정답 라벨 사전 작성 |
| 자격 필터 정확성 (`eligibility`, 1순위) | 위와 동일 | 상위 5건 중 '부적격' 공고 수, 규칙 기반 판정과 '부적격' 라벨 일치율 | 없음 (라벨 공유) |
| 추천 근거 설명 가능성 (`evidence`, 1순위) | `outputs/recommendations/`, `data/companies/`, `data/tenders/` | 근거 출처 확인 비율, 불일치 근거 목록 (`check_evidence_sources`) | 불일치 근거만 검토 |
| 초안 시작 가능 여부 (`template`, 보조) | `outputs/drafts/`, `data/tenders/`, `data/companies/` | 30건 생성·HTML 파싱 성공 여부, 필수 입력 항목 반영률 | 없음 |
| 초안 근거성 (`groundedness`, 보조) | `outputs/drafts/`, `data/companies/` | 불일치 항목 목록 (`check_groundedness`) | 불일치 발생 시 원인 확인 |

시간 단축, 담당자 만족도는 사람이 기록·평가하므로 스크립트 대상이 아닙니다.

### 12.4 자주 막히는 지점

| 증상 | 원인 | 해결 |
|-----|-----|-----|
| `uv`, `node` 명령을 찾을 수 없음 | 설치 직후 PATH 미반영 | 터미널을 새로 열기 |

| 첫 `run_demo.py`가 오래 멈춤 | BGE-M3 최초 다운로드 (약 2.3GB) | 1회만 발생. 캐시 위치를 바꾸려면 `HF_HOME` 환경변수 지정 |

| `langgraph dev` 실행 시 `app` import 오류 | 패키지 미설치 | `uv sync` 재실행 (9.4절 `[tool.hatch...]` 설정 확인) |

## 13. 최소 실행 경로 (첫 구현 대상)

'PoC 모듈 구현' Task의 기준 구현 대상은 **SC-001 단독 성공 경로**입니다: **기업 프로필 1개 + 공고 묶음 입력 → 자격·선호 필터 → 점수 계산 → 상위 추천 5건 출력**. 이 경로가 동작한 뒤에만 공고 분석 Agent(LLM), 그래프·HITL, SC-002 템플릿 순서로 넓힙니다.

### 13.1 고정 경로

| 항목 | 내용 |
|-----|-----|
| 입력 | `data/sample/company_01.json` (기업 1개) + `data/sample/tenders/` (공고 10건) |
| 공고 구성 | 추천 대상 후보 7건 + 필수 자격 미충족 2건 + 예산 범위 밖 1건 (필터·순위가 모두 동작하는지 보이도록 구성) |
| 공고 형식 | 공고 분석 Agent의 출력 형식(`TenderInfo`)으로 직접 작성. 그래서 이 경로는 LLM을 호출하지 않음 |
| 처리 | `match_qualifications` + `filter_tenders` (규칙) → `calculate_match_score` (규칙 + BGE-M3, 2.4절) → 점수 내림차순 상위 5건 |
| 추천 근거 | 항목별 점수에서 규칙으로 만든 근거 문장 + 출처 필드 (LLM 근거 생성은 6.2절 구현 순서 2에서 연결) |
| 출력 | 콘솔 JSON + `outputs/recommendations/company_01.json` |
| 필요한 것 | `uv sync`만. `.env`·Azure 키·LangGraph Server·Chroma·React 모두 불필요 |

```
company_01.json ─┐
                 ├→ 자격 판정·선호 필터 (규칙) ─→ 적합도 점수 (규칙 + BGE-M3) ─→ 상위 5건 + 근거 + 제외 사유 JSON
tenders/ 10건 ───┘        └→ 제외 3건 (사유 기록)
```

> **선택 근거 (최소 경로에서 LLM 제외)**: 메인 KPI(추천 정확도·자격 필터 정확성)를 결정하는 것은 필터와 점수 로직이고, 이 둘은 LLM을 쓰지 않습니다(2.4절). LLM을 빼면 누구나 키 없이 같은 결과를 재현할 수 있고, 결과가 틀렸을 때 원인을 점수 로직 안에서만 찾으면 됩니다.

### 13.2 실행 명령

```powershell
uv sync                                    # 최초 1회
uv run python scripts/run_demo.py          # 기본 입력: data/sample/company_01.json + data/sample/tenders/
uv run pytest tests/test_min_path.py       # 통과 기준 자동 확인
```

옵션: `--company <기업 JSON 경로>`, `--tenders <공고 폴더>`, `--top-k 5`. 예를 들어 `--tenders data/tenders`로 공고 30건에 같은 경로를 적용할 수 있습니다 (공고가 `TenderInfo` 형식일 때).

### 13.3 기대 출력과 통과 기준

**기대 출력 (형식 예시, 값은 가상 데이터)**

## 14. 기술 선택 근거

**선택 기준**은 세 가지입니다: ① 8주(하루 1-2시간) 안에 구현할 수 있는가, ② 로컬에서 바로 검증할 수 있는가, ③ 과정 제공 Azure 자원과 맞는가. **[PoC 임시]** 표시는 PoC 검증 결과에 따라 바뀔 수 있는 선택입니다.

모든 항목을 같은 형식으로 적었습니다: **선택 → 현재 PoC에 맞는 이유(1-2문장) → 검토한 대안과 보류 이유 → 재검토 조건**. '재검토 조건'은 이 결정을 다시 열어볼 신호이며, 발표에서 "왜 이렇게 했고 언제 바꾸는가"를 설명하는 근거로 씁니다. 설계 본문에 `> 선택 근거`를 붙인 항목은 '상세' 열에 위치를 표시했습니다.

### 14.1 설계 결정

| 구분 | 선택 | 현재 PoC에 맞는 이유 | 검토한 대안과 보류 이유 | 재검토 조건 | 상세 |
|------|-----|-----------------|-------------------|----------|-----|
| 적합도 계산 | 규칙 필터 + BGE-M3 유사도 하이브리드 | 자격·인원은 충족 여부가 분명해 규칙이 정확하고 '부적격 0건'을 보장합니다. 기술·실적은 표현이 달라도 의미가 같은 경우가 많아 유사도로 비교합니다. | LLM 판정: 결과가 매번 달라 재현·설명이 어렵고 호출 비용 발생 / 키워드 일치만: "벡터 검색"과 "벡터DB" 같은 동의어를 놓침 | 조정용 데이터에서 Precision@3이 목표(0.67)에 못 미치고 오류가 '적합도 점수' 유형에 몰릴 때 | 2.4 |
| 제안서 생성 | 고정 템플릿 + 입력값 삽입 (LLM 미사용) | 같은 입력이면 결과가 같아 테스트가 쉽고, 프로필 값만 넣으므로 '없는 사실 기재 0건'을 구조적으로 지킵니다. 남는 시간을 메인 기능(SC-001)에 씁니다. | Sub-Agent 4개가 섹션 문장 생성: 환각 검증·품질 평가까지 8주 안에 끝내기 어려움 | SC-001 1순위 KPI를 모두 달성하고 시간이 남을 때 (6.1절 확장 기능) | 2.3, 6.1 |
| Supervisor 라우팅 | 규칙 기반 (State에서 비어 있는 단계로 분기) | PoC 흐름은 '분석 → 매칭 → 선택 → 템플릿' 고정 순서라 규칙으로 충분하고, 잘못된 분기를 바로 추적할 수 있습니다. | LLM 작업 분해: 흐름이 고정된 PoC에서는 이점 없이 비용과 결과 변동만 늘어남 | 검증 Agent(재작성 루프)를 도입해 분기가 동적으로 바뀔 때 | 7 |
| HITL | 공고 선택 1곳만 필수 (`interrupt`) | '최종 의사결정은 담당자'라는 전제(1.1절)를 지키는 최소 지점입니다. | 제안서 확정 HITL ②: 템플릿 결과는 입력이 같으면 항상 같아 확인할 것이 없음 | 제안서에 LLM 문장 생성을 도입할 때 | 2.1 |
| Checkpoint | LangGraph Server 내장 (서버 없이 실행하는 스크립트는 `InMemorySaver`) **[PoC 임시]** | HITL ①의 '중단 → 화면에서 선택 → 같은 지점에서 재개'를 저장소 코드 없이 thread 단위로 제공합니다. PoC 세션은 하루 안에 끝나 장기 보존이 필요 없습니다. | SqliteSaver·Postgres: 재시작 후에도 보존되지만 설정·관리가 추가됨 | `langgraph dev` 재시작 후 대기 중이던 thread를 잃는 문제가 Phase 3 확인에서 실제로 불편할 때 | 2.5 |
| 추천 평가 지표 | Hit Rate@3 (판정, 80%) + Precision@3 (품질, 0.67) | 담당자는 1건만 고르므로(HITL ①) Hit Rate@3이 작업 성공과 대응하고, 나머지 추천을 검토하는 낭비는 Precision@3으로 드러냅니다. | Hit Rate@3 단독: 1건만 맞아도 성공이라 품질 설명이 약함 / nDCG: 순위까지 반영하지만 계산과 발표 설명 부담 | 담당자 인터뷰에서 1위 추천의 중요도가 특히 높다고 확인될 때 (Hit Rate@1 추가) | 12.3, 3번 KPI 1 |
| 평가 데이터 분리 | 기업 기준: 조정용 01-05 / 평가용 06-10 | 가중치를 맞춘 데이터로 성능을 재면 과대평가되므로 분리합니다. 기존 '5개사 → 10개사 확장' 일정과 그대로 맞습니다. | 공고 기준 분리: 기업당 후보 공고가 15건으로 줄어 추천 조건이 달라짐 / 분리 안 함: 과적합 위험 | 정답셋을 기업 20개사 이상으로 늘릴 때 (교차 검증 검토) | 12.3 |
| 최소 실행 경로 | LLM 없이 필터·점수·순위만 | 메인 KPI를 결정하는 로직만 먼저 고정하고, 키 없이 누구나 같은 결과를 재현할 수 있습니다. | 처음부터 전체 그래프: 실패 원인이 LLM·서버·로직 중 어디인지 나누기 어려움 | 13장 1단계 통과 후 2단계(공고 분석 Agent)로 넘어갈 때 | 13 |
| 데이터 수집 | 1회 수집한 정적 데이터셋 (공고 30건) | 정답 라벨과 공고가 고정되어야 KPI를 반복 측정할 수 있습니다. | 나라장터 API 실시간 연동: 공고가 계속 바뀌어 정답셋을 유지할 수 없음 (2번 문서 Out of Scope) | PoC 이후 운영 단계 | 12.2 |
