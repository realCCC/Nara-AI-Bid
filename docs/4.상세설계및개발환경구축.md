# Part 1. 상세 설계

## 1. Agent 페르소나 및 시스템 프롬프트

### 1.1 Agent 정의

| 항목 | 정의 |
|-----|------|
| Agent 이름 | 나라장터 입찰 어시스턴트 (Proposal Assistant) |
| 주요 역할 | 입찰 담당자를 위한 공고 추천·의사결정 지원(메인). 선택한 공고의 제안서 초안 템플릿은 템플릿 모듈이 생성 |
| 핵심 목표 | 1) 정확한 추천 (Hit Rate@3 80%·Precision@3 0.67, 하드 필터 기준 '부적격' 0건) 2) 출처가 확인되는 추천 근거 제시 (95%) 3) 공고 검토 + 제안서 골격 작성 시간 50% 이상 단축 4) 업체 프로필·공고서에 없는 사실 기재 0건 |
| 기본 전제 | 최종 의사결정(공고 선택, 제안서 최종 작성)은 반드시 담당자가 한다. Agent는 판단에 필요한 정보와 분석 근거만 제공 |
| LLM 사용 범위 | RAG 추천(10건 순위·근거)과 SC-002 평가항목 추출 두 곳만. 하드 필터·소프트 점수·템플릿 삽입은 룰 |
| 톤앤매너 | 전문가형 조력자: 공식적, 근거 기반, 신뢰감 중심. 추천 시 판단 근거를 3-4가지로 명시 |
| 제약사항 | 추측·불확실한 정보 금지, 의사결정 주도 금지, 과장된 표현 금지, 근거 제시 필수 |

### 1.2 System Prompt (공통)

```text
당신은 나라장터 입찰을 지원하는 전문가형 의사결정 조력자입니다.

[역할과 책임]
- 입찰 담당자의 공고 검토, 선별, 제안서 작성을 돕는 조력자 역할
- 업체 역량과 공고서 내용을 객관적으로 분석하고 연결
- 최종 의사결정은 담당자가 하도록 필요한 정보와 근거만 제공

[의사결정 원칙]
- 항상 입력된 데이터(업체 프로필, 공고 필드, 공고서 청크)와 객관적 근거로 판단 (추측 금지)
- 입력 데이터에 없는 정보는 "확인 필요"로 표시
- 공고서 내용을 근거로 쓸 때는 청크 원문을 그대로 인용하고 파일명·페이지를 함께 표시
- 필드 값을 근거로 쓸 때는 필드명과 값을 함께 표시

[답변 구조]
1. 추천 이유 3-4가지 명시 (과업 일치, 실적, 업종, 규모, 참가자격 등)
2. 충족 항목과 '자격 확인 필요' 항목을 명확히 구분 표시
3. 최종 판단은 담당자가 하도록 안내

[금지사항]
- 실제 낙찰 확률·평가 점수 예측 (정부 입찰 결과는 예측 불가)
- "적합하지 않습니다"처럼 일방적 거절 (대신 부족한 자격 분석 제시)
- 최종 입찰 여부 결정 (담당자만 가능)
- 입력에 없는 문장을 인용 문구로 만드는 것
```

### 1.3 Agent별 역할 프롬프트 요약

공통 System Prompt 위에 Agent별 역할 지시를 추가합니다.

| Agent / 모듈 | 역할 지시 요약 | 출력 형식 |
|-------|-------------|---------|
| Supervisor | State에서 비어 있는 단계를 찾아 다음 노드로 보냄 (규칙 기반, LLM 미사용) | 다음 실행 노드 이름 |
| 룰 모듈 (Agent 아님) | 하드 필터(H1-H6)와 소프트 점수(S1-S4) 계산. 프롬프트 없음 | `FilterResult`, `ScoredTender` (JSON) |
| RAG 추천 Agent | 업체 프로필 + 10건의 공고 필드 + 공고별 검색 청크를 읽고 10건의 순위와 근거 3-4개 생성. 근거마다 출처(PDF 인용 또는 필드) 표시, 공고서에서 업체가 충족하지 못하는 자격이 보이면 `qualification_flags`에 기록하고 순위를 낮춤 | `Recommendation` 목록 (JSON) |
| 평가항목 추출 (SC-002) | 선택 공고의 PDF 청크에서 평가항목·배점·과업기간만 추출. 원문에 없으면 null, 항목마다 출처(파일·페이지) | `CriteriaExtraction` (JSON) |
| 제안서 템플릿 모듈 (Agent 아님) | 고정 템플릿에 공고·업체·추천 근거·추출 평가항목 값을 삽입. LLM을 호출하지 않으므로 프롬프트 없음 | HTML (`<section>` 4개 + 대응표) |

**RAG 추천 Agent 출력 스키마 (`Recommendation`)**

```json
{
  "rank": 1,
  "bidNtceNo": "R26BK01501726",
  "summary": "중등 교원 대상 AI·디지털 교육 연수 운영",
  "reasons": [
    {"text": "과업이 업체의 교원 연수 실적과 같은 유형", "source_type": "pdf",
     "file": "공고문.pdf", "page": 1, "quote": "학교로 찾아가는 AI·디지털 기반 교육혁신 연수"},
    {"text": "공고 세부분류가 업체 업종에 포함", "source_type": "field",
     "field": "tender.pubPrcrmntClsfcNo", "value": "86101696"}
  ],
  "qualification_flags": []
}
```

**제안서 섹션 ID** (3.시나리오수립 SC-002 기대 출력과 동일)

| 섹션 | section id | 삽입하는 입력값 | `[확인 필요]`로 남기는 자리 |
|------|-----------|--------------|-----------------------|
| 1. 회사소개 | `company` | 회사명, 설립연도, 역량 키워드, 인증, 과거 실적 | 회사 비전·차별화 포인트 |
| 2. 수행방안 | `approach` | RAG 추천 근거, 추출한 기술능력 평가항목(목차), 항목별 관련 업체 근거 | 항목별 수행 방안 본문 |
| 3. 추진일정 | `schedule` | 고정 단계(착수·분석 / 수행 / 완료·보고) + 추출한 과업기간 | 단계별 기간 |
| 4. 조직구성 | `organization` | 역할별 보유 인원 | 투입 인력·역할 분담 |
| 5. 평가기준 대응표 | `criteria` | 평가항목·배점·출처, 대응 섹션, 관련 업체 근거 | 추출 실패·근거가 없는 항목 |

**템플릿 규칙**

```text
- 템플릿 파일은 허용 태그만 사용한다: section, h2, h3, p, ul, ol, li, table, thead, tbody, tr, th, td, strong, em, br
- 삽입하는 값은 모두 HTML 이스케이프한다 (Jinja2 autoescape=True. 공고서 원문은 외부 데이터이므로 태그로 해석되지 않게 함)
- 입력 데이터에 값이 없으면 추측하지 않고 "[확인 필요]"를 넣는다.
```

## 2. Agent 아키텍처 및 오케스트레이션

### 2.1 전체 구조 (Supervisor 패턴)

```
    React 화면  ──(LangGraph SDK: 실행 · 스트리밍 · 재개)──▶  LangGraph Server
                                                                 │
                                                          ┌──────┴───────┐
                                                          │  Supervisor  │
                                                          └──────┬───────┘
                  ┌──────────────────────┬───────────────────────┼──────────────────────┐
                  ▼                      ▼                       ▼                      ▼
          ┌──────────────┐      ┌──────────────┐        ┌───────────────┐      ┌──────────────────┐
          │ 하드 필터    │      │ 소프트 점수  │        │ RAG 추천      │      │ 제안서 템플릿     │
          │ (룰, 500건)  │ ──▶ │ (룰, 상위10) │ ──▶   │ Agent (10건)  │      │ 모듈 + 평가항목   │
          └──────────────┘      └──────────────┘        │ PDF→청크→LLM  │      │ 추출 (SC-002)    │
                                                        └───────────────┘      └──────────────────┘
                                                 [HITL ①] 공고 선택
```

| 구성 요소 | PoC 범위 | 비고 |
|---------|---------|------|
| Supervisor | **필수** | LangGraph 조건 분기로 흐름 제어 (규칙 기반) |
| 하드 필터 (룰) | **필수** | 공고 500건 → 업체별 후보. 제외 사유 기록 |
| 소프트 점수 (룰) | **필수** | 후보 → 상위 10건 + 항목별 점수 |
| RAG 추천 Agent | **필수 (메인)** | 10건 PDF 다운로드·파싱·청킹·임베딩·검색 → LLM 순위·근거. 품질 투자를 집중하는 구성 요소 |
| 평가항목 추출 | **필수 (축소)** | SC-002. 선택 공고 1건의 PDF 청크에서 LLM 구조화 추출 |
| 제안서 템플릿 모듈 | **필수 (축소)** | SC-002 초안 템플릿 + 평가기준 대응표, 고정 템플릿 + 입력값 삽입 |
| HITL ① 공고 선택 | **필수** | `interrupt` → React에서 응답 → `Command(resume=...)`로 재개 |
| HITL ② 제안서 확정 | **확장** | 본문은 템플릿 삽입이라 생략. LLM 문장 생성을 도입할 때 추가 |
| 검증 Agent (자기 검증·재작성 루프) | **확장 (2차 목표)** | 2.문제정의및서비스계획 기능 4. 재작성 최대 2회 상한 (근거: 2.문제정의및서비스계획 보조 지표) |

> **선택 근거 (Supervisor 패턴 + HITL 1곳)**: 작업 노드가 모두 Supervisor로 돌아오는 구조라, 이후 검증 Agent를 추가할 때 분기 하나만 더하면 됩니다. PoC에서는 흐름이 고정 순서라 Supervisor를 규칙 기반으로 두고(7장), 사람의 판단이 반드시 필요한 공고 선택 한 곳에만 HITL을 둡니다. 전체 결정과 재검토 조건은 14.1절에 모았습니다.

### 2.2 공고 추천 워크플로우 (SC-001)

| 단계 | 담당 | 처리 내용 |
|------|-----|---------|
| 1. 입력 | 담당자 + System | React에서 업체 프로필 JSON 업로드, 스키마 검증. 공고 500건 파일 로드·정규화(공백 제거, 금액 숫자 변환, 담당자 연락처 등 PII 필드 제거) |
| 2. 하드 필터 | 룰 모듈 | H1 PDF 보유, H3 업종, H4 참가 제한, H5 지역 제한(수동 매핑표), H6 예산 범위. H2 마감일은 테스트 데이터라 미적용. 공고별 통과·제외 사유 기록 (3.시나리오수립 SC-001 2단계) |
| 3. 소프트 점수 | 룰 모듈 | S1-S4 가중합으로 0-100점 → 상위 10건 **[초기 설정값]** + 항목별 점수 (2.4절) |
| 4. RAG 추천 | RAG 추천 Agent | 10건 PDF 다운로드(캐시) → 텍스트 추출 → 청킹 → BGE-M3 임베딩·Chroma 적재 → 공고별 검색 → LLM 순위·근거 3-4개(출처 포함) → 출처 대조 |
| 5. **[HITL ①] 공고 선택** | 담당자 | React 화면에서 10건(상위 3건 강조) 검토 후 1건 선택 → 승인 |
| 6. 저장 및 전환 | System | 선택 결과와 해당 공고 청크를 같은 thread의 State에 저장, SC-002로 진행 |

공고 500건 전체에 LLM을 쓰지 않고, 룰로 10건까지 줄인 뒤에만 PDF를 읽습니다. 그래서 업체 1건당 LLM 호출이 1회(10건 일괄 순위)로 고정되고, 1-3단계 결과는 같은 입력이면 항상 같습니다.

### 2.3 제안서 초안 템플릿 워크플로우 (SC-002)

| 단계 | 담당 | 처리 내용 |
|------|-----|---------|
| 1. 입력 | System | 선택 공고 필드 + 업체 프로필 + RAG 추천 근거 + 해당 공고 PDF 청크를 State에서 로드 |
| 2. 평가항목 추출 | 평가항목 추출 (LLM) | "평가 항목/배점/기술능력평가/과업 기간" 질의로 청크 검색 → `CriteriaExtraction` 추출, Pydantic 검증. 평가항목이 없으면 `techAbltEvlRt`·`bidPrceEvlRt` 비율만 사용 |
| 3. 초안 템플릿 생성 | 제안서 템플릿 모듈 | 섹션 4개 템플릿에 입력값 삽입. 평가항목별 관련 업체 근거는 BGE-M3 유사도(평가항목 ↔ 역량 키워드·실적명)로 선택, 임계값 미만이면 `[확인 필요]` |
| 4. 평가기준 대응표 | 제안서 템플릿 모듈 | 평가항목·배점·출처 + 대응 섹션 + 관련 업체 근거를 표 템플릿에 삽입 |
| 5. 조립·미리보기 | System + React | 단일 HTML 문서로 조립 → sanitize 후 미리보기 |
| 6. 다운로드 | 담당자 | `.html` 다운로드 후 `[확인 필요]` 자리 작성 |

> **선택 근거 (LLM 생성 → 템플릿 삽입으로 축소, 추출에만 LLM)**: 평가항목은 정형 필드에 없고 공고서에만 있어 사람이 옮기거나 LLM이 읽어야 합니다. 추출은 "원문에 있는 값을 구조화"하는 일이라 결과를 원문과 자동 대조할 수 있으므로 LLM을 여기까지만 쓰고, 본문은 템플릿 삽입으로 둡니다. 그래서 '없는 사실 기재 0건'(근거성 KPI)을 업체 사실은 구조적으로, 평가항목은 원문 대조로 지킬 수 있습니다.

### 2.4 소프트 점수와 RAG 순위

2.문제정의및서비스계획 '적합 공고 정의'의 세 단계를 그대로 처리 순서로 사용합니다: **입찰 자격(Eligibility)** 은 하드 필터, **기업 적합도(Suitability)** 는 아래 소프트 점수로 상위 10건 선별, **추천 순위(Ranking)** 는 RAG 추천 Agent가 10건의 공고서를 읽고 정합니다.

**소프트 점수 (룰)**

| 항목 | 가중치 | 계산 (0-1) | 사용 필드 |
|------|------|---------|------|
| S1 업종 세부 분류 일치 | 35% | 세부분류번호 일치 1.0 / 대분류만 일치 0.4 | 공고 `pubPrcrmntClsfcNo`, `pubPrcrmntLrgClsfcNm` ↔ 업체 `업종` |
| S2 공고명 ↔ 역량 키워드 겹침 | 30% | 공고명에 나오는 업체 역량 키워드 수 k → min(k, 3) / 3 | 공고 `bidNtceNm` ↔ 업체 `역량키워드` |
| S3 예산 ↔ 실적 규모 유사도 | 20% | r = 공고 예산 / 업체 과거 실적 평균 계약금액 → min(r, 1/r). 예산 없으면 0.5 | 공고 `asignBdgtAmt` ↔ 업체 `과거실적.계약금액` |
| S4 계약방식 선호 | 15% | 선호 계약방식에 포함되면 1.0, 아니면 0 | 공고 `cntrctCnclsMthdNm` ↔ 업체 `선호계약방식` |

**룰 점수** = (S1 × 0.35 + S2 × 0.30 + S3 × 0.20 + S4 × 0.15) × 100 → 0-100점. 동점은 공고번호 오름차순.  
가중치는 **[초기 설정값]**이며, Phase 3에 조정용 업체 01-05 상위 10건 라벨의 Precision@10이 가장 높아지도록 조정한 뒤 **평가용 업체 라벨링 전에 고정**합니다 (가중치가 바뀌면 상위 10건이 바뀌어 라벨을 다시 붙여야 하므로, 12.3절).

**RAG 순위**: LLM이 10건을 한 번에 비교해 순위를 매깁니다. 공고서에서 업체가 충족하지 못하는 자격이 보이면 `qualification_flags`에 적고 하위로 보냅니다. LLM 출력 검증에 실패하면 룰 점수 순위와 룰 근거(항목별 점수 + 필드 출처)로 대체합니다 (5장).

> **선택 근거 (룰 선별 + RAG 순위)**: 자격·업종·예산처럼 '충족/미충족'이 정형 필드로 분명한 항목은 룰이 정확하고 설명하기 쉬우며, LLM 판정과 달리 '부적격 0건'을 보장할 수 있습니다. 과업 내용·참가자격 세부·평가 방법은 공고서에만 있어 룰로 볼 수 없으므로, 룰로 10건까지 줄인 뒤 그 10건의 공고서만 RAG로 읽습니다. 500건 모두에 RAG를 쓰면 PDF 다운로드·임베딩·LLM 비용이 50배가 되고, 룰만 쓰면 공고명 이상의 내용을 보지 못합니다. 같은 10건에 대해 룰 순위와 RAG 순위를 모두 평가하므로 RAG의 효과를 같은 라벨로 보여줄 수 있습니다.

### 2.5 상태(State) 관리

LangGraph의 공유 State 하나로 SC-001과 SC-002를 연결합니다. LangGraph Server의 **thread** 1개가 담당자 작업 세션 1개에 대응합니다.

| State 필드 | 내용 | 생성 시점 | 사용처 |
|-----------|------|---------|------|
| `company_profile` | 업체 프로필 (파싱 완료) | SC-001 1단계 | 전 단계 |
| `tenders` | 정규화된 공고 500건 | SC-001 1단계 | 하드 필터 |
| `filter_log` | 공고별 통과·제외와 사유 (규칙 ID, 비교 필드 값) | SC-001 2단계 | 화면 상세, 자격 필터 KPI |
| `top10` | 상위 10건 + 룰 점수 + 항목별 점수 | SC-001 3단계 | RAG 추천, 비교 지표 |
| `rag_chunks` | 공고별 PDF 청크 (`{bidNtceNo: [{file, page, text}]}`) | SC-001 4단계 | RAG 추천, 출처 대조, SC-002 추출 |
| `recommendations` | 10건 RAG 순위 + 근거(출처 포함) + 자격 확인 필요 항목 | SC-001 4단계 | HITL ①, 제안서 템플릿 |
| `selected_tender_id` | 담당자가 선택한 공고번호 | HITL ① | SC-002 전체 |
| `criteria` | 추출한 평가항목·배점·과업기간 (출처 포함) | SC-002 2단계 | 템플릿, 대응표 |
| `draft_sections` | 초안 템플릿 섹션 HTML 4개 (`{section_id: html}`) | SC-002 3단계 | 조립 |
| `criteria_table` | 평가기준 대응표 (HTML 표) | SC-002 4단계 | 조립 |
| `proposal_html` | 최종 조립된 HTML 문서 | SC-002 5단계 | 다운로드 |

**Checkpoint**: LangGraph Server가 thread별 checkpoint를 자동 저장하므로, 담당자가 화면을 닫았다가 돌아와도 HITL 대기 지점부터 이어서 실행합니다. 서버용 그래프는 checkpointer를 지정하지 않고, 서버 없이 그래프를 실행하는 스크립트(`evaluate.py`)만 `InMemorySaver`를 붙여 compile합니다 (`interrupt`는 checkpointer가 있어야 동작, 7장). `tenders` 500건은 State에 매번 넣지 않고 파일 경로만 두고 노드에서 읽어 checkpoint 크기를 줄입니다.

> **선택 근거 (서버 내장 checkpoint)**: HITL ①은 '실행 중단 → 화면에서 선택 → 같은 지점에서 재개'가 핵심이며, 서버가 이 동작을 thread 단위로 기본 제공하므로 저장소 코드를 따로 작성하지 않아도 됩니다. PoC 세션은 하루 안에 끝나므로 장기 보존(SqliteSaver·Postgres)은 필요해질 때 추가합니다.

| `export_document` | PDF/Word 변환 | `draft_id, format` | `.pdf` / `.docx` 파일 | 확장 |

### 3.6 도구 호출 규약 (하네스)

| 규칙 | 내용 |
|------|------|
| 출력 스키마 검증 | LLM JSON 출력은 Pydantic 모델로 검증 (`Recommendation`, `CriteriaExtraction`). 제안서 HTML은 템플릿 출력이므로 단위 테스트로 구조를 검증 |
| 출처 대조 | `rag_rank` 출력은 `check_evidence_sources`를 통과한 근거만 화면에 표시. 근거가 2개 미만으로 줄면 룰 근거로 보충 |
| 재시도 제한 | 검증 실패 시 최대 2회 재시도 **[초기 설정값]**, 이후 폴백 경로 실행 (비용·지연 상한) |

| 화면 렌더링 | React는 서버 HTML을 DOMPurify로 한 번 더 sanitize한 뒤 표시 (서버 검증과 이중 방어) |
| 로깅 | 도구 호출, 입력/출력 요약, 토큰 사용량, 필터 단계별 남은 공고 수를 기록 |

## 4. 지식 베이스 및 메모리 전략

### 4.1 RAG (검색 증강 생성) 전략

RAG는 목표 자체가 아니라 RAG 추천 Agent가 호출하는 도구 중 하나로 구성합니다 (1.역량및기술스택확인 하네스 원칙).

| 항목 | 결정 |
|------|------|
| 데이터 소스 | 업체별 소프트 점수 상위 10건의 공고서 PDF (공고 첨부 중 `.pdf`만). 업체 정보는 청킹하지 않고 프롬프트에 구조화 JSON으로 그대로 넣음 |
| PDF 수집 | `ntceSpecDocUrl*`에서 실행 시 내려받아 `data/pdfs/{bidNtceNo}/`에 캐시. 평가 실행 전에는 대상 업체들의 상위 10건 합집합을 미리 내려받음 (`scripts/fetch_pdfs.py`) |
| 텍스트 추출 | PyMuPDF 페이지 단위 추출. 텍스트가 거의 없는 페이지(스캔 이미지)는 건너뛰고 로그에 기록 (OCR은 확장) |
| 청킹 방식 | 페이지 안에서 문단 단위로 약 500자, 겹침 100자 **[초기 설정값]**. 메타데이터: `bidNtceNo`, `file`, `page`, `chunk_id` (출처 표시·대조에 사용) |
| 임베딩 모델 | BGE-M3 (오픈소스, 한국어 지원) |
| Vector DB | Chroma (로컬 실행). 실행 단위 컬렉션에 10건만 적재하고 실행 후 삭제 (청크 원문은 State·결과 파일에 보존) |
| 검색 | 공고별로 업체 역량 키워드·실적명 질의 + 고정 질의("입찰참가자격", "과업 내용", "평가 방법")로 top-k 5 **[초기 설정값]**, 중복 제거 |
| 활용처 | RAG 추천 Agent의 순위·근거 생성, SC-002 평가항목 추출, 평가항목별 관련 업체 근거 선택(같은 BGE-M3 모델) |
| 알려진 한계 | PDF 보유 437건 중 제안요청서·과업지시서까지 PDF인 공고는 63건. 나머지는 입찰공고문만 PDF라 과업 세부·평가항목 근거가 약함 → 오류 분석에서 '근거 부족' 유형으로 따로 집계 |

> **선택 근거 (10건만 청킹·임베딩)**: 500건 PDF를 모두 내려받아 색인하면 다운로드·임베딩 시간이 업체 수와 무관하게 커지고, 실제로 읽을 공고는 업체당 10건뿐입니다. 상위 10건만 처리하면 CPU 환경에서도 업체 1건당 처리 시간이 짧고, 검색 범위가 10건으로 좁아 다른 공고 청크가 섞일 위험도 줄어듭니다.  
> **선택 근거 (BGE-M3)**: 한국어 공고서 문장을 다국어 임베딩으로 비교할 수 있고, 오픈소스라 2번 문서 제약(외부 의존성 최소화)을 충족합니다.  
> **선택 근거 (Chroma)**: 실행당 청크 수백 개 규모에서는 별도 서버 없이 로컬로 충분하고, 공고번호·페이지 같은 메타데이터 필터를 기본 제공합니다.

8주(하루 1-2시간) 기준이며, 프로젝트 로드맵의 단일 기준입니다. 프로젝트는 2026-09-28에 시작했고 1-2주차는 기획 문서(1-4번 문서)에 사용했으므로, 개발은 **3-8주차(6주)**에 진행합니다. KPI 측정은 3.시나리오수립 KPI 측정 종합표에 따라 Phase 4에 수행합니다.

## 7. LangGraph 구조 예시

상세 설계 단계의 출발점이 되는 그래프 골격입니다. (의사코드 수준, 모델명은 설정값으로 분리)

```python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt


class ProposalState(TypedDict):
    company_profile: dict
    tenders_path: str                 # 공고 500건 파일 경로 (State에는 경로만)
    filter_log: list[dict]            # 공고별 통과·제외 + 사유
    top10: list[dict]                 # 상위 10건 + 룰 점수 + 항목별 점수
    rag_chunks: dict[str, list[dict]] # {bidNtceNo: [{file, page, text}]}
    recommendations: list[dict]       # RAG 순위 + 근거(출처 포함) + qualification_flags
    selected_tender_id: str | None
    criteria: dict                    # 추출한 평가항목·배점·과업기간 (출처 포함)
    draft_sections: dict[str, str]    # {section_id: "<section>...</section>"}
    criteria_table: str               # "<table>...</table>"
    proposal_html: str


def filter_and_score(state: ProposalState) -> dict:
    # 룰 모듈: 공고 로드 → hard_filter → soft_score → 상위 10건 (LLM 미사용)
    ...

def rag_recommend(state: ProposalState) -> dict:
    # RAG 추천 Agent: 10건 PDF → 청크 → 임베딩·검색 → LLM 순위·근거 → 출처 대조
    # 검증 실패 시 룰 점수 순위 + 룰 근거로 대체
    ...

def select_tender(state: ProposalState) -> dict:
    # HITL ①: React에서 공고 1건 선택할 때까지 대기
    tender_id = interrupt({"recommendations": state["recommendations"]})
    return {"selected_tender_id": tender_id}

def extract_criteria(state: ProposalState) -> dict:
    # SC-002: 선택 공고 청크에서 평가항목·배점 추출 (LLM, 원문에 없으면 null)
    ...

def build_proposal_template(state: ProposalState) -> dict:
    # 제안서 템플릿 모듈 (LLM 미사용): 섹션 4개 + 대응표에 입력값 삽입 → 단일 HTML 조립
    ...


def supervisor(state: ProposalState) -> dict:
    # Supervisor: 작업 노드 결과를 받아 다음 작업을 결정 (실제 분기는 route에서 수행)
    return {}

def route(state: ProposalState) -> str:
    # PoC 1차: State에 비어 있는 단계를 찾아 다음 노드로 보내는 규칙 기반 라우팅
    if "top10" not in state:
        return "filter_and_score"
    if "recommendations" not in state:
        return "rag_recommend"
    if not state.get("selected_tender_id"):
        return "select_tender"
    if "criteria" not in state:
        return "extract_criteria"
    if not state.get("proposal_html"):
        return "build_proposal_template"
    return END


WORKERS = {
    "filter_and_score": filter_and_score,
    "rag_recommend": rag_recommend,
    "select_tender": select_tender,
    "extract_criteria": extract_criteria,
    "build_proposal_template": build_proposal_template,
}

builder = StateGraph(ProposalState)
builder.add_node("supervisor", supervisor)
for name, fn in WORKERS.items():
    builder.add_node(name, fn)
    builder.add_edge(name, "supervisor")   # 작업이 끝나면 Supervisor로 복귀

builder.add_edge(START, "supervisor")
builder.add_conditional_edges("supervisor", route, [*WORKERS, END])

# LangGraph Server가 checkpointer를 주입하므로 compile 시 지정하지 않음
graph = builder.compile()


# 서버 없이 실행하는 스크립트(evaluate.py)용: interrupt를 쓰려면 checkpointer 필요
def build_local_graph():
    from langgraph.checkpoint.memory import InMemorySaver
    return builder.compile(checkpointer=InMemorySaver())
```

`top10`이 빈 목록(하드 필터 통과 0건)이어도 키가 생기므로 같은 노드를 반복하지 않고 다음 단계로 넘어가며, `rag_recommend`는 빈 목록을 그대로 반환합니다. `evaluate.py`는 `build_local_graph()`로 실행하다가 HITL ①에서 멈추면 `Command(resume=<1순위 bidNtceNo>)`로 자동 재개합니다.

서버 진입점 설정(`langgraph.json`)과 코드 위치는 10.3절에 있습니다.

**React 측 호출 흐름 (개념)**

| 동작 | SDK 호출 |
|------|---------|
| 작업 시작 | thread 생성 → `proposal` 그래프 실행 (필터 → 점수 → RAG 진행 상태 스트리밍) |
| HITL ① 공고 선택 | interrupt 데이터(추천 10건) 표시 → 선택한 `bidNtceNo`로 재개 |
| 초안 템플릿 미리보기 | 실행 종료 후 State의 `proposal_html`을 sanitize해 표시 |
| 다운로드 | State의 `proposal_html`을 `.html` 파일로 저장 |

**설계 포인트**
- Supervisor는 모든 작업 노드의 결과를 받아 다음 노드를 정하는 허브 역할. PoC 1차는 규칙 기반 라우팅으로 흐름을 고정하고, LLM 기반 작업 분해는 검증 Agent와 함께 2차 목표에서 적용
- 하드 필터와 소프트 점수는 항상 함께 실행되고 LLM을 쓰지 않으므로 노드 하나(`filter_and_score`)로 묶음. 최소 실행 경로(13장)는 이 노드의 도구 함수를 직접 호출
- `interrupt`로 HITL ①에서 실행을 멈추고, LangGraph Server의 thread checkpoint가 State를 보존해 React에서 재개 요청 시 같은 지점부터 이어서 실행
- LLM을 쓰는 노드는 `rag_recommend`, `extract_criteria` 두 개뿐이며, 둘 다 출력을 원문 대조로 검증
- 확장 단계에서 LLM 문장 생성을 도입하면 `build_proposal_template` 뒤에 HITL ②(`review_proposal`) 노드를 추가
- 검증 Agent(2차 목표)는 `route`에 `build_proposal_template` 다음 분기로 추가 예정

| Node.js | 22 LTS 이상 | `winget install --id OpenJS.NodeJS.LTS -e` | `node --version`, `npm --version` |

설치 후 새 터미널을 열어야 PATH가 반영됩니다. Node.js 20 LTS는 2026-04에 지원이 끝나 제외합니다.

## 11. Azure OpenAI 설정

### 11.1 설정 고정표

생성은 Azure OpenAI, 임베딩은 로컬 BGE-M3로 나눕니다. 임베딩을 오픈소스로 두는 이유는 2.문제정의및서비스계획 제약사항(외부 의존성 최소화)이며, 필요하면 환경변수만 바꿔 Azure Embedding으로 전환합니다.

| 사용 목적 | 사용 리소스 / 배포명 | 환경변수 | 참조 모듈 |
|---------|-----------------|--------|---------|
| Generation | 과정 제공 Azure OpenAI 리소스 / 배포명 **`gpt-4.1`** (과정 안내 배포명으로 확정) | `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_API_KEY`, `OPENAI_API_VERSION`, `AZURE_OPENAI_CHAT_DEPLOYMENT` | `app/config.py`의 `get_chat_model()` → `app/agents/*`, `scripts/check_env.py` |
| Embedding (PoC) | 로컬 BGE-M3 `BAAI/bge-m3` (Azure 리소스 사용 안 함) | `EMBEDDING_PROVIDER=local`, `EMBEDDING_MODEL` | `app/config.py`의 `get_embeddings()` → `app/tools/embedding.py` |
| Embedding (대체안) | 같은 Azure 리소스 / `text-embedding-3-small` 배포 | `EMBEDDING_PROVIDER=azure`, `AZURE_OPENAI_EMBEDDING_DEPLOYMENT` | 위와 동일 (코드 변경 없음) |
| Vector DB | 로컬 Chroma | `CHROMA_DIR` | `app/tools/embedding.py` |

코드에는 모델명을 쓰지 않고 `app/config.py`만 환경변수를 읽습니다. 나머지 모듈은 `get_chat_model()`, `get_embeddings()`를 호출하므로 배포명이 바뀌어도 `.env`만 수정하면 됩니다. `langchain-openai`의 `AzureChatOpenAI`는 `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_API_KEY`, `OPENAI_API_VERSION`을 환경변수에서 바로 읽습니다.

### 11.2 Agent별 모델 매핑 ([초기 설정값])

PoC에서는 생성 배포 1개(`gpt-4.1`)를 모든 Agent가 공유하고, Agent별로 temperature와 출력 형식만 다르게 둡니다. 배포가 하나면 할당량과 설정 관리가 단순하고, 비용이나 속도 문제가 실측으로 확인된 Agent만 별도 배포로 분리합니다.

| Agent / 처리 | 모델 | temperature | 출력 형식 | 분리 검토 조건 |
|------------|-----|-------------|---------|-------------|
| Supervisor | 사용 안 함 (규칙 기반 라우팅, 7장) | - | - | - |
| 룰 모듈: 하드 필터·소프트 점수 | 사용 안 함 (규칙, 2.4절) | - | JSON | - |
| RAG 추천 Agent: 10건 순위·근거 | gpt-4.1 | 0 | 구조화 출력 JSON (`Recommendation` 목록, 근거마다 출처) | 업체당 1회 호출. 입력이 길어 속도가 문제로 실측되면 공고별 청크 수(top-k) 축소 |
| 평가항목 추출 (SC-002) | gpt-4.1 | 0 | 구조화 출력 JSON (`CriteriaExtraction`) | 반복 호출 비용이 크면 `gpt-4.1-mini`로 분리 |
| 제안서 템플릿 모듈 | 사용 안 함 (고정 템플릿 + 입력값 삽입) | - | HTML | 확장 단계에서 섹션별 문장 생성 도입 시 gpt-4.1 |
| `check_env.py` 연결 확인 | gpt-4.1 | 0 | 텍스트 | - |
| 임베딩 (PDF 청크 적재·검색, 평가항목별 업체 근거) | BGE-M3 (로컬) | - | 벡터 | 처리 속도가 부족하면 Azure Embedding으로 전환 |

### 11.3 환경변수 목록 (`.env.example`)

### 11.4 비밀값 관리

- `.env`는 `.gitignore`에 넣어 커밋하지 않고, 변수 이름만 적은 `.env.example`을 커밋합니다.
- LangGraph Server는 `langgraph.json`의 `"env": ".env"`로 실행 시 자동으로 읽고, `scripts/`는 `python-dotenv`로 읽습니다.
- React 쪽에는 Azure 키를 두지 않습니다. `VITE_`로 시작하는 값은 브라우저에 노출되므로 서버 주소만 넣고, 모든 LLM 호출은 LangGraph Server에서 수행합니다.

### 12.3 평가 스크립트 실행

평가는 두 단계로 나눕니다. ① `--run`으로 결과를 만들고 ② `--kpi`로 그 결과를 정답 데이터와 대조합니다. `--run` 없이 실행하면 `outputs/`에 이미 있는 결과만 채점하므로, LLM을 다시 호출하지 않고 채점 로직만 반복 확인할 수 있습니다.

| 단계 | 명령 | 입력 | 출력 |
|------|-----|-----|-----|
| ① 결과 생성 | `uv run python scripts/evaluate.py --split test --run` | `data/companies/`, `data/raw/tenders_202605.json`, `data/region_limits.csv` | `outputs/recommendations/{company_id}.json` (필터 내역, 상위 10건 룰 점수, RAG 순위·근거), `outputs/drafts/{bidNtceNo}_{company_id}.html` (업체별 RAG 1순위 초안 템플릿) |
| ② 채점 | `uv run python scripts/evaluate.py --split test --kpi accuracy,eligibility,evidence,template,groundedness` | ①의 결과 + 정답 데이터 | 콘솔 요약 + `outputs/eval/report_YYYYMMDD.json` |

`--run`은 그래프를 서버 없이 직접 실행하며, HITL ①은 RAG 1순위 공고를 자동 선택합니다. `--company company_41`처럼 업체를 지정하면 1개만 평가합니다. `--rule-only`를 붙이면 RAG 없이 상위 10건까지만 만듭니다 (라벨링 시트용, LLM 미사용).

**평가 대상 선택 (`--split`)**: 조정에 쓴 데이터로 성능을 재면 과대평가되므로 업체를 나눕니다 (3.시나리오수립 KPI 1 '라벨링 절차').

| `--split` | 대상 | 용도 | 사용 KPI |
|-----------|-----|-----|---------|
| `tune` | 업체 01-05 | 가중치·프롬프트 조정. 여러 번 실행해도 됨 (라벨은 선택) | `accuracy` |
| `test` | 업체 41-50 | **최종 KPI 판정**. 가중치 고정 → 라벨 커밋 후 1회만 실행 | 전체 |
| `all` | 업체 01-50 | 데모·스모크 테스트 (라벨 없이 실행 여부만 확인) | 없음 |

**라벨링 절차 (Phase 3)**

```powershell
# 1. 조정용: 상위 10건 시트 생성 → 라벨링 → 가중치 비교 (새로 상위 10건에 들어온 공고만 추가 라벨)
uv run python scripts/evaluate.py --split tune --run --rule-only --labeling-sheet
uv run python scripts/evaluate.py --split tune --kpi accuracy --rule-only --weights 0.35,0.30,0.20,0.15
# 2. Precision@10이 가장 높은 가중치를 .env의 SCORE_WEIGHTS에 고정
# 3. 평가용: 상위 10건 시트 생성 (RAG 미실행) → 순위를 모르는 상태로 라벨링 → labels.csv 커밋
uv run python scripts/evaluate.py --split test --run --rule-only --labeling-sheet
uv run python scripts/evaluate.py --check-labels --split test
```

`--labeling-sheet`는 업체별 상위 10건을 순위·점수 없이 공고번호 순으로 `data/labels/sheet_{split}.csv`에 씁니다. `--check-labels`는 시트의 모든 조합에 라벨이 있는지, 라벨과 체크리스트 c1-c4가 일치하는지, 라벨 커밋 시각이 RAG 결과 파일보다 앞서는지 확인합니다.

**Phase 4 실행 순서**

```powershell
# 1. 라벨 점검 (평가용 100조합 완비, 체크리스트 일치, RAG 실행 전 커밋)
uv run python scripts/evaluate.py --check-labels --split test
# 2. 평가용 1회 실행 + 1순위 KPI 채점 (RAG 포함)
uv run python scripts/evaluate.py --split test --run --kpi accuracy,eligibility,evidence
# 3. 초안 템플릿 KPI (같은 실행 결과 사용)
uv run python scripts/evaluate.py --split test --kpi template,groundedness
# 4. 규칙 단위 테스트 (자격 필터 KPI의 일부)
uv run pytest tests/test_rules.py
```

`--kpi all`은 위 2·3단계를 한 번에 실행합니다. 리포트에는 조정용 결과도 참고로 남기지만 KPI 판정에는 평가용 결과만 씁니다.

**자동 판정 범위** (3.시나리오수립 KPI 측정 종합표 기준)

| KPI (`--kpi` 값) | 입력 | 스크립트 출력 | 사람이 하는 일 |
|-----|-----|------------|-------------|
| 추천 정확도 (`accuracy`, 1순위) | `outputs/recommendations/`, `data/labels/labels.csv` | **Hit Rate@3** (판정, 목표 80%), **Precision@3** (품질, 목표 0.67), 룰 Precision@3, Precision@10, 오류 유형(하드 필터 / 소프트 점수 / RAG 순위 / 근거 부족)과 어긋난 체크리스트 조건(c1-c4) | 순위를 가린 라벨링 |
| 자격 필터 정확성 (`eligibility`, 1순위) | 위 + `data/labels/filter_sample.csv` | 라벨의 '부적격'을 `ineligible_basis`(hard/doc)로 나눈 건수, hard 기준 부적격 수(목표 0), doc 기준 부적격 중 `qualification_flags` 표시 비율, 샘플 30건 대조 결과 집계 | 샘플 30건 원본 대조 기록 |
| 추천 근거 설명 가능성 (`evidence`, 1순위) | `outputs/recommendations/` (청크 포함), `data/companies/`, 공고 원본 | 근거 출처 확인 비율, 불일치 근거 목록 (`check_evidence_sources`) | 불일치 근거만 검토 |
| 초안 시작 가능 여부 (`template`, 보조) | `outputs/drafts/`, 추출 결과, `data/companies/` | 10건 생성·HTML 파싱 성공 여부, 필수 입력 항목 반영률, 평가항목 추출 성공 공고 수 | 없음 |
| 초안 근거성 (`groundedness`, 보조) | `outputs/drafts/`, `data/companies/`, 청크 | 불일치 항목 목록 (`check_groundedness`) | 불일치 발생 시 원문 확인 |

시간 단축, 담당자 만족도는 사람이 기록·평가하므로 스크립트 대상이 아닙니다.

## 13. 최소 실행 경로 (첫 구현 대상)

'PoC 모듈 구현' Task의 기준 구현 대상은 **SC-001 룰 단독 성공 경로**입니다: **업체 프로필 1개 + 공고 묶음 입력 → 하드 필터 → 소프트 점수 → 상위 10건 출력**. 이 경로가 동작한 뒤에만 RAG(PDF·임베딩·LLM), 그래프·HITL, SC-002 템플릿 순서로 넓힙니다.

### 13.1 고정 경로

| 항목 | 내용 |
|-----|-----|
| 입력 | `data/sample/company_01.json` (업체 1개) + `data/sample/tenders_sample.json` (원본 형식 공고 20건) + `data/sample/region_limits_sample.csv` |
| 공고 구성 | 실제 500건에서 발췌. 통과 13건 + 제외 7건 (H1 PDF 없음 2, H3 업종 불일치 2, H4 중소기업 제한 1, H5 지역 제한 1, H6 예산 범위 밖 1). 업체 01은 중소기업이 아닌 것으로 두어 H4를 검증 |
| 처리 | `load_tenders` → `hard_filter` → `soft_score(k=10)` → `rule_reasons` |
| 추천 근거 | 항목별 점수에서 룰로 만든 근거 문장 + 필드 출처 (RAG 근거는 13.4절 3단계에서 연결) |
| 출력 | 콘솔 JSON + `outputs/recommendations/company_01.json` |
| 필요한 것 | `uv sync`만. `.env`·Azure 키·인터넷·BGE-M3·LangGraph Server·Chroma·React 모두 불필요 |

```
company_01.json ─────┐
tenders_sample 20건 ─┼→ 하드 필터 (H1, H3-H6) ─→ 소프트 점수 (S1-S4) ─→ 상위 10건 + 룰 근거 + 제외 사유 JSON
region_limits ───────┘        └→ 제외 7건 (규칙 ID·필드 값 기록)
```

> **선택 근거 (최소 경로에서 RAG 제외)**: 1순위 KPI 중 자격 필터 정확성과 상위 10건 선별(Precision@10)은 룰만으로 결정됩니다. 룰을 먼저 고정하면 누구나 키·인터넷 없이 같은 결과를 재현할 수 있고, 이후 RAG 결과가 틀렸을 때 원인을 RAG 단계 안에서만 찾으면 됩니다.

### 13.2 실행 명령

```powershell
uv sync                                    # 최초 1회
uv run python scripts/run_demo.py          # 기본 입력: data/sample/
uv run pytest tests/test_min_path.py       # 통과 기준 자동 확인
```

옵션: `--company <업체 JSON 경로>`, `--tenders <공고 원본 경로>`, `--top-k 10`. 예를 들어 `--tenders data/raw/tenders_202605.json --company data/companies/company_01.json`으로 공고 500건에 같은 경로를 적용할 수 있습니다.

## 14. 기술 선택 근거

**선택 기준**은 세 가지입니다: ① 8주(하루 1-2시간) 안에 구현할 수 있는가, ② 로컬에서 바로 검증할 수 있는가, ③ 과정 제공 Azure 자원과 맞는가. **[PoC 임시]** 표시는 PoC 검증 결과에 따라 바뀔 수 있는 선택입니다.

모든 항목을 같은 형식으로 적었습니다: **선택 → 현재 PoC에 맞는 이유(1-2문장) → 검토한 대안과 보류 이유 → 재검토 조건**. '재검토 조건'은 이 결정을 다시 열어볼 신호이며, 발표에서 "왜 이렇게 했고 언제 바꾸는가"를 설명하는 근거로 씁니다. 설계 본문에 `> 선택 근거`를 붙인 항목은 '상세' 열에 위치를 표시했습니다.

### 14.1 설계 결정

| 구분 | 선택 | 현재 PoC에 맞는 이유 | 검토한 대안과 보류 이유 | 재검토 조건 | 상세 |
|------|-----|-----------------|-------------------|----------|-----|
| 추천 구조 | 하드 필터(룰) → 소프트 점수(룰, 상위 10건) → RAG 순위·근거(10건 PDF만) | 자격·업종·예산은 정형 필드라 룰이 정확하고 '부적격 0건'을 보장합니다. 과업·평가 방법은 공고서에만 있어 RAG로 읽되, 10건으로 줄여 비용·시간을 업체당 고정합니다. | 500건 전부 RAG: PDF 다운로드·임베딩·LLM 비용 약 50배 / 룰만: 공고명 이상의 내용을 보지 못함 / 임베딩 유사도 점수: 공고서가 없는 500건 단계에서는 공고명만 비교하게 되어 키워드 겹침과 차이가 작음 | 평가에서 Precision@10이 낮아 상위 10건에 '추천'이 거의 없을 때 (소프트 점수 개선 또는 k 확대) / RAG Precision@3이 룰 Precision@3보다 낮을 때 | 2.4 |
| 제안서 생성 | 고정 템플릿 + 입력값 삽입 (평가항목 추출에만 LLM) | 본문은 같은 입력이면 결과가 같아 테스트가 쉽고, 프로필 값만 넣으므로 '없는 사실 기재 0건'을 구조적으로 지킵니다. 평가항목은 공고서에만 있어 추출하되 원문과 대조합니다. 남는 시간을 메인 기능(SC-001)에 씁니다. | Sub-Agent 4개가 섹션 문장 생성: 환각 검증·품질 평가까지 8주 안에 끝내기 어려움 | SC-001 1순위 KPI를 모두 달성하고 시간이 남을 때 (6.1절 확장 기능) | 2.3, 6.1 |
| Supervisor 라우팅 | 규칙 기반 (State에서 비어 있는 단계로 분기) | PoC 흐름은 '필터·점수 → RAG → 선택 → 추출 → 템플릿' 고정 순서라 규칙으로 충분하고, 잘못된 분기를 바로 추적할 수 있습니다. | LLM 작업 분해: 흐름이 고정된 PoC에서는 이점 없이 비용과 결과 변동만 늘어남 | 검증 Agent(재작성 루프)를 도입해 분기가 동적으로 바뀔 때 | 7 |
| HITL | 공고 선택 1곳만 필수 (`interrupt`) | '최종 의사결정은 담당자'라는 전제(1.1절)를 지키는 최소 지점입니다. | 제안서 확정 HITL ②: 템플릿 결과는 입력이 같으면 항상 같아 확인할 것이 없음 | 제안서에 LLM 문장 생성을 도입할 때 | 2.1 |
| Checkpoint | LangGraph Server 내장 (서버 없이 실행하는 스크립트는 `InMemorySaver`) **[PoC 임시]** | HITL ①의 '중단 → 화면에서 선택 → 같은 지점에서 재개'를 저장소 코드 없이 thread 단위로 제공합니다. PoC 세션은 하루 안에 끝나 장기 보존이 필요 없습니다. | SqliteSaver·Postgres: 재시작 후에도 보존되지만 설정·관리가 추가됨 | `langgraph dev` 재시작 후 대기 중이던 thread를 잃는 문제가 Phase 3 확인에서 실제로 불편할 때 | 2.5 |
| 추천 평가 지표 | Hit Rate@3 (판정, 80%) + Precision@3 (품질, 0.67) + 룰 Precision@3·Precision@10 (비교) | 담당자는 1건만 고르므로(HITL ①) Hit Rate@3이 작업 성공과 대응하고, 나머지 추천을 검토하는 낭비는 Precision@3으로 드러냅니다. 같은 10건에서 룰 순위와 비교해 RAG 효과를 보입니다. | Hit Rate@3 단독: 1건만 맞아도 성공이라 품질 설명이 약함 / nDCG: 순위까지 반영하지만 계산과 발표 설명 부담 | 담당자 인터뷰에서 1위 추천의 중요도가 특히 높다고 확인될 때 (Hit Rate@1 추가) | 12.3, 3번 KPI 1 |
