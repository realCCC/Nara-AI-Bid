# Part 1. 상세 설계

## 1. 전체 구조

```
React ──(LangGraph SDK)──▶ LangGraph Server ──▶ SQLite (작업 이력)
                                │
                           Supervisor (규칙 기반 라우팅)
          ┌──────────────┬──────┴───────┬────────────────────┐
     하드 필터(룰) → 소프트 점수(룰) → RAG 추천 Agent      제안서 템플릿 모듈
       500건            상위 10건       10건 PDF→LLM         + 평가항목 추출
                                          │
                                  [HITL ①] 공고 선택
```

| 구성 요소 | 범위 | 역할 |
|---|---|---|
| 업체 로그인 (간이) | 보조 | 업체 ID·비밀번호를 업체 JSON과 대조 → 프로필 자동 로드 (회원가입·세션 만료 없음) |
| Supervisor | 필수 | State에서 비어 있는 단계로 분기 (LLM 미사용) |
| 하드 필터·소프트 점수 | 필수 | 룰로 500건 → 상위 10건 (LLM 미사용) |
| RAG 추천 Agent | **필수 (메인)** | 10건 PDF → 청크 → 검색 → LLM 순위·근거 |
| 평가항목 추출 | 필수 (축소) | 선택 공고 PDF에서 평가항목·배점 추출 (LLM) |
| 제안서 템플릿 모듈 | 필수 (축소) | 고정 템플릿 + 값 삽입 (LLM 미사용) |
| HITL ① 공고 선택 | 필수 | `interrupt` → React 선택 → 재개 |
| 작업 이력 저장 (SQLite) | 필수 | 추천 결과·선택·초안을 `data/app.db`에 저장, 이전 작업 조회 |
| 검증 Agent, HITL ② | 확장 | 2차 목표 |

**LLM은 두 곳만 사용**: RAG 순위·근거, 평가항목 추출. 나머지는 룰이라 결과가 항상 같습니다.

## 2. 워크플로우

**SC-001 공고 추천**: 업체 로그인 → 업체 ID로 프로필 로드(비밀번호 필드 제거) → 공고 500건 로드(공백 제거, 금액 변환, PII 제거) → 하드 필터(H1, H3-H6) → 소프트 점수 상위 10건 → 10건 PDF 다운로드·청킹·임베딩·검색 → LLM 순위·근거 → 출처 대조 → HITL ① 선택

**SC-002 초안 템플릿**: State 로드 → 평가항목 추출(LLM, Pydantic 검증) → 섹션 4개 + 대응표 템플릿 삽입 → sanitize 후 미리보기 → HTML 다운로드

**소프트 점수** = (S1 업종 세부 × 0.35 + S2 키워드 × 0.30 + S3 예산 규모 × 0.20 + S4 계약방식 × 0.15) × 100. 동점은 공고번호 순. 가중치는 조정용 업체 01-05로만 조정하고 평가 라벨링 전에 고정합니다.

## 3. Agent 프롬프트 원칙

- 입력 데이터(업체 프로필, 공고 필드, 공고서 청크)로만 판단, 없는 정보는 "확인 필요"
- 공고서 근거는 원문 그대로 인용 + 파일·페이지, 필드 근거는 필드명 + 값
- 금지: 낙찰 확률 예측, 최종 입찰 결정, 입력에 없는 인용 생성

**RAG 추천 출력 스키마 (`Recommendation`)**

```json
{
  "rank": 1, "bidNtceNo": "R26BK01501726",
  "reasons": [
    {"text": "과업이 업체 연수 실적과 같은 유형", "source_type": "pdf", "file": "공고문.pdf", "page": 1, "quote": "..."},
    {"text": "세부분류 일치", "source_type": "field", "field": "tender.pubPrcrmntClsfcNo", "value": "86101696"}
  ],
  "qualification_flags": []
}
```

## 4. State

| 필드 | 내용 | 생성 단계 |
|---|---|---|
| `company_profile` | 업체 프로필 | SC-001 1 |
| `tenders_path` | 공고 파일 경로 (500건은 State에 넣지 않음) | SC-001 1 |
| `filter_log` | 공고별 통과·제외 사유 | SC-001 2 |
| `top10` | 상위 10건 + 항목별 점수 | SC-001 3 |
| `rag_chunks` | 공고별 PDF 청크 | SC-001 4 |
| `recommendations` | RAG 순위 + 근거 | SC-001 4 |
| `selected_tender_id` | 선택 공고 | HITL ① |
| `criteria` | 평가항목·배점·과업기간 | SC-002 2 |
| `proposal_html` | 최종 HTML | SC-002 5 |

LangGraph Server의 thread 1개 = 담당자 작업 1건이며, checkpoint로 HITL 대기 지점에서 재개합니다.

## 4-1. 작업 이력 저장 (SQLite)

State(checkpoint)는 그래프 실행용이고, **결과 조회용 데이터는 SQLite에 따로 저장**합니다. Python 표준 `sqlite3`만 사용해 추가 설치가 없고, 파일 하나(`data/app.db`, git 제외)라 서버를 재시작해도 남습니다.

| 테이블 | 주요 컬럼 | 저장 시점 |
|---|---|---|
| `runs` | `thread_id`(PK), `company_id`(로그인 업체 ID), `status`(recommended / selected / done / failed), `created_at`, `updated_at` | 작업 시작 시 생성, 단계마다 갱신 |
| `recommendations` | `thread_id`, `rank`, `bidNtceNo`, `soft_score`, `reasons_json`, `source`(rag / rule) | SC-001 RAG 추천(또는 룰 대체) 직후 |
| `selections` | `thread_id`, `bidNtceNo`, `selected_at` | HITL ① 재개 직후 |
| `proposals` | `thread_id`, `bidNtceNo`, `criteria_json`, `proposal_html`, `created_at` | SC-002 조립 직후 |

- 쓰기는 `save_run` 도구 하나로 모으고 노드 끝에서 호출합니다 (`thread_id` 기준 upsert라 재실행해도 중복 없음).
- 공고 500건·업체 프로필은 **기존 파일 그대로** 쓰고 DB에 넣지 않습니다 (원본은 파일, DB는 결과만).
- React의 '이전 작업' 목록은 로그인한 업체의 `runs`만 최근순으로 읽습니다 (LangGraph Server 커스텀 라우트 `GET /history`, `langgraph.json`의 `http.app`).
- 스키마는 `app/db/schema.sql`, 최초 실행 시 `init_db()`가 테이블이 없으면 생성합니다.

## 6. 에러 처리

| 상황 | 처리 |
|---|---|
| 없는 업체 ID / 비밀번호 불일치 | 로그인 화면에 오류 메시지, 다음 단계 진행 차단 |
| 업체 JSON 스키마 오류 | `validate_data.py`에서 사전 차단, 로그인 시 누락 필드 표시 |
| 하드 필터 통과 10건 미만 / 0건 | 있는 만큼만 진행 / RAG 생략하고 제외 사유 표시 |
| PDF 다운로드·추출 실패 | 해당 공고는 룰 근거만 표시 |
| RAG 출력 검증 실패 | 룰 점수 순위 + 룰 근거로 대체 |
| 근거 출처 불일치 | 해당 근거 숨김, 2개 미만이면 룰 근거 보충 |
| 평가항목 추출 실패 | 기술·가격 평가 비율만 넣고 `[확인 필요]` |
| HITL 대기 중 연결 끊김 | checkpoint에서 재개 |
| SQLite 쓰기 실패 | 로그만 남기고 그래프는 계속 진행 (이력 저장은 부가 기능) |

**프로젝트 위험**: 공고서 PDF에 과업 세부가 없음(437건 중 374건) → '근거 부족'으로 따로 집계 / 필드 의미 오해 → Phase 1에 활용가이드 확인 / 지역 매핑 오류 → 근거 페이지 기록

## 8. LangGraph 골격

```python
class ProposalState(TypedDict):
    company_profile: dict
    top10: list[dict]
    recommendations: list[dict]
    selected_tender_id: str | None
    criteria: dict
    proposal_html: str
    # ... (4장 State 표)

def select_tender(state):          # HITL ①
    tender_id = interrupt({"recommendations": state["recommendations"]})
    return {"selected_tender_id": tender_id}

def route(state) -> str:           # 규칙 기반: 비어 있는 단계로
    if "top10" not in state:              return "filter_and_score"
    if "recommendations" not in state:    return "rag_recommend"
    if not state.get("selected_tender_id"): return "select_tender"
    if "criteria" not in state:           return "extract_criteria"
    if not state.get("proposal_html"):    return "build_proposal_template"
    return END

builder = StateGraph(ProposalState)
builder.add_node("supervisor", lambda s: {})
for name, fn in WORKERS.items():
    builder.add_node(name, fn)
    builder.add_edge(name, "supervisor")   # 작업 후 Supervisor로 복귀
builder.add_edge(START, "supervisor")
builder.add_conditional_edges("supervisor", route, [*WORKERS, END])
graph = builder.compile()                  # 서버가 checkpointer 주입
```

평가 스크립트는 `InMemorySaver`로 compile하고 HITL ①에서 RAG 1순위를 자동 선택합니다.

## 13. 최소 실행 경로 (첫 구현 대상)

**업체 1개 + 샘플 공고 20건 → 하드 필터 → 소프트 점수 → 상위 10건** (LLM·임베딩·서버 없이)

- 입력: `data/sample/` (업체 1개, 실제 공고 20건 = 통과 13 + 제외 7, 지역 매핑 샘플)
- 출력: `outputs/recommendations/company_01.json` (상위 10건 + 룰 근거 + 제외 사유)

**통과 기준** (`tests/test_min_path.py`)
1. 추천 10건, 점수 내림차순
2. 제외 7건이 정확한 규칙 ID로 들어 있음
3. 점수 0-100, 항목별 점수 0-1
4. 모든 근거에 실제 존재하는 필드 출처
5. 두 번 실행해도 결과 동일

**단계별 확장**: ① 룰 추천 → ② 500건 + PDF 청킹 → ③ RAG + 출처 대조 → ④ 그래프 + HITL → ⑤ SC-002 템플릿 → ⑥ React 화면

## 14. 평가

| `--split` | 대상 | 용도 |
|---|---|---|
| `tune` | 업체 01-05 | 가중치·프롬프트 조정 (여러 번 실행 가능) |
| `test` | 업체 41-50 | **최종 KPI 판정** (가중치 고정 → 라벨 커밋 후 1회) |

순서: 조정용으로 가중치 확정 → 평가용 상위 10건 시트 생성(RAG 미실행) → 순위를 가리고 라벨링·커밋 → RAG 포함 1회 실행·채점. 시간 단축과 만족도는 사람이 기록합니다.

## 15. 기술 선택 근거

| 결정 | 선택 | 이유 | 바꿀 시점 |
|---|---|---|---|
| 추천 구조 | 룰 필터 → 룰 점수 → 10건만 RAG | 자격은 룰이 정확하고 부적격 0건 보장, 비용은 업체당 10건으로 고정 | Precision@10이 낮거나 RAG가 룰보다 못할 때 |
| 제안서 | 고정 템플릿 + 값 삽입 | 없는 사실 0건을 구조적으로 보장, 남는 시간을 추천에 투자 | 1순위 KPI 달성 후 |
| Supervisor | 규칙 기반 | 흐름이 고정이라 LLM 분기 이점 없음 | 검증 Agent 도입 시 |
| LLM | Azure OpenAI gpt-4.1 | 과정 제공 자원, 구조화 출력 지원 | 비용·속도 문제 실측 시 |
| 프레임워크 | LangGraph + Server | 분기·HITL·checkpoint·API 내장 | - |
| UI | React + LangGraph SDK | HITL 재개·HTML 미리보기 필요 (Streamlit은 제약) | - |
| 임베딩 / DB | BGE-M3 / Chroma 로컬 | 한국어 지원·무료, 10건 규모에 충분 | 속도 병목 시 Azure Embedding |
| 작업 이력 DB | SQLite | 설치 불필요(표준 라이브러리), 파일 1개, 1인 PoC에 충분 | 다중 사용자·동시 쓰기 필요 시 PostgreSQL |
| PDF 파싱 | PyMuPDF | 한글 추출 품질, 페이지 번호 확보 | 추출 실패율이 높을 때 |
| 패키지 | uv + Python 3.11 | `uv sync` 한 줄로 동일 환경 재현 | - |

**1번 문서 대비 변경**: Claude → Azure gpt-4.1(과정 자원), Streamlit → React(HITL 화면), FastAPI → LangGraph Server(내장 기능), 2단 계층 Supervisor·검증 Agent → 2차 목표(8주 일정)
