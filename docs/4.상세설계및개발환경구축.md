# Part 1. 상세 설계

## 1. Agent 페르소나 및 시스템 프롬프트

### 1.1 Agent 정의

| 항목 | 정의 |
|-----|------|
| Agent 이름 | 나라장터 입찰 어시스턴트 (Proposal Assistant) |
| 주요 역할 | 입찰 담당자를 위한 공고 추천·의사결정 지원 및 제안서 초안 생성 |
| 핵심 목표 | 1) 공고 검토 + 제안서 작성 시간 50% 이상 단축 2) 추천 근거 제시로 객관적 공고 선별 지원 3) 필수 항목 80% 이상 반영한 초안으로 제안서 품질 표준화 4) 기업 프로필에 없는 사실 기재 0건 |
| 기본 전제 | 최종 의사결정(공고 선택, 제안서 확정)은 반드시 담당자가 한다. Agent는 판단에 필요한 정보와 분석 근거만 제공 |
| 톤앤매너 | 전문가형 조력자: 공식적, 근거 기반, 신뢰감 중심. 추천 시 판단 근거를 3-4가지로 명시 |
| 제약사항 | 추측·불확실한 정보 금지, 의사결정 주도 금지, 과장된 표현 금지, 근거 제시 필수 |

### 1.2 System Prompt (공통)

```text
당신은 나라장터 입찰을 지원하는 전문가형 의사결정 조력자입니다.

[역할과 책임]
- 입찰 담당자의 공고 검토, 선별, 제안서 작성을 돕는 조력자 역할
- 업체 역량과 공고 요구사항을 객관적으로 분석하고 연결
- 최종 의사결정은 담당자가 하도록 필요한 정보와 근거만 제공

[의사결정 원칙]
- 항상 입력된 데이터와 객관적 근거로 판단 (추측 금지)
- 점수 제시 시 계산 항목(기술/경험/인력)과 근거를 함께 설명
- 입력 데이터에 없는 정보는 "확인 필요"로 표시
- 수치를 쓸 때는 출처(입력 데이터의 어느 항목인지)를 함께 표시

[답변 구조]
1. 추천 이유 3-4가지 명시 (기술, 실적, 예산, 인력 등)
2. 충족 항목과 부족 항목을 명확히 구분 표시
3. 최종 판단은 담당자가 하도록 안내
4. 제안서 생성 시 평가기준별 대응 전략 포함

[금지사항]
- 실제 낙찰 확률·평가 점수 예측 (정부 입찰 결과는 예측 불가)
- "적합하지 않습니다"처럼 일방적 거절 (대신 부족한 자격 분석 제시)
- 최종 입찰 여부 결정 (담당자만 가능)
- 공고 신뢰성 판단 (담당자 책임)
```

### 1.3 Agent별 역할 프롬프트 요약

공통 System Prompt 위에 Agent별 역할 지시를 추가합니다.

| Agent | 역할 지시 요약 | 출력 형식 |
|-------|-------------|---------|
| Supervisor | 요청을 하위 작업으로 분해하고 Agent 호출 순서·병렬 여부 결정, 결과 취합 | 다음 실행 노드 이름 |
| 공고 분석 Agent | 공고 원문에서 과업내용·필수자격·평가기준·예산·기간 추출 | `TenderInfo` (JSON) |
| 매칭 Agent | 기업 정보와 공고 요구사항 비교, 적합도 점수와 근거 생성 | `MatchResult` (JSON) |
| 제안서 작성 Agent (Sub-Agent ×4) | 회사소개 / 수행방안 / 추진일정 / 조직구성 섹션별 초안 작성 | HTML 조각 (`<section>` 1개) |

**제안서 섹션 ID** (3.시나리오수립 SC-002 기대 출력과 동일)

| 섹션 | section id | 생성 주체 |
|------|-----------|---------|
| 1. 회사소개 | `company` | Sub-Agent 1 |
| 2. 수행방안 (기술방안, 기술 아키텍처) | `approach` | Sub-Agent 2 |
| 3. 추진일정 | `schedule` | Sub-Agent 3 |
| 4. 조직구성 | `organization` | Sub-Agent 4 |
| 5. 평가기준 대응표 | `criteria` | 매칭 Agent |

**HTML 출력 지시 (제안서 작성 Agent 공통)**

```text
- <section id="{섹션ID}"> 하나만 출력하고, 그 밖의 텍스트는 쓰지 않는다.
- 허용 태그: section, h2, h3, p, ul, ol, li, table, thead, tbody, tr, th, td, strong, em, br
- script, style, iframe, img, a, on* 속성, 인라인 style 속성은 쓰지 않는다.
- 입력 데이터에 없는 수치는 쓰지 않고 "확인 필요"로 표시한다.
```

## 2. Agent 아키텍처 및 오케스트레이션

### 2.1 전체 구조 (Supervisor 패턴)

```
    React 화면  ──(LangGraph SDK: 실행 · 스트리밍 · 재개)──▶  LangGraph Server
                                                                 │
                                                          ┌──────┴───────┐
                                                          │  Supervisor  │
                                                          └──────┬───────┘
                                       ┌─────────────────────────┼──────────────────┐
                                       ▼                         ▼                  ▼
                                ┌─────────────┐           ┌─────────────┐   ┌──────────────────┐
                                │ 공고 분석   │           │  매칭       │   │ 제안서 작성       │
                                │ Agent       │           │  Agent      │   │ Agent (HTML)      │
                                └─────────────┘           └─────────────┘   │ ├ Sub1 회사소개   │
                                                                            │ ├ Sub2 수행방안   │
                                                                            │ ├ Sub3 추진일정   │
                                                                            │ └ Sub4 조직구성   │
                                                                            └──────────────────┘
                                                 [HITL ①] 공고 선택     [HITL ②] 제안서 확정
```

| 구성 요소 | PoC 범위 | 비고 |
|---------|---------|------|
| Supervisor | **필수** | LangGraph 조건 분기로 흐름 제어 |
| 공고 분석 Agent | **필수** | SC-001, SC-002 공통 사용 |
| 매칭 Agent | **필수** | SC-001 추천, SC-002 평가기준 대응표 생성 |
| 제안서 작성 Agent (Sub-Agent 4개 병렬) | **필수** | SC-002, HTML 출력 |
| Human-in-the-loop 승인 2곳 | **필수** | `interrupt` → React에서 응답 → `Command(resume=...)`로 재개 |
| 검증 Agent (자기 검증·재작성 루프) | **확장 (2차 목표)** | 2.문제정의및서비스계획 기능 4. 재작성 최대 2회 상한 (근거: 2.문제정의및서비스계획 보조 지표) |

### 2.2 공고 추천 워크플로우 (SC-001)

| 단계 | 담당 | 처리 내용 |
|------|-----|---------|
| 1. 입력 | 담당자 + System | React에서 기업 프로필 JSON 업로드, 스키마 검증 |
| 2. 공고 분석 | 공고 분석 Agent | 공고 30건 병렬 파싱 → 과업내용·필수자격·평가기준 구조화 |
| 3. 필터링 | 매칭 Agent (규칙) | 필수 자격 미충족 공고 제외, 기업 선호 조건(예산 범위·지역) 밖 공고 제외 |
| 4. 적합도 계산 | 매칭 Agent | 하이브리드 점수 계산 (2.4절) → 상위 5건 **[초기 설정값]** + 추천 근거 3-4가지 |
| 5. **[HITL ①] 공고 선택** | 담당자 | React 화면에서 상위 5건 검토 후 1건 선택 → 승인 |
| 6. 저장 및 전환 | System | 선택 결과를 같은 thread의 State에 저장, SC-002로 진행 |

선호 조건 필터는 2.문제정의및서비스계획 적합성 기준의 '선호 조건 불일치'(적격-비추천 라벨)에 대응하므로 PoC 필수로 둡니다. 규칙 비교만 하므로 구현 부담이 작습니다.

### 2.3 제안서 생성 워크플로우 (SC-002)

| 단계 | 담당 | 처리 내용 |
|------|-----|---------|
| 1. 입력 | System | 선택 공고 + 기업 프로필 State에서 자동 로드 |
| 2. 섹션별 초안 생성 | 제안서 작성 Agent (Sub-Agent 4개 병렬) | 회사소개 / 수행방안 / 추진일정 / 조직구성 HTML 생성 → 구조 검증 → Supervisor가 취합 |
| 3. 평가기준 대응표 | 매칭 Agent | 공고 평가기준 ↔ 초안 내용 매핑, 항목별 강점·보완점 HTML 표 |
| 4. **[HITL ②] 검토 및 확정** | 담당자 | React 화면에서 sanitize된 초안 확인, 섹션 수정·재생성 후 "제안서 완성" 승인 |
| 5. 최종 저장 | System | 섹션 + 대응표를 단일 HTML 문서로 조립, 다운로드 제공, checkpoint로 버전 기록 |

### 2.4 적합도 점수 계산 방식 (하이브리드)

2.문제정의및서비스계획 '적합 공고 정의'의 세 단계를 그대로 처리 순서로 사용합니다: **입찰 자격(Eligibility)** 은 규칙 필터, **기업 적합도(Suitability)** 는 아래 점수, **추천 순위(Ranking)** 는 점수 내림차순 상위 5건. 적합도 점수는 3.시나리오수립에서 정의한 가중치(기술 40% + 경험 40% + 인력 20%)를 유지하되, 항목 특성에 따라 계산 방식을 나눕니다.

| 항목 | 가중치 | 계산 방식 | 근거 |
|------|------|---------|------|
| 기술 적합도 | 40% | BGE-M3 임베딩 코사인 유사도 (기업 보유 기술 ↔ 공고 요구 기술) | 표현이 달라도 의미가 같은 기술 매칭 (예: "벡터 검색" ↔ "벡터DB") |
| 경험 적합도 | 40% | BGE-M3 임베딩 코사인 유사도 (기업 과거 실적 ↔ 공고 과업내용) | 유사 프로젝트 경험을 의미 단위로 비교 |
| 인력 적합도 | 20% | 규칙 기반: 요구 인원 대비 보유 인원 충족 비율 | 숫자 비교라 규칙이 더 정확 |
| 필수 자격 | 필터 | 규칙 기반: 하나라도 미충족 시 추천 제외 (부족 항목은 별도 표시) | 자격 미달 공고는 점수와 무관하게 제외 |

**최종 점수** = (기술 × 0.4 + 경험 × 0.4 + 인력 × 0.2) × 100 → 0-100점  
가중치는 **[초기 설정값]**이며, Phase 4 정답셋 결과로 조정합니다.

### 2.5 상태(State) 관리

LangGraph의 공유 State 하나로 SC-001과 SC-002를 연결합니다. LangGraph Server의 **thread** 1개가 담당자 작업 세션 1개에 대응합니다.

| State 필드 | 내용 | 생성 시점 | 사용처 |
|-----------|------|---------|------|
| `company_profile` | 기업 프로필 (파싱 완료) | SC-001 1단계 | 전 단계 |
| `tenders` | 구조화된 공고 목록 | SC-001 2단계 | 매칭, 제안서 작성 |
| `recommendations` | 상위 5건 + 점수 + 근거 | SC-001 4단계 | HITL ① |
| `selected_tender_id` | 담당자가 선택한 공고 ID | HITL ① | SC-002 전체 |
| `draft_sections` | 섹션별 HTML 4개 (`{section_id: html}`) | SC-002 2단계 | 취합, HITL ② |
| `criteria_table` | 평가기준 대응표 (HTML 표) | SC-002 3단계 | HITL ② |
| `proposal_html` | 최종 조립된 HTML 문서 | SC-002 5단계 | 다운로드 |
| `approval_status` | 승인 대기 / 승인 완료 | HITL ①, ② | 흐름 재개 판단 |

**Checkpoint**: LangGraph Server가 thread별 checkpoint를 자동 저장하므로, 담당자가 화면을 닫았다가 돌아와도 HITL 대기 지점부터 이어서 실행합니다. 그래프 코드에서 checkpointer를 따로 지정하지 않습니다.

## 3. 도구 및 함수 명세 (Capability)

### 3.6 시나리오 → 모듈/컴포넌트 매핑

3.시나리오수립의 '상세 흐름 테이블' 단계 번호를 그대로 사용해 구현 모듈에 대응시킨 표입니다.

**SC-001: 공고 추천**

| 시나리오 단계 | 모듈명 | 담당 컴포넌트 | 입력 | 출력 |
|-------------|-------|-----------|-----|-----|
| 1 | 파일 수신 & 검증 | FileUploadModule (React 업로드 + 서버 검증) | JSON 파일 | 파싱된 기업정보 객체 |
| 2 | 공고 분석 | TenderAnalysisAgent (공고 분석 Agent) | 공고 30건 | 공고별 `TenderInfo` |
| 3 | 자격·선호 조건 필터 | FilterModule | 기업정보 + `TenderInfo` | 필터 통과 공고 목록, 제외 사유 |
| 3 | 적합도 계산 | EmbeddingModule + SimilarityModule (매칭 Agent) | 기업정보 + 필터 통과 공고 | 적합도 점수, 추천 근거 |
| 4-5 | 결과 표시·선택 (HITL ①) | RecommendationList (React) | 상위 5건 | 선택된 공고 ID |
| 6 | SC-002 전환 | LangGraph State (같은 thread) | 선택 결과 | SC-002 입력 |

```
FileUploadModule → TenderAnalysisAgent → FilterModule → EmbeddingModule + SimilarityModule → RecommendationList
```

**SC-002: 제안서 초안 생성**

| 시나리오 단계 | 모듈명 | 담당 컴포넌트 | 입력 | 출력 |
|-------------|-------|-----------|-----|-----|
| 1 | 입력 로드 | LangGraph State (SC-001 결과 재사용) | 선택 공고 ID | 공고 `TenderInfo` + 기업정보 |
| 2 | 섹션별 생성 | SectionGeneratorAgent (Sub-Agent 4개 병렬) | 공고 + 기업정보 | 섹션별 HTML 4개 |
| 3 | 평가기준 대응표 | CriteriaTableModule (매칭 Agent) | 평가기준 + 섹션 HTML | 대응표 HTML |
| 4-5 | 미리보기·편집 (HITL ②) | ProposalViewer / SectionEditor (React) | HTML (sanitize 후) | 수정된 섹션 HTML |
| 6 | 최종 조립 | ProposalAssemblyModule | 섹션 4개 + 대응표 | 최종 HTML 문서 |
| 7 | 파일 내보내기 | ExportModule | 최종 HTML | `.html` 파일 (향후 PDF/Word) |

```
State 로드 → SectionGeneratorAgent (병렬 4개) → CriteriaTableModule → ProposalViewer / SectionEditor → ProposalAssemblyModule → ExportModule
```

**모듈별 구현 순서** (6장 로드맵, 13장 최소 실행 경로와 동일)

| 모듈 | Phase | 우선순위 | 의존성 |
|------|-------|---------|--------|
| FileUploadModule | 1 | 필수 | 없음 |
| TenderAnalysisAgent | 1 (최소 버전), 2 (고도화) | 필수 | 없음 |
| EmbeddingModule | 1 | 필수 | FileUploadModule |
| SimilarityModule | 1 | 필수 | EmbeddingModule, TenderAnalysisAgent |
| FilterModule | 2 | 필수 | TenderAnalysisAgent |
| SectionGeneratorAgent | 2 | 필수 | TenderAnalysisAgent |
| CriteriaTableModule | 2 | 필수 | SectionGeneratorAgent |
| ProposalAssemblyModule | 2 | 필수 | SectionGeneratorAgent, CriteriaTableModule |
| RecommendationList (React) | 3 | 필수 | SimilarityModule |
| ProposalViewer / SectionEditor (React) | 3 | 필수 | ProposalAssemblyModule |
| ExportModule (HTML) | 3 | 필수 | ProposalAssemblyModule |
| ExportModule (PDF/Word) | 이후 | 확장 | ExportModule (HTML) |

## 4. 지식 베이스 및 메모리 전략

### 4.1 RAG (검색 증강 생성) 전략

RAG는 목표 자체가 아니라 Agent가 호출하는 도구 중 하나로 구성합니다 (1.역량및기술스택확인 하네스 원칙).

| 항목 | 결정 |
|------|------|
| 데이터 소스 | IT 용역 공고 30건 (조달청 API 수집 + 수동 보완), 가상 기업 프로필 10개사 |
| 청킹 방식 | 공고: 섹션별 (공고명 / 과업내용 / 필수자격 / 평가기준), 기업: 영역별 (회사정보 / 기술 / 실적 / 인력) |
| 임베딩 모델 | BGE-M3 (오픈소스, 한국어 지원) |
| Vector DB | Chroma (로컬 실행) |
| 활용처 | 매칭 Agent의 기술·경험 유사도 계산, 제안서 작성 시 유사 실적 검색 |

### 4.2 대화 메모리

| 항목 | 결정 |
|------|------|
| 메모리 유형 | LangGraph State + Server 내장 checkpoint (대화 이력이 아닌 작업 상태 중심) |
| 세션 단위 | LangGraph Server thread 1개 = 담당자 작업 1건 (SC-001 → SC-002) |
| 세션 시작 | 기업 프로필 로드 (기본 컨텍스트) |
| SC-001 | 추천 결과, 선택 공고 저장 |
| SC-002 | 섹션별 HTML 초안, 담당자 수정 버전 기록 |
| 세션 종료 | 최종 HTML 제안서와 선택 이력만 보존, 나머지 중간 상태 삭제 |
| 개인정보 | 발주처 담당자 연락처 등 PII는 저장하지 않거나 마스킹 (2.문제정의및서비스계획 제약사항) |

| 섹션 생성 일부 실패 | 성공한 섹션만 저장, 실패 섹션만 재생성 | 위와 동일 |

| 서버 연결 끊김 (HITL 대기 중) | thread checkpoint에서 재개 | "이전 작업을 이어서 진행합니다" |

## 7. LangGraph 구조 예시

상세 설계 단계의 출발점이 되는 그래프 골격입니다. (의사코드 수준, 모델명은 설정값으로 분리)

```python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt


class ProposalState(TypedDict):
    company_profile: dict
    tenders: list[dict]
    recommendations: list[dict]
    selected_tender_id: str | None
    draft_sections: dict[str, str]   # {section_id: "<section>...</section>"}
    criteria_table: str              # "<table>...</table>"
    proposal_html: str
    approval_status: str


def analyze_tenders(state: ProposalState) -> dict:
    # 공고 분석 Agent: 공고 원문 → TenderInfo 구조화
    ...

def match_tenders(state: ProposalState) -> dict:
    # 매칭 Agent: 필터링 → 하이브리드 점수 → 상위 5건 + 근거
    ...

def select_tender(state: ProposalState) -> dict:
    # HITL ①: React에서 공고 1건 선택할 때까지 대기
    tender_id = interrupt({"recommendations": state["recommendations"]})
    return {"selected_tender_id": tender_id}

def generate_sections(state: ProposalState) -> dict:
    # 제안서 작성 Agent: Sub-Agent 4개 병렬 실행 → 섹션별 HTML 검증 후 취합
    ...

def build_criteria_table(state: ProposalState) -> dict:
    # 매칭 Agent: 평가기준 대응표(HTML 표) 생성
    ...

def review_proposal(state: ProposalState) -> dict:
    # HITL ②: React에서 검토·수정 후 확정할 때까지 대기
    edited = interrupt({"draft": state["draft_sections"], "table": state["criteria_table"]})
    return {"draft_sections": edited, "approval_status": "approved"}

def assemble_proposal(state: ProposalState) -> dict:
    # 섹션 4개 + 대응표 → 단일 HTML 문서
    ...


def supervisor(state: ProposalState) -> dict:
    # Supervisor: 작업 노드 결과를 받아 다음 작업을 결정 (실제 분기는 route에서 수행)
    return {}

def route(state: ProposalState) -> str:
    # PoC 1차: State에 비어 있는 단계를 찾아 다음 노드로 보내는 규칙 기반 라우팅
    if not state.get("tenders"):
        return "analyze_tenders"
    if not state.get("recommendations"):
        return "match_tenders"
    if not state.get("selected_tender_id"):
        return "select_tender"
    if not state.get("draft_sections"):
        return "generate_sections"
    if not state.get("criteria_table"):
        return "build_criteria_table"
    if state.get("approval_status") != "approved":
        return "review_proposal"
    if not state.get("proposal_html"):
        return "assemble_proposal"
    return END


WORKERS = {
    "analyze_tenders": analyze_tenders,
    "match_tenders": match_tenders,
    "select_tender": select_tender,
    "generate_sections": generate_sections,
    "build_criteria_table": build_criteria_table,
    "review_proposal": review_proposal,
    "assemble_proposal": assemble_proposal,
}

builder = StateGraph(ProposalState)
builder.add_node("supervisor", supervisor)
for name, fn in WORKERS.items():
    builder.add_node(name, fn)
    builder.add_edge(name, "supervisor")   # 작업이 끝나면 Supervisor로 복귀

builder.add_edge(START, "supervisor")
builder.add_conditional_edges("supervisor", route, [*WORKERS, END])

# LangGraph Server가 checkpointer를 주입하므로 compile 시 지정하지 않음
graph = builder.compile()
```

서버 진입점 설정(`langgraph.json`)과 코드 위치는 10.3절에 있습니다.

**React 측 호출 흐름 (개념)**

| 동작 | SDK 호출 |
|------|---------|
| 작업 시작 | thread 생성 → `proposal` 그래프 실행 (진행 상태 스트리밍) |
| HITL ① 공고 선택 | interrupt 데이터(추천 5건) 표시 → 선택한 `tender_id`로 재개 |
| HITL ② 제안서 확정 | interrupt 데이터(섹션 HTML) sanitize 후 표시 → 수정본으로 재개 |
| 다운로드 | State의 `proposal_html`을 `.html` 파일로 저장 |

**설계 포인트**
- Supervisor는 모든 작업 노드의 결과를 받아 다음 노드를 정하는 허브 역할. PoC 1차는 규칙 기반 라우팅으로 흐름을 고정하고, LLM 기반 작업 분해는 검증 Agent와 함께 2차 목표에서 적용
- `interrupt`로 HITL ①, ②에서 실행을 멈추고, LangGraph Server의 thread checkpoint가 State를 보존해 React에서 재개 요청 시 같은 지점부터 이어서 실행
- `generate_sections` 내부는 Sub-Agent 4개를 병렬 실행 (상세 설계 단계에서 서브그래프 또는 `Send` API로 구체화)
- 검증 Agent(2차 목표)는 `route`에 `generate_sections` 다음 분기로 추가 예정

## 11. Azure OpenAI 설정

### 11.1 설정 고정표

생성은 Azure OpenAI, 임베딩은 로컬 BGE-M3로 나눕니다. 임베딩을 오픈소스로 두는 이유는 2.문제정의및서비스계획 제약사항(외부 의존성 최소화)이며, 필요하면 환경변수만 바꿔 Azure Embedding으로 전환합니다.

| 사용 목적 | 사용 리소스 / 배포명 | 환경변수 | 참조 모듈 |
|---------|-----------------|--------|---------|
| Generation | 과정 제공 Azure OpenAI 리소스 / 배포명 **`gpt-4.1`** (과정 안내 배포명으로 확정) | `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_API_KEY`, `OPENAI_API_VERSION`, `AZURE_OPENAI_CHAT_DEPLOYMENT` | `app/config.py`의 `get_chat_model()` → `app/agents/*`, `scripts/check_env.py` |
| Embedding (PoC) | 로컬 BGE-M3 `BAAI/bge-m3` (Azure 리소스 사용 안 함) | `EMBEDDING_PROVIDER=local`, `EMBEDDING_MODEL` | `app/config.py`의 `get_embeddings()` → `app/tools/embedding.py`, `scripts/ingest.py` |
| Embedding (대체안) | 같은 Azure 리소스 / `text-embedding-3-small` 배포 | `EMBEDDING_PROVIDER=azure`, `AZURE_OPENAI_EMBEDDING_DEPLOYMENT` | 위와 동일 (코드 변경 없음) |
| Vector DB | 로컬 Chroma | `CHROMA_DIR` | `app/tools/embedding.py`, `scripts/ingest.py` |

코드에는 모델명을 쓰지 않고 `app/config.py`만 환경변수를 읽습니다. 나머지 모듈은 `get_chat_model()`, `get_embeddings()`를 호출하므로 배포명이 바뀌어도 `.env`만 수정하면 됩니다. `langchain-openai`의 `AzureChatOpenAI`는 `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_API_KEY`, `OPENAI_API_VERSION`을 환경변수에서 바로 읽습니다.

### 11.2 Agent별 모델 매핑 ([초기 설정값])

PoC에서는 생성 배포 1개(`gpt-4.1`)를 모든 Agent가 공유하고, Agent별로 temperature와 출력 형식만 다르게 둡니다. 배포가 하나면 할당량과 설정 관리가 단순하고, 비용이나 속도 문제가 실측으로 확인된 Agent만 별도 배포로 분리합니다.

| Agent / 처리 | 모델 | temperature | 출력 형식 | 분리 검토 조건 |
|------------|-----|-------------|---------|-------------|
| Supervisor | 사용 안 함 (규칙 기반 라우팅, 7장) | - | - | - |
| 공고 분석 Agent | gpt-4.1 | 0 | 구조화 출력 JSON (`TenderInfo`) | 30건 반복 호출 비용이 크면 `gpt-4.1-mini`로 분리 |
| 매칭 Agent: 자격 판정·적합도 점수 | 사용 안 함 (규칙 + BGE-M3 유사도, 2.4절) | - | JSON | - |
| 매칭 Agent: 추천 근거·평가기준 대응표 | gpt-4.1 | 0 | JSON / HTML `<table>` | - |
| 제안서 작성 Sub-Agent 4개 | gpt-4.1 | 0.3 | HTML `<section>` | 병렬 호출로 할당량(TPM)이 부족할 때 |
| `check_env.py` 연결 확인 | gpt-4.1 | 0 | 텍스트 | - |
| 임베딩 (유사도·Chroma 적재·실적 검색) | BGE-M3 (로컬) | - | 벡터 | 처리 속도가 부족하면 Azure Embedding으로 전환 |

### 11.4 비밀값 관리

- `.env`는 `.gitignore`에 넣어 커밋하지 않고, 변수 이름만 적은 `.env.example`을 커밋합니다.
- LangGraph Server는 `langgraph.json`의 `"env": ".env"`로 실행 시 자동으로 읽고, `scripts/`는 `python-dotenv`로 읽습니다.
- React 쪽에는 Azure 키를 두지 않습니다. `VITE_`로 시작하는 값은 브라우저에 노출되므로 서버 주소만 넣고, 모든 LLM 호출은 LangGraph Server에서 수행합니다.

### 12.3 평가 스크립트 실행

평가는 두 단계로 나눕니다. ① `--run`으로 평가용 결과를 만들고 ② `--kpi`로 그 결과를 정답 데이터와 대조합니다. `--run` 없이 실행하면 `outputs/`에 이미 있는 결과만 채점하므로, LLM을 다시 호출하지 않고 채점 로직만 반복 확인할 수 있습니다.

| 단계 | 명령 | 입력 | 출력 |
|------|-----|-----|-----|
| ① 결과 생성 | `uv run python scripts/evaluate.py --run` | `data/companies/*.json`, `data/tenders/*.json` | `outputs/recommendations/{company_id}.json` (기업별 상위 5건), `outputs/drafts/{tender_id}_{company_id}.html` (공고별 추천 1순위 기업 초안 30건) |
| ② 채점 | `uv run python scripts/evaluate.py --kpi accuracy,coverage,groundedness,html` | ①의 결과 + 아래 표의 정답 데이터 | 콘솔 요약 + `outputs/eval/report_YYYYMMDD.json` |

`--run`은 그래프를 서버 없이 직접 실행하며, HITL ①은 1순위 공고를 자동 선택하고 HITL ②는 수정 없이 자동 확정합니다(사람 개입 없는 초안 품질을 측정하기 위함). `--company company_01`처럼 기업을 지정하면 1개사만 평가합니다.

**자동 판정 범위** (3.시나리오수립 KPI 측정 종합표 기준)

| KPI (`--kpi` 값) | 입력 | 스크립트 출력 | 사람이 하는 일 |
|-----|-----|------------|-------------|
| 추천 정확도 (`accuracy`) | `outputs/recommendations/`, `data/labels/labels.csv` | 기업별 상위 3건과 정답 라벨 대조, 정확도, 오류 유형(자격 필터 / 적합도 점수) | 정답 라벨 사전 작성 |
| 자격 판정 정확도 (`accuracy`에 포함, 보조) | 위와 동일 | 규칙 기반 판정과 '부적격' 라벨 일치율 | 없음 |
| 초안 커버율 (`coverage`) | `outputs/drafts/`, `data/labels/coverage_checklist.csv` | 초안별 필수 항목 포함 비율, 30건 평균 | 체크리스트 사전 작성 |
| 초안 근거성 (`groundedness`) | `outputs/drafts/`, `data/companies/` | 불일치 항목 목록 (`check_groundedness`) | 불일치 항목의 허위/표현 차이 최종 판정 |
| HTML 유효성 (`html`) | `outputs/drafts/` | 섹션 4개 + 대응표 파싱 성공 여부 | 없음 |

시간 단축, 담당자 만족도, 재사용성은 사람이 기록·평가하므로 스크립트 대상이 아닙니다.

## 13. 최소 실행 경로 (첫 구현 대상)

'PoC 모듈 구현' Task의 첫 구현 단위는 **기업 프로필 1개 입력 → 공고 1건 분석 → 추천 점수 반환**으로 고정합니다.

입력은 `data/sample/`의 기업 1개사(`company_01.json`)와 공고 1건(`tender_001.json`)입니다. `run_demo.py`는 기업 프로필을 스키마로 검증한 뒤, 공고 원문을 공고 분석 Agent에 넘겨 gpt-4.1을 **1회** 호출해 `TenderInfo`로 구조화합니다. 이어서 자격 판정(`match_qualifications`)은 규칙으로, 적합도 점수(`calculate_match_score`)는 규칙과 BGE-M3 유사도로 계산해 점수·항목별 점수·근거를 JSON으로 출력합니다. 서버, 화면, Chroma 없이 노드 함수를 직접 호출하므로, 이 경로가 동작하면 LLM 연결·스키마·점수 로직이 모두 검증된 것입니다. 이 흐름이 동작한 뒤에만 다음 단계로 범위를 넓힙니다.

```
data/sample/company_01.json ─┐
                              ├→ analyze_tenders (공고 분석, LLM 1회) → match_qualifications (자격 판정, 규칙)
data/sample/tender_001.json ──┘                                      → calculate_match_score (적합도, 규칙 + BGE-M3)
                                                                      → 점수 + 항목별 점수 + 근거 JSON 출력
```

**데모 명령** (인자를 생략하면 위 샘플 1쌍이 기본값)

```powershell
uv run python scripts/run_demo.py --company data/sample/company_01.json --tender data/sample/tender_001.json
```

**기대 출력 (형식 예시, 값은 가상 데이터)**

```json
{
  "tender_id": "2026-00015",
  "eligible": true,
  "missing_qualifications": [],
  "score": 94,
  "breakdown": {"tech": 0.97, "experience": 0.95, "staff": 0.85},
  "reasons": ["RAG, LLM, 벡터DB 요구 기술 3/3 보유", "유사 실적: 금융 챗봇(2024)", "AI개발자 3명 보유"]
}
```

**단계별 확장**

| 단계 | 범위 | 입력 → 출력 | 완료 기준 | 확인 방법 |
|------|-----|-----------|---------|---------|
| 0 | 환경 확인 | - | 12.1절 1-5단계 통과 | `check_env.py`, `ingest.py --sample` |
| 1 | 공고 1건 분석 | 공고 JSON 1건 → `TenderInfo` | Pydantic 검증 통과 | `run_demo.py` |
| 2 | **기업 1개 × 공고 1건 점수 (고정 경로)** | 기업 1개 + `TenderInfo` → 점수 + 근거 | 위 기대 출력 형식으로 출력 | `run_demo.py` |
| 3 | 기업 1개 × 공고 30건 추천 | 기업 1개 + 공고 30건 → 상위 5건 | `recommendations` State에 저장 | LangGraph Studio |
| 4 | HITL ① 연결 | 상위 5건 → 1건 선택 후 재개 | `selected_tender_id` 저장 | LangGraph Studio |
| 5 | 이후 확장 | 섹션 1개 생성 → 4개 병렬 → 대응표 → HITL ② | Phase 2 범위 | LangGraph Studio, React |

## 14. 기술 선택 근거

선택 기준은 세 가지입니다: 8주(하루 1-2시간) 안에 구현 가능한가, 로컬에서 바로 검증할 수 있는가, 과정 제공 Azure 자원과 맞는가. **[PoC 임시]** 표시는 PoC 검증 결과에 따라 바뀔 수 있는 선택입니다.

| 구분 | 선택 | 지금 PoC에 맞는 이유 | 대체안과 보류 이유 |
|------|-----|-----------------|---------------|
| 생성 LLM | Azure OpenAI gpt-4.1 **[PoC 임시: 배포명]** | 과정 제공이라 비용·계정 부담이 없고, 구조화 출력(JSON)을 지원 | 다른 LLM API: 별도 계정·비용 필요 |
| Agent Framework | LangGraph (+ LangChain) | Supervisor·병렬 실행·interrupt 기반 HITL이 내장, 1번 문서 학습 목표와 일치 | LangChain 단일 체인: 분기·HITL 재개를 직접 구현해야 함 |
| 백엔드 서버 | LangGraph Server (`langgraph dev`) | 그래프를 API로 바로 노출, thread·checkpoint·스트리밍 내장으로 서버 코드가 필요 없음 | FastAPI: 세션·스트리밍·재개를 직접 구현해야 해 8주 일정에 부담 |
| 프론트엔드 | React (Vite) + LangGraph JS SDK | HITL 2곳과 HTML 미리보기·섹션 편집 화면이 필요 (2번 문서 UI 결정) | Streamlit: 빠르지만 HITL 재개·HTML 편집 화면 구성에 제약 |
| 패키지 관리 | uv | Python 버전·가상환경·lock 파일을 한 도구로 관리해 재현성이 높음 | pip + requirements: Python 버전·lock 별도 관리 / poetry: 설치·속도 부담 |
| 임베딩 | BGE-M3 로컬 **[PoC 임시]** | 한국어 지원, 무료, 오프라인 검증 가능, 2번 문서 제약(오픈소스) 충족 | Azure Embedding: 다운로드 없고 빠르지만 호출 비용·외부 의존. 환경변수로 전환 가능 (11.1절) |
| Vector DB | Chroma 로컬 **[PoC 임시]** | 패키지 설치만으로 로컬 파일 저장, 공고 30건 규모에 충분 | FAISS: 메타데이터 필터를 직접 구현 / Azure AI Search: 리소스 생성·비용 발생 |
| Checkpoint | LangGraph Server 내장 **[PoC 임시]** | 설정 없이 HITL 재개 지원 | SqliteSaver: 장기 보존은 되지만 설정 추가. dev 모드 재시작 시 보존 여부는 Phase 3에 확인 |
| HTML 보안 | DOMPurify + 서버 허용 태그 검증 | LLM 생성 HTML의 XSS를 이중으로 방어 | Markdown 출력 후 변환: 안전하지만 표·섹션 구조 제어가 약함 |
| 출력 검증 | Pydantic (JSON) + 태그 화이트리스트 (HTML) | 실패 감지가 명확해 재시도 조건을 정하기 쉬움 | 자유 텍스트 파싱: 실패 감지가 어려움 |
| Prompt | Chain-of-Thought + Few-Shot | 추천 근거를 단계별로 설명하고 HTML 형식이 안정됨 | Zero-Shot: 토큰은 적지만 출력 형식이 흔들림 |
| 실행 방식 | 로컬 우선 → Docker (Phase 3) | 초기 세팅이 단순하고 반복이 빠름 | 처음부터 Docker: 환경은 같지만 초기 부담이 큼 |
| Monitoring | Python logging **[PoC 임시]** | 추가 비용 없이 단계별 실행·토큰 사용량 기록 | LangSmith/Langfuse: 트레이스 시각화, 필요 시 `LANGSMITH_API_KEY`만 추가 |

**1.역량및기술스택확인 대비 변경 사항**

1번 문서의 선호 스택과 학습 목표는 유지하되, 2번 문서의 서비스 결정과 과정 제공 자원에 맞춰 아래 항목을 바꿨습니다.

| 항목 | 1번 문서 | 현재 설계 | 변경 이유 |
|------|--------|---------|---------|
| 생성 LLM | Claude | Azure OpenAI gpt-4.1 (배포 이름은 환경변수) | 과정에서 제공하는 자원으로 비용·계정 부담 없음, 코드에 모델명을 고정하지 않아 교체 가능 |
| UI | Streamlit | React (Vite) + LangGraph SDK | HITL 2곳(공고 선택, 제안서 확정)과 HTML 미리보기·섹션 편집 화면이 필요 (2번 문서 UI 결정) |
| API 서버 | FastAPI (확장) | LangGraph Server | thread·checkpoint·스트리밍이 내장되어 별도 API 서버 코드가 필요 없음 |
| Agent 계층 | 하위 Supervisor를 둔 2단 계층 | 1단 Supervisor + 제안서 작성 Agent 내부 Sub-Agent 4개 | 8주 일정에서 먼저 동작하는 흐름을 확보, 2단 계층은 검증 Agent와 함께 2차 목표 |
| 검증 Agent | 완료 기준에 포함 | 2차 목표 | 2번 문서에서 기능 4(자동 검증 루프)를 2차 목표로 결정 |
