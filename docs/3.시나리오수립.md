핵심 사용자 시나리오 및 워크플로우

중소기업(IT·교육·연구조사 등 용역 업종)의 입찰·영업 담당자는 매일 올라오는 공고를 검토해 응찰할 공고를 고르고, 고른 공고마다 제안서 초안을 처음부터 작성합니다. 이 문서는 이 반복 업무를 AI Agent가 돕는 2가지 핵심 시나리오(SC-001 공고 추천, SC-002 제안서 초안 템플릿 생성)의 사용자 여정과 KPI를 정의합니다. **메인 시나리오는 SC-001**이며, SC-002는 담당자가 이어서 작성할 초안 템플릿까지만 생성합니다 (2.문제정의및서비스계획 범위 결정). 모듈 구조·개발 환경 등 설계 세부는 4.상세설계및개발환경구축에서 다룹니다.

## 사용자 페르소나: Mid-Tech 담당자

### 대상 사용자
대상 사용자는 공공 용역 입찰에 참여하는 중소기업의 입찰·영업 담당자입니다. 기술 비전공자이지만 기본적인 데이터는 이해하는 Mid-Tech 수준으로, 엑셀·JSON 파일을 다룰 수 있고 웹 화면의 기본 필터와 옵션을 이해합니다.

### 사용자의 Pain Point
1. **공고 탐색 시간**: 매일 올라오는 많은 공고 중 적합한 공고를 찾는 데 오랜 시간을 씁니다.
2. **반복 업무**: 공고 분석과 제안서 초안 작성을 공고마다 처음부터 반복합니다.
3. **품질 편차**: 담당자 경험에 따라 공고 선별과 제안서 품질의 편차가 큽니다.

## 시나리오 1: 공고 검토 및 선택 프로세스

### ID
SC-001

### 시나리오명
"아침에 적합 공고 찾아 최종 선택하기"

### 상황
입찰 담당자가 새로 올라온 공고 중 자사 역량과 맞는 공고를 **검토 → 선택**해야 한다. 수작업으로는 검토할 수 있는 공고 수가 제한되어 적합한 공고를 놓치는 경우가 생기고, 같은 인력으로는 처리량을 늘리기 어렵다.

### 목표
| 구분 | 내용 |
|------|------|
| 현재 | 공고 목록 확인·자격 확인·공고서 읽기·순위 결정을 모두 수작업으로 수행 |
| 기대 | 자격 확인과 1차 선별은 룰이, 공고서 검토와 순위·근거 정리는 RAG가 수행하고, 담당자는 추천 결과 검토와 최종 선택만 수행 |
| 효율성 | 공고 검토 + 선택 시간 단축 (**[목표값]** 업무 시간 50% 이상 단축) |
| 의사결정 | 근거가 붙은 추천(**[목표값]** 추천 정확도 Hit Rate@3 80% 이상, Precision@3 0.67 이상) + 담당자 최종 판단 |
| 기대 효과 | 같은 시간에 더 많은 공고를 객관적으로 선별해 수주 기회 확대 |

### 사전 조건
- 업체 프로필 JSON이 준비됨 (가상 업체 50건 중 1건, 스키마는 아래 '입력 예시')
- 공공데이터포털에서 내려받은 용역 공고 500건(2026-05 공고분)이 정적 파일로 준비됨. 공고서 PDF는 추천 대상으로 선별된 공고만 내려받아 캐시
- 지역 제한 공고(PDF 보유 45건)의 제한 시·도 수동 매핑표가 준비됨 (`rgnLmtBidLocplcJdgmBssNm`에는 지역명이 없음, 4.상세설계및개발환경구축 12.2절)

### 단계별 상세 흐름

#### 1단계 - 입력 데이터 준비

**담당자 액션**: React 화면에 진입하여 업체 프로필 JSON 파일 업로드  
**시스템 동작**: 업체 정보 파싱 및 스키마 검증, 공고 500건 로드

**입력 데이터 (업체)**:
- 회사명, 설립연도, 중소기업 여부, 소재지(시·도)
- 업종: 공공조달분류 대분류 + 세부분류번호
- 참여 가능 금액 범위 (최소·최대)
- 역량 키워드 (예: 교육, 방과후, 컴퓨터, 디지털, 코딩)
- 선호 계약방식 (예: 제한경쟁)
- 인증, 직무별 보유 인력, 과거 실적(기간, 계약금액, 발주처, 키워드)

#### 2단계 - 하드 필터 (룰, 탈락 조건)

**담당자 액션**: "추천 시작" 버튼 클릭  
**System**: 공고 500건을 아래 규칙으로 걸러냄. 하나라도 걸리면 제외하고 제외 사유(규칙 ID, 비교한 필드 값)를 기록

| 규칙 | 조건 | 비교 필드 | 비고 |
|-----|-----|---------|-----|
| H1 공고서 PDF 보유 | 첨부 파일명(`ntceSpecFileNm1`-`10`) 중 `.pdf`가 1개 이상 | 공고 첨부 파일명 | 500건 중 437건 통과. HWP만 있는 공고는 제외 |
| H2 마감일 | 기준일 이후 마감 (`bidClseDt`) | - | **테스트 데이터(2026-05)라 미적용**. API 연계 시 적용 |
| H3 업종 일치 | 공고 대분류(`pubPrcrmntLrgClsfcNm`)가 업체 업종 대분류에 포함되거나, 세부분류번호(`pubPrcrmntClsfcNo`)가 업체 세부분류에 포함 | 공고 ↔ 업체 `업종` | 공고 필드의 앞뒤 공백 제거 후 비교 |
| H4 참가 제한 | `bidPrtcptLmtYn` 또는 `indstrytyLmtYn`이 `Y`(중소기업 제한)이면 업체 `중소기업여부`가 `true` | 공고 ↔ 업체 `중소기업여부` | 두 필드의 정확한 의미는 공공데이터포털 활용가이드로 확인 **[확인 필요]** |
| H5 지역 제한 | `rgnLmtBidLocplcJdgmBssNm`이 비어 있으면 통과. 값이 있으면 수동 매핑표의 허용 시·도에 업체 `소재지`가 포함 | 공고 ↔ 지역 매핑표 ↔ 업체 `소재지` | 매핑표에 없는 공고는 보수적으로 제외 |
| H6 예산 범위 | `asignBdgtAmt`가 업체 `참여가능금액` 최소-최대 안 | 공고 ↔ 업체 `참여가능금액` | 예산이 비어 있으면 통과시키고 '예산 확인 필요' 표시 |

**출력**: 업체별 후보 공고 목록 + 공고별 통과·제외 내역

#### 3단계 - 소프트 점수 (룰, 상위 10건 선별)

**System**: 하드 필터를 통과한 공고에 0-100점을 매겨 **상위 10건 [초기 설정값]**을 확정

| 항목 | 가중치 **[초기 설정값]** | 계산 (0-1) |
|-----|---------|-----|
| S1 업종 세부 분류 일치 | 35% | 세부분류번호 일치 1.0 / 대분류만 일치 0.4 |
| S2 공고명 ↔ 역량 키워드 겹침 | 30% | 공고명(`bidNtceNm`)에 나오는 업체 역량 키워드 수 k → min(k, 3) / 3 |
| S3 예산 ↔ 실적 규모 유사도 | 20% | r = 공고 예산 / 업체 과거 실적 평균 계약금액 → min(r, 1/r). 예산이 없으면 0.5 |
| S4 계약방식 선호 | 15% | 공고 계약방식(`cntrctCnclsMthdNm`)이 업체 선호 계약방식에 포함되면 1.0, 아니면 0 |

**룰 점수** = (S1 × 0.35 + S2 × 0.30 + S3 × 0.20 + S4 × 0.15) × 100. 동점이면 공고번호 오름차순으로 정해 결과를 재현할 수 있게 합니다. 하드 필터 통과 공고가 10건 미만이면 있는 만큼만 넘기고 화면에 안내합니다.

**출력**: 상위 10건 + 항목별 점수 (룰 근거)

#### 4단계 - RAG 추천 (10건만)

**System**: 상위 10건의 공고서 PDF만 처리해 순위와 근거를 생성

1. 10건의 공고서 PDF를 내려받아(캐시) 텍스트 추출 → 페이지·문단 단위로 청킹 (메타데이터: 공고번호, 파일명, 페이지)
2. BGE-M3로 임베딩해 Chroma에 저장 (이번 실행의 10건만)
3. 업체 역량 키워드·실적명과 고정 질의(입찰참가자격, 과업 내용, 평가 방법)로 공고별 관련 청크 검색
4. LLM이 업체 프로필 + 10건의 공고 필드 + 공고별 검색 청크를 읽고 **순위와 근거 3-4개**를 생성. 근거마다 출처를 붙임
   - PDF 출처: 파일명, 페이지, 원문 인용 문구
   - 필드 출처: 공고·업체 필드명과 값
5. 공고서에 업체가 충족하지 못하는 자격(예: 특정 면허, 실적 건수)이 보이면 '자격 확인 필요'로 표시하고 순위를 낮춤
6. LLM 출력을 스키마로 검증. 실패하면 룰 점수 순위와 룰 근거로 대체 (4.상세설계및개발환경구축 5장)

**출력**: 10건의 RAG 순위 + 룰 점수 + 근거(출처 포함) + 하드 필터 통과 내역

> **한계**: PDF 보유 437건 중 제안요청서·과업지시서까지 PDF인 공고는 63건이고, 나머지는 입찰공고문만 PDF입니다. 이런 공고는 과업 세부 내용이 공고서에 적어 RAG 근거가 입찰참가자격·사업 개요·평가 방법 수준에 그칩니다. HWP 파싱은 확장 단계입니다.

#### 5단계 - 담당자 검토 및 최종 선택 (Human-in-the-loop ①)

**담당자 액션**: React 화면의 추천 공고 확인 및 선택

**추천 공고 10건 표시** (상위 3건 강조):
- 순위, 공고명, 수요기관, 예산, 마감일, 룰 점수
- 클릭하면 상세정보 표시 (하드 필터 통과 내역, 룰 항목별 점수, RAG 근거와 공고서 인용, 자격 확인 필요 항목)

**담당자 선택 기준**:
1. 자격 충족: 하드 필터는 시스템이 사전 적용. '자격 확인 필요' 표시가 있으면 공고서 원문을 확인
2. 과업 적합성: 공고서 근거가 우리 역량·실적과 맞는가?
3. 근거의 충분성: 다른 후보 대비 순위와 근거가 납득되는가?
4. 비즈니스 전략: 수익성과 수행 여력이 맞는가?

**최종 선택**: 위 기준을 종합하여 제안서를 작성할 공고 **1건 선택**

**승인 지점**: 담당자가 선택한 공고 확정 → LangGraph `interrupt`에서 재개

#### 6단계 - 선택 결과 저장 및 다음 단계 준비

**System**: 선택된 공고 정보를 LangGraph State(thread)에 저장, SC-002로 전달

**저장 데이터**: 공고번호, 선택 시각, 선택 근거, 해당 공고의 PDF 청크 (SC-002 평가항목 추출에 재사용)

### 상세 흐름 테이블

| 단계 | 담당자 행동 | Agent/System 처리 | 출력 |
|------|-----------|------------------|------|
| 1 | 화면 진입 → 업체 JSON 업로드 | 업체 정보 파싱·검증, 공고 500건 로드 | 업체 프로필 확인됨 |
| 2 | "추천 시작" 클릭 | 하드 필터 (룰) | 후보 공고 + 제외 사유 |
| 3 | 대기 (진행 상태 확인) | 소프트 점수 (룰) | 상위 10건 + 항목별 점수 |
| 4 | 대기 (진행 상태 확인) | RAG 추천 Agent (10건 PDF 청킹·검색 → LLM 순위·근거) | 10건 순위 + 근거(출처 포함) |
| 5 | 추천 10건 확인, 상세보기 → 1건 최종 선택 (HITL ①) | 근거·인용 표시, 선택 결과 검증·저장 | 선택 확정 |
| 6 | "제안서 만들기" 클릭 | SC-002로 전환 (같은 thread 유지) | 제안서 작성 준비 |

#### 추천 공고 (10건 중 상위 5건 표시)

### 성공 기준 및 KPI 측정

SC-001은 메인 시나리오이므로 KPI 1(추천 정확도), KPI 1-2(자격 필터 정확성), KPI 1-3(추천 근거 설명 가능성)을 **1순위 KPI**로 둡니다.

#### KPI 1: 추천 정확도 (Hit Rate@3 80% 이상, 품질 지표 Precision@3 0.67 이상) - **2.문제정의및서비스계획 1순위 KPI**

**정의**

| 지표 | 정의 | 역할 | 목표 | 판정 |
|-----|-----|-----|-----|-----|
| **Hit Rate@3** (판정 지표) | RAG 순위 상위 3건에 '추천' 라벨 공고가 1건 이상 있는 업체의 비율 | 작업 성공: 담당자가 입찰할 공고를 1건 고를 수 있는가 | **[목표값]** 80% 이상 (평가용 10개 중 8개 이상) | KPI 달성 여부 결정 |
| **Precision@3** (품질 지표) | 업체별 (RAG 상위 3건 중 '추천' 라벨 수 / 3)의 평균 | 추천 품질: 상위 3건 중 몇 건이 실제로 검토할 가치가 있는가 | **[목표값]** 0.67 이상 (평균 3건 중 2건) | 함께 측정·보고. 미달 시 오류 분석 근거로 사용 |
| 룰 Precision@3 (비교 지표) | 업체별 (룰 점수 상위 3건 중 '추천' 라벨 수 / 3)의 평균 | RAG 순위가 룰 순위보다 나은지 비교 | 목표 없음 | 보고만 함 |

**지표 선택 근거 (Hit Rate@3을 판정 지표로 유지하는 이유와 한계)**

- 판정 지표로 유지하는 이유: SC-001에서 담당자는 추천 목록에서 **공고 1건을 골라** SC-002로 넘어갑니다(HITL ①). 따라서 "상위 3건 안에 고를 공고가 있는가"는 담당자의 작업 성공 여부와 직접 대응합니다.
- 한계: Hit Rate@3은 나머지 2건이 '적격-비추천'이어서 담당자가 검토 시간을 낭비하는 경우를 구분하지 못합니다. 이 한계는 Precision@3을 함께 측정해 보완합니다.
- 비교 지표를 두는 이유: 같은 10건에 대해 룰 점수 순위와 RAG 순위를 모두 평가하면, 공고서를 읽는 RAG 단계가 실제로 순위를 개선했는지 같은 라벨로 보여줄 수 있습니다.
- 목표 80% 근거: 평가용 업체 10개 기준 한 단위가 10%p이며, "10개 중 8개 이상"을 담당자가 상위 3건만 봐도 되는 수준으로 둡니다.

**정답(GT) 라벨 기준**

공고 500건 × 업체 50개(25,000조합)는 모두 라벨링할 수 없으므로, **평가용 업체 10개 × 시스템 상위 10건 = 100조합**만 담당자 1인이 3단계 라벨과 판단 사유 1줄을 기록합니다 (상위 정의: 2.문제정의및서비스계획 '적합 공고 정의').

- Precision@3 계산: 평가용 업체 10개 각각의 (RAG 상위 3건 중 '추천' 라벨 수 / 3)의 평균. 룰 Precision@3, Precision@10도 같은 라벨로 계산

**판정 주체**: 자동 — 없음 (점수 평균 계산만) / 사람 — 5단계 평가와 인터뷰 (최종 판정)  
**측정 시점**: Phase 4(7-8주차)

## 시나리오 2: 제안서 초안 템플릿 생성 프로세스

### ID
SC-002

### 시나리오명
"선택된 공고에 맞춘 제안서 초안 템플릿을 받아 담당자가 이어서 작성하기"

### 상황
담당자가 SC-001에서 공고 1건을 선택함. 이제 제안서를 작성해야 하는데, 회사소개, 수행방안, 일정계획, 조직구성의 골격을 매번 처음부터 잡아야 하고, 공고별로 평가기준이 다르기 때문에 목차도 매번 달라짐. 결과적으로 공고별 제안서 작성에 묶여서 더 많은 공고에 응찰할 수 없음.

### 목표
| 구분 | 내용 |
|------|------|
| 현재 | 제안서 골격(목차, 회사소개, 평가기준 정리)을 공고마다 수작업으로 처음부터 작성 |
| 기대 | 시스템이 공고서 PDF에서 평가항목·배점을 추출하고, **고정 템플릿에 공고·업체·추천 근거 값을 삽입**해 초안 템플릿(섹션 4개 + 평가기준 대응표)을 만들고, 담당자는 다운로드 후 `[확인 필요]` 자리를 채움 |
| 범위 | 완성형 제안서가 아님. LLM은 평가항목·배점 추출에만 쓰고 문장을 생성하지 않음. 추천된 공고에서 제안서 작성이 시작될 수 있다는 **연결성**을 보여주는 보조 기능 |
| 효율성 | 제안서 골격 작성 시간 단축 (**[목표값]** SC-001 + SC-002 합산 업무 시간 50% 이상 단축) |
| 품질 | 공고 평가항목과 업체 정보가 템플릿에 빠짐없이 들어감 (**[목표값]** 필수 입력 항목 반영률 100%) |
| 기대 효과 | 같은 인력으로 대응 가능한 공고 수 증가, 담당자 경험과 무관하게 같은 골격에서 작성 시작 |

### 사전 조건
- SC-001에서 특정 공고 1건 선택 완료 (공고번호, 선택 시각 기록됨)
- 업체 프로필이 State에 있음 (회사 정보, 역량 키워드, 인력 구성, 과거 실적)
- 선택된 공고의 필드 값과 공고서 PDF 청크가 State에 있음 (SC-001 4단계 결과 재사용)

### 단계별 상세 흐름

#### 1단계 - 입력 데이터 준비

**담당자 액션**: SC-001에서 "제안서 만들기" 버튼 클릭  
**System**: 선택된 공고번호 + 업체 프로필 + RAG 추천 근거 + 해당 공고의 PDF 청크를 같은 thread의 State에서 자동 로드

**입력 데이터**:
- 공고 정보: 공고명, 수요기관, 예산, 마감일, 계약방식, 기술·가격 평가 비율(`techAbltEvlRt`, `bidPrceEvlRt`), 공고서 PDF 청크
- 업체 정보: 회사명, 역량 키워드, 인증, 인력 구성, 과거 실적

#### 2단계 - 평가항목·배점 추출 (RAG + LLM 구조화 추출)

**System**: 선택 공고의 PDF 청크에서 "평가 항목", "배점", "기술능력평가", "과업 기간"으로 검색한 청크를 LLM에 주고 아래 JSON으로 추출. 스키마로 검증하고 각 항목에 출처(파일·페이지)를 붙임

```json
{
  "과업기간": {"값": "계약일로부터 2026-12-31까지", "출처": {"파일": "공고문.pdf", "페이지": 1}},
  "평가항목": [
    {"대분류": "기술능력평가", "항목": "사업 이해도", "배점": 10, "출처": {"파일": "공고문.pdf", "페이지": 3}}
  ]
}
```

- 공고서 PDF에 평가항목이 없으면(제안요청서가 HWP인 경우) 공고 필드의 기술·가격 평가 비율만 행으로 넣고 세부 항목은 `[확인 필요]`로 둡니다.
- 추출값은 템플릿에 그대로 들어가므로, 원문에 없는 항목·배점을 만들지 않도록 프롬프트에서 "원문에 없으면 null"을 강제하고 KPI 1-2에서 원문과 대조합니다.

#### 3단계 - 초안 템플릿 생성 (고정 템플릿 + 입력값 삽입)

**System**: 제안서 템플릿 모듈이 고정 HTML 템플릿에 입력값을 삽입해 섹션 4개를 만듦. **이 단계는 LLM을 호출하지 않음**

| 섹션 | 삽입하는 입력값 | `[확인 필요]`로 남기는 자리 |
|------|---------------|-----------------------|
| 1. 회사소개 | 업체 프로필: 회사명, 설립연도, 역량 키워드, 인증, 과거 실적 표 | 회사 비전·차별화 포인트 |
| 2. 수행방안 | 추출한 기술능력 평가항목을 목차(`<h3>`)로, 항목별 관련 업체 근거(역량·실적) | 항목별 수행 방안 본문 |
| 3. 추진일정 | 고정 단계(착수·분석 / 수행 / 완료·보고) + 추출한 과업기간 | 단계별 기간 |
| 4. 조직구성 | 업체 보유인력(역할별 인원) | 투입 인력·역할 분담 |

평가항목별 관련 업체 근거는 BGE-M3 유사도(평가항목 ↔ 업체 역량 키워드·실적명)로 고르며, 유사도가 임계값 미만이면 `[확인 필요]`로 둡니다. SC-001의 RAG 추천 근거도 수행방안 첫머리에 그대로 옮겨 두 시나리오를 연결합니다.

**출력**: 섹션별 HTML 조각 4개 (`<section>` 단위, 삽입값은 HTML 이스케이프)

#### 4단계 - 평가기준 대응표 생성

**System**: 추출한 평가항목을 행으로 하는 고정 표 템플릿에 값을 삽입

1. 평가항목·배점을 그대로 행으로 삽입 (예: 사업 이해도 10점, 교육과정 구성 20점)
2. 평가항목별 대응 섹션 번호와 관련 업체 근거(3단계와 같은 결과) 삽입
3. 추출 실패·근거가 없는 항목은 `[확인 필요]`로 표시

**출력**: 평가기준 대응표 (HTML `<table>`)

#### 5단계 - 미리보기 및 다운로드

**담당자 액션**: React 화면에서 초안 템플릿과 대응표를 미리보기로 확인한 뒤 "다운로드" 클릭

- 화면에서는 섹션을 편집하지 않습니다. `[확인 필요]` 자리 작성과 수정은 다운로드 후 담당자가 수행합니다.
- 평가항목 추출 결과는 공고서 출처(파일·페이지)와 함께 표시해 담당자가 원문과 대조할 수 있게 합니다.
- 본문은 템플릿 삽입이라 "다시 생성"과 확정 단계(HITL ②)는 두지 않습니다. LLM 문장 생성을 도입하는 확장 단계에서 HITL ②를 추가합니다.

**출력**:
- 초안 템플릿 HTML (섹션 4개 + 평가기준 대응표, 인쇄용 CSS 포함한 단일 `.html` 파일)

**저장 파일명**: `공고번호_회사명_v1.0.html`

| 단계 | 담당자 행동 | System 처리 | 출력 | 역할 |
|------|-----------|------------------|------|------|
| 1 | "제안서 만들기" 클릭 | 공고·업체·추천 근거·PDF 청크 State에서 로드 | 데이터 준비 완료 | System |

| 평가기준 대응표 | **필수 (축소)** | 추출한 평가항목·배점 + 대응 섹션 + 관련 업체 근거 삽입 |
| 안전한 렌더링 | **필수** | sanitize(DOMPurify) 후 React 화면 미리보기 |
| HTML 다운로드 | **필수** | 인쇄용 CSS 포함 단일 `.html` 파일 저장 |
| HWP 제안요청서 파싱 | **확장** | 평가항목이 HWP에만 있는 공고 대응 |
| 섹션별 고도 생성 (LLM 문장 생성) | **확장** | 수행방안 본문 등 서술형 생성, 도입 시 HITL ②(확정 / 다시 생성) 추가 |
| 자기 검증·재작성 루프 | **확장** | 2.문제정의및서비스계획 기능 4 |

| PDF/Word 변환 | **확장** | 1차에는 브라우저 인쇄(PDF로 저장)로 대체 |

### 성공 기준 및 KPI 측정

SC-002의 KPI는 **보조 KPI**입니다. 생성 품질이 아니라 "추천된 공고에서 바로 제안서 작성을 시작할 수 있는가"만 확인합니다.

#### KPI 1: 초안 시작 가능 여부 (필수 입력 항목 반영률 100%) - **2.문제정의및서비스계획 보조 KPI**

**정의**: 초안 템플릿이 오류 없이 생성되고, 추출한 평가항목과 업체의 필수 입력 항목이 빠짐없이 들어갔는지 여부

**측정 방법**:
- 측정 대상: 평가용 업체 41-50 × 각 업체의 RAG 1순위 공고 = 초안 템플릿 10건 (실제 사용 흐름과 동일)
- 자동 검사 1 (생성): 10건 모두 HTML 파싱 성공, 섹션 4개 + 대응표 존재
- 자동 검사 2 (반영): 아래 항목을 추출 JSON·업체 프로필 값에서 바로 뽑아 HTML에 들어 있는지 확인. 추출 실패 항목은 `[확인 필요]`로 들어 있으면 반영으로 봄
- 계산식: 초안별 (반영된 항목 수 / 전체 항목 수) × 100 → 10건 평균
- 함께 기록: 평가항목 추출 성공 공고 수 (공고서 PDF에 평가항목이 없는 공고 비율 파악)

| 섹션 | 필수 입력 항목 (출처) |
|------|-------------|
| 회사소개 | 회사명, 역량 키워드, 과거 실적명 (업체 프로필) |
| 수행방안 | 추출한 기술능력 평가항목 전부가 목차로 등장 (추출 JSON) |
| 조직구성 | 역할별 인원 (업체 `보유인력`) |
| 평가기준 대응표 | 추출한 평가항목·배점 전부가 행으로 등장 (추출 JSON) |

**판정 기준**: 10건 모두 생성 + 평균 반영률 **100%** (템플릿 삽입 방식이라 누락이 있으면 버그로 봄)  
**판정 주체**: 자동 (최종 판정) / 사람 — 없음  
**측정 시점**: Phase 2부터 회귀 테스트로 상시 확인, Phase 4에 최종 측정

#### KPI 1-2: 초안 근거성 (업체 프로필·공고서에 없는 사실 기재 0건) - **2.문제정의및서비스계획 보조 KPI**

**정의**: 초안에 쓴 사실 항목이 업체 프로필과 공고서 원문에 근거하는지 여부. 업체 사실은 템플릿이 프로필 값만 삽입하므로 구조상 0건이어야 하고, 평가항목은 LLM 추출이라 원문 대조가 필요함

**측정 방법**:
- 측정 대상: KPI 1과 같은 초안 10건
- 업체 사실 대조: 실적명, 발주처, 금액, 기간, 인원 수, 보유 인증을 업체 프로필 JSON 값과 문자열·숫자 비교
- 평가항목 대조: 추출한 평가항목명·배점이 출처로 표시한 PDF 페이지 청크 원문에 있는지 자동 확인, 불일치는 사람이 원문 확인
- 결과: 불일치 항목 목록

**판정 기준**: **0건** (허위 기재는 감점·제재 위험)  
**판정 주체**: 자동 — 불일치 목록 생성 (최종 판정) / 사람 — 불일치가 나오면 원문 확인과 원인 분류  
**측정 시점**: Phase 4(7-8주차)

#### KPI 2: 업무 시간 단축 (50% 이상) - **2.문제정의및서비스계획 업무 KPI**

**정의**: 제안서 초안 골격(목차, 회사소개·조직구성 표, 평가기준 대응표) 작성에 소요되는 시간 단축. 본문 서술은 양쪽 모두 담당자 몫이므로 측정에서 제외

**측정 항목** (수작업 vs 서비스 각각 기록):
- 공고서에서 평가항목 정리 (수작업 vs 평가항목 추출 모듈)
- 초안 골격·평가기준 대응표 작성 (수작업 vs 제안서 템플릿 모듈)
- 담당자 확인 (양쪽 모두 담당자)

**계산식**: (수작업 시간 − 서비스 사용 시간) / 수작업 시간 × 100  
**측정 방법**: 대표 공고 3건을 담당자 1인이 두 방식으로 수행하고 시간 기록 (수작업·서비스 소요시간 모두 **[실측 예정값]**)  
**판정 기준**: SC-001 + SC-002 합산 **50% 이상 단축**  
**판정 주체**: 자동 — Agent 실행 시간 로그 기록 / 사람 — 수작업 골격 작성 시간과 확인 시간 기록 (최종 단축률 산출)  
**측정 시점**: Phase 4(7-8주차)

> 기존 KPI 3 '초안 재사용성(A+B 80%)'은 삭제했습니다. 초안 템플릿은 `[확인 필요]` 자리를 남기는 것이 전제라 문장 단위 재사용 비율로 평가하는 것이 맞지 않기 때문입니다. 템플릿의 유용성은 SC-001 KPI 3 담당자 만족도에서 함께 평가합니다.

### 업무 시간 단축

### 품질 개선
1. **자격요건 누락 방지**: 하드 필터로 부적격 공고를 추천에서 제외하고, 공고서에서 추출한 평가항목을 초안 템플릿에 빠짐없이 옮깁니다.
2. **공고별 맞춤 골격**: 담당자 경험과 무관하게 공고 평가항목 기준의 목차에서 작성을 시작합니다.
3. **평가기준 대응 정리**: 평가항목별로 대응 섹션과 업체 근거를 표로 정리하고, 근거가 없는 항목은 `[확인 필요]`로 표시합니다.

### 의사결정 지원
1. **추천 근거 제시**: 자격·역량이 맞는 공고를 근거와 출처(공고서의 어느 페이지, 업체·공고의 어느 값인지)와 함께 선별합니다.
2. **데이터 기반 판단**: 룰 항목별 점수와 공고서 근거로 객관적으로 비교합니다.
3. **사람의 최종 결정**: 최종 선택과 확정은 담당자가 수행하며, AI는 조력자 역할입니다.

### 정량 평가 (자동 측정 중심, 평가 주체는 KPI 측정 종합표 참조)

**SC-001 (공고 추천)**
- **추천 정확도:** 평가용 업체 41-50 × 상위 10건(100조합)에 대해 Hit Rate@3 80% 이상(판정), Precision@3 0.67 이상(품질 지표). 정답은 담당자 1인이 체크리스트 기준으로 순위를 가린 채 RAG 실행 전에 라벨링. 룰 Precision@3과 비교해 RAG 효과를 보고. 가중치·프롬프트는 업체 01-05(조정용)로만 조정
- **자격 필터 정확성:** 하드 필터 통과 공고 중 하드 필터 기준 '부적격' 0건 (단위 테스트 + 샘플 30건 대조 + 라벨 집계)
- **추천 근거 설명 가능성:** 추천 근거의 출처 확인 비율 95% 이상

**SC-002 (초안 템플릿, 보조)**
- **초안 시작 가능 여부:** 10건 모두 섹션 4개 + 대응표가 파싱 가능한 구조로 생성, 필수 입력 항목 반영률 100%
- **초안 근거성:** 초안 템플릿 10건에서 프로필·공고서 원문에 없는 사실 기재 0건

### 정성 평가 (사용자 피드백)

**담당자 인터뷰 (1인)**
- SC-001: 추천 공고 적합도, 입찰 여부 판단 도움 수준, 화면 이해도
- SC-002: 초안 템플릿 목차의 적절성, 템플릿 활용 의향, 골격 작성 시간 절감 체감, 전반 만족도 (5점 척도)

**초안 템플릿 검증**
- 실제 공고 3건에서 생성된 초안 템플릿으로 담당자가 골격 작성을 마칠 때까지의 소요 시간 측정
- 템플릿에 추가하면 좋을 고정 항목 기록 (확장 단계 개선에 사용)

### 최종 검증 (Gate)
- 평가용 업체 5개 × RAG 1순위 공고 = 5건 End-to-End 테스트 (업로드 → 추천 → 선택 → 초안 다운로드)
- 통과 기준: 1순위 KPI 3종(추천 정확도, 자격 필터 정확성, 근거 설명 가능성) 달성 필수 + 시간 단축 50% + 보조 KPI 달성 + 담당자 만족도 3.5/5.0 이상
- 담당자가 초안 템플릿에서 바로 본문 작성을 시작할 수 있는 수준인지 확인
