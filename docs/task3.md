입찰·영업 담당자의 반복적인 공고 검토와 제안서 작성을 AI로 자동화하는 2가지 핵심 시나리오입니다.

> **수치 표기 원칙**: 모든 수치는 괄호로 근거를 붙입니다. 외부 출처가 없는 추정치(현재 소요시간, 월 처리량 등)는 쓰지 않고 Phase 4(7~8주차) 실측으로 확정합니다. 목표치·설계값은 '팀 설정'으로 표시합니다.

## 시나리오 1: 공고 검토 및 선택 프로세스

### ID
SC-001

### 시나리오명
"아침에 적합 공고 찾아 최종 선택하기"

### 상황
입찰 담당자가 새로 올라온 공고 중 자사 역량과 맞는 공고를 **검토 → 선택**해야 한다. 수작업으로는 검토할 수 있는 공고 수가 제한되어 적합한 공고를 놓치는 경우가 생기고, 같은 인력으로는 처리량을 늘리기 어렵다.

### 목표
- **현재:** 공고 분석·자격 확인·순위 결정을 모두 수작업으로 수행
- **기대:** 분석·매칭·순위는 Agent가 수행하고, 담당자는 추천 결과 검토와 최종 선택만 수행
- **핵심 메리트:**
  - 효율성: 공고 검토 + 선택 시간 단축 (목표: task2 KPI '업무 시간 단축 50% 이상')
  - 의사결정: 근거가 붙은 추천(목표: 추천 정확도 90% 이상) + 담당자 최종 판단
  - 결과: 시간 단축 + 양(수량 증가) + 질(객관적 선별) 결합 → 수주 기회 확대

### 사전 조건
- 기업 프로필 정보 시스템에 등록 완료 (기술 스택, 보유 인력, 과거 프로젝트 실적)
- IT 용역 공고 30건이 정적 데이터셋으로 준비됨 (근거: task2 In Scope)

### 단계별 상세 흐름

#### 1단계 - 입력 데이터 준비

**담당자 액션**: React 화면에 진입하여 기업 프로필 JSON 파일 업로드  
**시스템 동작**: 기업정보(기술 스택, 인력, 실적) 파싱 및 스키마 검증

**입력 데이터**:
- 회사명, 설립연도, 인력 규모
- 기술 보유: Java, Spring, React, PostgreSQL, AWS 등
- 자격증: ISO27001, CMMI Level 3 등
- 직무별 인력 분포
- 최근 프로젝트 경험(기간, 예산, 결과)

#### 2단계 - 공고 분석 Agent 실행

**담당자 액션**: "공고 분석 시작" 버튼 클릭  
**System**: 공고 분석 Agent가 공고 30건 병렬 처리

**Agent 처리**:
1. 각 공고의 과업 내용, 자격요건, 평가기준을 자동 파싱
2. 공고를 기술 분류(웹 개발, 데이터 분석 등)로 카테고리화
3. 필수 자격요건 항목 추출 (기술 스택, 경험 연수, 인력 수, 자격증)

**출력**: 공고별 구조화된 데이터 (기술 분류, 필수 자격, 평가 기준)

#### 3단계 - 매칭 Agent 실행

**System**: 매칭 Agent가 기업 정보 vs 각 공고 요구사항 비교

**Agent 처리**:
1. 기술 스택 매칭: 기업 보유 기술 vs 공고 필수 기술
2. 경험 매칭: 기업 프로젝트 경험 vs 공고 과업내용 적합도
3. 인력 매칭: 기업 가용 인력 vs 공고 요구 인력
4. 적합도 점수 계산: 0~100점, 기술 40% + 경험 40% + 인력 20% (근거: 팀 설정 초기값, 기술·경험을 핵심 판단 요소로 봄. Phase 4 정답셋 결과로 조정)

**출력**: 상위 5건 공고의 적합도 점수 + 추천 근거 (근거: KPI는 상위 3건 기준, 비교 여유분 2건을 더한 팀 설정값)

#### 4단계 - 담당자 검토 및 최종 선택 (Human-in-the-loop ①)

**담당자 액션**: React 화면의 추천 공고 확인 및 선택

**상위 5건 추천 공고 표시**:
- 순위, 공고명, 예산, 마감일, 적합도 점수
- 클릭하면 상세정보 표시 (기술 일치 항목, 자격요건 충족 여부, 추천 근거)

**담당자 선택 기준**:
1. 자격 충족: 필수 자격요건을 모두 충족하는가? (미충족 공고는 시스템이 사전 제외)
2. 기술 매칭: 우리 팀의 역량을 최대한 활용할 수 있는가?
3. 적합도 점수: 다른 후보 대비 점수와 근거가 충분한가?
4. 비즈니스 전략: 수익성과 수행 여력이 맞는가?

**최종 선택**: 위 기준을 종합하여 제안서를 작성할 공고 **1건 선택**

**승인 지점**: 담당자가 선택한 공고 확정 → LangGraph `interrupt`에서 재개

#### 5단계 - 선택 결과 저장 및 다음 단계 준비

**System**: 선택된 공고 정보를 LangGraph State(thread)에 저장, SC-002로 전달

**저장 데이터**: 공고 ID, 선택 시각, 선택 근거

### 상세 흐름 테이블

| 단계 | 담당자 행동 | Agent/System 처리 | 출력 |
|------|-----------|------------------|------|
| 1 | 화면 진입 → JSON 업로드 | 기업정보 파싱·검증 | 기업 프로필 확인됨 |
| 2 | "공고 분석 시작" 클릭 | 공고 분석 Agent 실행 | 공고 구조화 데이터 |
| 3 | 대기 (진행 상태 확인) | 매칭 Agent 실행 | 상위 5건 추천 공고 |
| 4 | 추천 공고 5건 확인, 상세보기 | 기술/자격/근거 표시 | 매칭 분석표 |
| 5 | 공고 1건 최종 선택 (HITL ①) | 선택 결과 검증·저장 | 선택 확정 |
| 6 | "제안서 만들기" 클릭 | SC-002로 전환 (같은 thread 유지) | 제안서 작성 준비 |

**판정 기준**: 정확도 **90% 이상** (근거: 기업 10개사 중 9개사 이상)  
**측정 시점**: Phase 4(7~8주차) 자동화 테스트

- 공고 분석 (수작업 vs 공고 분석 Agent)
- 매칭 및 순위 결정 (수작업 vs 매칭 Agent)
- 담당자 검토 및 선택 (양쪽 모두 담당자)

**계산식**: (수작업 시간 − 서비스 사용 시간) / 수작업 시간 × 100  
**측정 방법**: 대표 공고 3건을 담당자 1인이 두 방식으로 수행하고 시간 기록  
**판정 기준**: SC-001 + SC-002 합산 **50% 이상 단축** (근거: task2 KPI 목표)  
**측정 시점**: Phase 4(7~8주차)

## 시나리오 2: 제안서 초안 자동 생성 프로세스

### ID
SC-002

### 시나리오명
"선택된 공고에 대해 제안서 초안을 자동으로 생성하고 담당자가 고도화하기"

### 상황
담당자가 SC-001에서 공고 1건을 선택함. 이제 제안서 초안을 작성해야 하는데, 회사소개, 기술방안, 일정계획, 조직구성 등을 매번 처음부터 작성해야 하고, 공고별로 평가기준이 다르기 때문에 매번 다른 접근이 필요함. 결과적으로 공고별 제안서 작성에 묶여서 더 많은 공고에 응찰할 수 없음.

### 목표
- **현재:** 제안서 초안을 공고마다 수작업으로 처음부터 작성
- **기대:** Agent가 HTML 초안 + 평가기준 대응표를 생성하고, 담당자는 검토·수정만 수행
- **핵심 메리트:**
  - 효율성: 제안서 작성 시간 단축 (목표: task2 KPI '업무 시간 단축 50% 이상')
  - 품질: 공고별 맞춤 작성 + 평가기준 대응표 자동 매핑 → 필수 항목 누락 방지 (목표: 커버율 80% 이상)
  - 의사결정: 평가기준별 강점 제시로 제안 전략 수립 시간 단축
  - 결과: 같은 인력으로 대응 가능한 공고 수 증가 + 각 제안서 경쟁력 향상

### 사전 조건
- SC-001에서 특정 공고 1건 선택 완료 (공고 ID, 선택 시각 기록됨)
- 기업 프로필 정보 시스템에 등록 완료 (회사 소개, 기술 보유, 인력 구성, 과거 프로젝트 실적)
- 선택된 공고의 상세 정보 준비됨 (과업 내용, 평가 기준, 필수 자격 요건, 마감일, 예산)

### 단계별 상세 흐름

#### 1단계 - 입력 데이터 준비

**담당자 액션**: SC-001에서 "제안서 만들기" 버튼 클릭  
**System**: 선택된 공고 ID + 기업 프로필을 같은 thread의 State에서 자동 로드

**입력 데이터**:
- 공고 정보: 공고명, 과업 내용, 평가 기준, 필수 자격, 예산, 마감일
- 기업 정보: 회사명, 기술 스택, 인력 구성, 과거 프로젝트 실적

#### 2단계 - 제안서 작성 Agent 실행 (4개 섹션 병렬 생성)

**System**: 제안서 작성 Agent가 4개 섹션을 병렬로 생성

**Agent 처리** (LangGraph Supervisor + Sub-Agent 구조):
- **Sub-Agent 1**: 회사소개 섹션 → 기업명, 핵심역량, 유사 실적
- **Sub-Agent 2**: 기술방안 섹션 → 공고 요구사항 분석 + 기업 기술 매칭 → 시스템 구성 제시
- **Sub-Agent 3**: 추진일정 섹션 → 공고 기간 분석 + Phase별 일정 구성
- **Sub-Agent 4**: 조직구성 섹션 → 기업 인력 기반 팀 구성 제안

**출력**: 섹션별 HTML 조각 4개 (`<section>` 단위, 허용 태그만 사용)

#### 3단계 - 평가기준 대응표 자동 생성

**System**: 매칭 Agent가 공고 평가 기준과 제안서 내용을 매칭

**Agent 처리**:
1. 공고에 명시된 평가 기준 항목 추출 (예: 기술력 50점, 가격 30점, 실적 20점)
2. 생성된 제안서의 각 섹션이 평가 기준의 어느 부분을 충족하는지 매칭
3. 각 평가 기준별 강점/보완점 분석

**출력**: 평가기준 대응표 (HTML `<table>`)

#### 4단계 - 담당자 검토 및 고도화 (Human-in-the-loop ②)

**담당자 액션**: React 화면에서 생성된 HTML 초안과 평가기준 대응표 검토·수정

**검토 프로세스**:
1. 자동 생성된 초안 읽기
   - 회사명, 기술명, 인력 정보 정확성 확인
   - 숫자 일치성 검증 (예산, 인력 수, 프로젝트 기간)
   - 공고 요구사항과의 적합성 재확인

2. 필요시 수정 (섹션 단위 편집 또는 "섹션 다시 생성")
   - 회사 기밀정보 추가 또는 제거
   - 실적사례 상세화 (예: "금융 챗봇" → "OO은행 금융 챗봇 개발(2024년)"처럼 실제 수치·기간 보강)
   - 기술방안의 차별화 포인트 강조
   - 약점 보완 전략 추가 (예: 가격 경쟁력 약점 → 효율적 인력 구성으로 보완)

3. 평가기준 대응 검증
   - 각 평가 기준별 대응 전략이 명확한지 확인

**승인 지점**: 담당자가 "제안서 완성" 버튼 클릭 → LangGraph `interrupt`에서 수정본과 함께 재개

#### 5단계 - 최종 제안서 생성 및 저장

**System**: 담당자 수정사항 반영 후 최종 HTML 문서 조립

**출력**:
- 최종 제안서 HTML (섹션 4개 + 평가기준 대응표, 인쇄용 CSS 포함한 단일 `.html` 파일)
- 수정 이력 (LangGraph checkpoint 기록)

**저장 파일명**: `공고ID_회사명_v1.0.html`

### 상세 흐름 테이블

| 단계 | 담당자 행동 | Agent/System 처리 | 출력 | 역할 |
|------|-----------|------------------|------|------|
| 1 | "제안서 만들기" 클릭 | 공고+기업정보 State에서 로드 | 데이터 준비 완료 | System |
| 2 | 진행 상태 확인 (대기) | 제안서 작성 Agent 실행 | 섹션별 HTML 4개 | Sub-Agent ×4 |
| 3 | 대기 | 평가기준 매칭 실행 | 대응표 HTML | 매칭 Agent |

### 성공 기준 및 KPI 측정

#### KPI 1: 제안서 초안 커버율 (80% 이상) - **task2 핵심 KPI**

**정의**: 공고 필수 항목 반영률 (평가기준 및 과업요구사항 포함도)

**측정 방법**:
- 측정 대상: 공고 30건 × 각 공고의 추천 1순위 기업 = 초안 30건 (근거: 실제 사용 흐름과 같고, 300조합 전체 대비 생성 비용·검토 시간 1/10)
- 각 공고별로 **필수 포함 항목 체크리스트** 사전 작성:
  - 회사소개: 기업명, 핵심역량, 유사 실적
  - 기술방안: 시스템 아키텍처, 보안대책, 개발 단계
  - 추진일정: Phase 구분, 산출물
  - 조직구성: 역할별 인원
  - 평가기준 대응표: 공고 평가 항목 전부에 대한 대응 전략
- 자동 검사: HTML을 섹션(`<section id>`) 단위로 파싱한 뒤 체크리스트 항목 포함 여부를 키워드 매칭으로 검증
- 계산식: 초안별 (포함된 필수 항목 수 / 전체 필수 항목 수) × 100 → 30건 평균

**판정 기준**: 평균 커버율 **80% 이상** (근거: task2 KPI 목표)  
**측정 시점**: Phase 4(7~8주차) 자동화 테스트

#### KPI 1-2: 제안서 초안 근거성 (프로필에 없는 사실 기재 0건) - **task2 핵심 KPI**

**정의**: 초안에 쓴 사실 항목이 기업 프로필에 근거하는지 여부 (커버율이 "빠짐없이 담았는가"라면, 근거성은 "담긴 내용이 사실인가")

**측정 방법**:
- 측정 대상: 커버율과 같은 초안 30건
- 사실 항목 추출: 실적명, 발주처, 금액, 기간, 인원 수, 보유 자격·인증
- 자동 대조: 추출 항목을 기업 프로필 JSON 값과 문자열·숫자 비교 → 불일치 항목 목록 생성
- 담당자 확인: 불일치 목록만 담당자 1인이 검토해 "허위/표현 차이"로 최종 판정
- 계산: 초안 30건의 허위 판정 항목 수 합계

**판정 기준**: **0건** (근거: task2 KPI 목표, 허위 기재는 감점·제재 위험)  
**측정 시점**: Phase 4(7~8주차)

#### KPI 2: 업무 시간 단축 (50% 이상) - **task2 핵심 KPI**

**정의**: 제안서 초안 작성부터 최종 검토까지 소요되는 시간 단축

**측정 항목** (수작업 vs 서비스 각각 기록):
- 제안서 초안 작성 (수작업 vs 제안서 작성 Agent)
- 평가기준 대응 분석 (수작업 vs 매칭 Agent)
- 담당자 검토 및 수정 (양쪽 모두 담당자)

**계산식**: (수작업 시간 − 서비스 사용 시간) / 수작업 시간 × 100  
**측정 방법**: 대표 공고 3건을 담당자 1인이 두 방식으로 수행하고 시간 기록  
**판정 기준**: SC-001 + SC-002 합산 **50% 이상 단축** (근거: task2 KPI 목표)  
**측정 시점**: Phase 4(7~8주차)

#### KPI 3: 생성 초안의 실용성 (재사용 가능 비율 80% 이상) - **품질 및 재사용성**

**정의**: 생성된 제안서 초안 중 실무에 바로 사용 가능한 정도

**측정 방법**:
- 담당자 1인이 자동 생성된 초안 10건을 검토 (근거: 커버율 측정용 30건 중 1/3 표본, 수작업 검토 가능한 분량)
- 각 문장/섹션을 분류:
  - (A) 완벽함: 수정 불필요
  - (B) 경미한 수정: 오류 수정만 필요 (숫자, 표기 등)
  - (C) 의미 있는 재작성: 내용 수정 필요
  - (D) 완전히 새로 작성: 항목 전체 재작성

- 계산: (A + B 항목의 글자 수) / (전체 초안 글자 수) × 100

**판정 기준**: 
- 재사용 가능 비율(A+B) **80% 이상** (근거: 커버율 목표와 같은 기준으로 팀 설정)
- 담당자 만족도 **3.5점 이상**(5점 만점, 근거: SC-001 KPI 3과 동일 기준)

**측정 시점**: Phase 4(7~8주차)

## 부록 E. 검증 계획

### 정량 평가 (자동)

**SC-001 (공고 추천)**
- **추천 정확도:** 정답셋 300조합(30 공고 × 10 기업)에 대해 90% 이상
  - 정답 판정: 담당자 1인이 사전 라벨링한 '추천' 공고 (3단계 라벨 중)
- **자격 판정 정확도(보조):** 규칙 기반 Eligibility 판정과 '부적격' 라벨 일치율

**SC-002 (제안서 생성)**
- **초안 커버율:** 초안 30건 평균 80% 이상
- **초안 근거성:** 초안 30건에서 프로필에 없는 사실 기재 0건
- **HTML 유효성:** 30건 모두 섹션 4개 + 대응표가 파싱 가능한 구조로 생성

### 정성 평가 (사용자 피드백)

**담당자 인터뷰 (1인)**
- SC-001: 추천 공고 적합도, 입찰 여부 판단 도움 수준, 화면 이해도
- SC-002: 생성 초안 완성도, 재사용 가능 비율, 수정 소요 시간, 전반 만족도 (5점 척도)

**초안 품질 검증**
- 실제 공고 3건에서 자동 생성된 초안을 담당자가 직접 수정하며 소요 시간 측정
- 수정 필요 항목 분류: KPI 3의 A~D 기준 사용

### 최종 검증 (Gate)
- 실제 공고 3건 × 가상 기업 5개 = 15건 End-to-End 테스트 (근거: 시간 측정 공고 3건 × 초기 기업 5개사)
- 통과 기준: 핵심 KPI 4종 달성 + 담당자 만족도 3.5/5.0 이상
- 담당자가 검수 후 실제 제출 가능한 수준인지 확인

### SC-002: 제안서 초안 생성 시스템
