# 나라장터 AI 입찰 어시스턴트 - 문제 정의 및 서비스 기획

## 1. 프로젝트 개요

### 프로젝트명

나라장터 AI 입찰 어시스턴트 - 기업 맞춤 공고 추천 서비스 (+ 제안서 초안 템플릿 생성)

**범위 결정 (2026-10-12, 멘토 피드백 반영)**: 메인 기능은 **기업 맞춤 공고 추천**이다. 이 프로젝트의 핵심 가치는 "업체 정보를 바탕으로 어떤 공고를 선별하고 왜 추천하는지"를 보여주는 데 있다. 제안서는 8주 안에 완성형으로 만들 수 없고 어차피 담당자가 다시 작업해야 하므로, **고정 템플릿 + 입력값 삽입** 방식의 초안 템플릿까지만 생성한다. 제안서 기능의 역할은 "추천된 공고를 바탕으로 제안서 작성이 시작될 수 있다"는 연결성을 보여주는 것이다.

**범위 결정 (2026-10-14, 데이터·추천 구조 개정)**: 공고는 공공데이터포털에서 별도로 내려받은 **실제 용역 공고 500건**(2026-05 공고분, 첨부 공고서 PDF 포함)을, 업체는 **가상 업체 JSON 50건**을 사용한다. 추천은 **① 하드 필터(룰, 탈락 조건) → ② 소프트 점수(룰, 상위 10건 선별) → ③ RAG 추천(10건의 공고서 PDF만 청킹·임베딩해 순위와 근거 생성)** 3단계로 처리한다. 조달청 API 실시간 연계는 고도화 단계로 미룬다.

## 2. 문제 정의

### 현재 상황 (As-Is)

입찰 담당자는 나라장터에 매일 올라오는 다수의 공고 중에서 자사 역량과 맞는 공고를 일일이 확인해야 한다. 적합 공고를 찾은 후에는 공고문과 제안요청서를 읽으면서 자격요건, 필수 제출서류, 평가기준을 수작업으로 정리해야 한다. 제안서 작성 시에는 이전 제안서를 복사하거나 템플릿을 수정하는 방식으로 진행하는데, 공고마다 요구사항이 다르기 때문에 매번 초안부터 작성해야 한다. 이 모든 업무는 담당자 개인의 경험과 시간에 크게 의존하고 있다.

### Pain Point (문제점)

**시간 손실**: 공고 검토와 공고별 제안서 초안 작성이 모두 수작업이라, 담당자가 처리할 수 있는 공고 수가 물리적으로 제한된다. 그 결과 검토하지 못한 공고 중 적합 공고를 놓치게 된다. (구체적 소요시간은 Phase 4 실측으로 확인)

**품질 불일치**: 담당자마다 공고 적합성 판단 기준이 다르고, 제안서도 작성자마다 스타일이 달라 일관성이 낮다. 자격요건이나 평가기준 항목을 놓치는 휴먼에러도 발생할 수 있으며, 필수 항목 누락은 곧 감점·탈락으로 이어진다.

**기회 비용 (가장 치명적)**: 검토하지 못하고 넘어가는 공고 중에 적합한 것이 있을 수 있고, 소수 인력이 반복적인 탐색·정리·초안 작성에 묶여 있어 더 중요한 전략적 업무에 집중할 수 없다. 이는 결국 수주 기회 손실과 담당자 역량 미활용으로 이어진다.

### 기회 요인

공고 분석 -> 매칭 -> 제안서 작성 -> 검토로 이어지는 업무 흐름이 체계적으로 정의되어 있어서 단계별 AI Agent로 자동화할 수 있다. LLM의 발전으로 요구사항을 이해하고 기업 정보와 연결해 설득력 있는 문장을 생성할 수 있게 되었다. 조달청이 입찰공고정보를 공공데이터포털로 공개하고 있어(API·파일) 실제 데이터 기반 검증이 가능하다 (근거: 공공데이터포털 '조달청_나라장터 입찰공고정보서비스'). 공고의 업종 분류·참가 제한·지역 제한·배정예산이 정형 필드로 제공되므로 자격 판단은 규칙으로 처리하고, 과업 내용·평가기준처럼 첨부 공고서에만 있는 정보는 RAG로 읽게 할 수 있다. 특히 최종 판단은 사람이 하되, 반복적인 탐색·정리·초안 작성만 AI가 담당하는 구조로 설계하면 담당자의 시간을 크게 줄일 수 있다.

## 3. 목표 사용자 (Target User)

공공 용역 입찰에 참여하는 중소기업(IT·교육·연구조사·행사 등 용역 업종)의 입찰·영업 담당자

주요 역할: 공고 모니터링, 입찰 참여 여부 판단, 제안서 작성 및 제출

업무 특성: 소수 인원이 많은 공고를 처리해야 하고, 마감일에 쫓기는 반복 문서 업무 비중이 높음

서비스와의 관계: 담당자의 최종 판단을 대체하지 않고, 공고 선택과 제안서 초안화에 필요한 정보를 빠르고 일관되게 제공하는 조력자 역할

## 4. 프로젝트 목표

### 정성적 목표 (비즈니스 관점)

1. **업무 자동화로 수주 기회 확대**: 공고 탐색·요약·제안서 초안 작성의 반복적이고 시간 소모적인 업무를 AI 기반으로 자동화한다. 같은 인력으로 처리할 수 있는 공고 수를 늘려 수주 기회를 넓힌다. (확대 폭은 Phase 4 시간 단축 실측값으로 산출)

2. **의사결정 품질 향상으로 수주율 개선**: 추천 근거와 자격요건 충족 여부를 명확히 제시해 입찰 참여 여부를 빠르고 객관적으로 판단하도록 지원한다. 이를 통해 자격 미달 공고를 사전에 거르고 제안서 필수 항목 누락을 예방한다.

3. **기술 내재화** (개발팀 학습 목표): LangGraph 기반 멀티 Agent 오케스트레이션 및 Supervisor 패턴, React 기반 HITL(Human-in-the-loop) 화면 구현으로 실전 AI 서비스 설계 경험을 획득한다.

### 수치 출처 구분 (Baseline 기준)

문서의 모든 수치는 아래 세 가지 중 하나로 구분하며, 출처가 없는 추정치는 쓰지 않는다.

| 출처 유형 | 의미 | 해당 수치 |
| ------ | --- | ------ |
| **실측** | Phase 4(7-8주차)에 직접 측정한 값 | 현재(수작업) 소요시간, 서비스 사용 소요시간, 시간 단축률, 각 KPI 결과값 |
| **인터뷰** | Phase 4에 담당자 1인에게 확인한 값 | 담당자 월 실제 업무시간, 일 검토 공고 수 |
| **팀 설정(가정)** | 프로젝트 검증을 위해 팀이 정한 목표·설계값 | KPI 목표치(80%, 0.67, 0건, 95%, 50%, 100%), 데이터셋 규모(공고 500건 × 업체 50개, 라벨은 평가용 업체 10개 × 상위 10건 = 100조합), 소프트 점수 가중치 |

**Baseline**: 현재 업무의 소요시간과 처리량은 가정하지 않고, 대표 공고 3건을 수작업으로 수행한 **실측값**과 담당자 **인터뷰값**으로 정한다. 월 처리 가능 건수 = 담당자 월 업무시간(인터뷰) ÷ 공고 1건당 소요시간(실측).

### 적합 공고 정의 (Ground Truth 기준)

"자격이 되는 공고"와 "기업에 적합한 공고"는 다른 문제이므로 세 단계로 나누어 판단한다.

| 단계 | 질문 | 판단 방식 | 정답(Ground Truth) |
| --- | --- | ------ | ------- |
| **입찰 자격 (Eligibility)** | 이 업체가 입찰에 참여할 수 있는가? | **하드 필터 (룰)**: 공고 정형 필드(업종 분류, 참가 제한, 지역 제한, 배정예산)를 업체 프로필과 대조. 하나라도 미충족이면 제외 | 공고 필드 값과 공고서에 명시된 자격 (객관 기준) |
| **기업 적합도 (Suitability)** | 자격이 되는 공고 중 이 업체가 검토할 가치가 있는 공고는? | **소프트 점수 (룰)**: 업종 세부 일치, 키워드 겹침, 예산 규모 유사도, 계약방식 선호 → 상위 10건 | 담당자 1인의 라벨 (아래 기준) |
| **추천 순위 (Ranking)** | 상위 10건 중 무엇을 먼저 볼 것인가? | **RAG 추천**: 10건의 공고서 PDF에서 업체 역량과 관련된 내용을 검색해 LLM이 순위와 근거 생성 | 별도 정답 없음. 추천 정확도 KPI(Hit Rate@3, Precision@3)로 간접 평가 |

**정답 라벨 (평가용 업체 10개 × 시스템 상위 10건 = 100조합 각각에 1개)**

공고 500건 × 업체 50개(25,000조합)를 모두 라벨링할 수는 없으므로, 시스템이 선별한 상위 10건에만 사람이 라벨을 붙인다. 하드 필터가 제외한 공고의 정확성은 '자격 필터 정확성' KPI에서 따로 검증한다.

| 라벨 | 정의 |
| --- | --- |
| 부적격 | 공고 필드 또는 공고서에 명시된 자격 미충족 |
| 적격-비추천 | 자격은 충족하지만 아래 적합성 기준 중 하나 이상에 걸림 |
| 추천 | 자격 충족 + 적합성 기준 모두 통과 |

**적합성 기준 (적격-비추천 판단 근거)**

- 과업 불일치: 공고서의 과업 내용이 업체 보유 역량 키워드와 맞지 않음
- 유사 실적 없음: 공고 과업과 같은 유형의 수행 실적이 없음
- 사업 규모 불일치: 공고 예산이 업체의 과거 수행 규모와 크게 다름
- 수행 여력 부족: 공고서가 요구하는 인력을 현재 보유 인력으로 구성하기 어려움

담당자는 라벨마다 판단 사유를 1줄로 기록해, 이후 추천이 틀린 경우 원인(필터 오류 vs 점수·순위 오류 vs 기준 해석 차이)을 구분할 수 있게 한다.

### 정량적 목표 (KPI)

메인 기능이 공고 추천이므로 KPI를 **추천 KPI(1순위) → 업무 KPI → 제안서 KPI(보조)** 순으로 정렬한다. 제안서 KPI는 생성 품질이 아니라 "초안 작성을 시작할 수 있는가"만 확인한다.

**1순위 KPI: 공고 추천 (메인 기능 검증)**

| KPI            | 목표 수치                            | 측정 방법                                                                                              | 의미                      |
| -------------- | -------------------------------- | -------------------------------------------------------------------------------------------------- | ----------------------- |
| **추천 정확도** | **Hit Rate@3**: RAG 순위 상위 3건에 '추천' 라벨 공고가 1건 이상 있는 업체 비율 80% 이상(평가용 10개 중 8개 이상), **Precision@3** 0.67 이상을 함께 보고 (근거: 담당자가 상위 3건만 봐도 될 수준으로 팀이 설정한 목표) | 평가용 업체 10개의 상위 10건(100조합)에 순위를 가린 채 3단계 라벨을 부여한 뒤 RAG 순위 상위 3건과 비교. 룰 점수 순위 상위 3건의 Precision@3도 함께 계산해 RAG의 효과를 비교. | 담당자가 추천을 신뢰할 수 있는가      |
| **자격 필터 정확성** | 하드 필터 통과 공고 중 하드 필터 기준(업종·참가 제한·지역·예산)으로 '부적격'인 공고 0건 (근거: 자격 미달 공고 추천은 담당자 시간을 낭비시키므로 허용하지 않음) | 규칙별 단위 테스트(빈 값, 표기 차이, 경계값) + 통과·제외 샘플 30건을 사람이 원본 필드와 대조 + 100조합 라벨 중 '부적격' 수 집계. 공고서에만 있는 자격으로 인한 '부적격'은 별도 집계. | 자격이 안 되는 공고를 확실히 거르는가 |
| **추천 근거 설명 가능성** | 추천 근거 항목 중 출처가 확인되는 비율 95% 이상. 출처는 공고서 PDF 청크(파일·페이지·인용 문구) 또는 공고·업체 필드 값 (근거: 근거 없는 추천 이유는 신뢰를 떨어뜨리므로 팀이 설정한 목표, Phase 4 1차 측정 후 조정) | 근거마다 출처를 함께 출력하게 하고, 인용 문구가 해당 청크 원문에 있는지·필드 값이 입력 데이터와 일치하는지 자동 대조. | 왜 추천했는지 데이터로 설명할 수 있는가 |

**업무 KPI**

| KPI            | 목표 수치                            | 측정 방법                                                                                              | 의미                      |
| -------------- | -------------------------------- | -------------------------------------------------------------------------------------------------- | ----------------------- |
| **업무 시간 단축**   | 공고 검토 + 제안서 초안 골격 작성 총시간 50% 이상 단축 (근거: '절반 이하'를 체감 가능한 개선 기준으로 팀 설정) | 대표 공고 3건을 기존 수작업 vs 서비스 사용으로 각각 수행. 공고 분석·자격 매칭·초안 골격(목차·대응표·회사소개) 작성 시간 기록 및 비교. | 담당자의 실질적인 시간 절감이 이루어지는가 |

**보조 KPI: 제안서 초안 템플릿 (연결 기능 확인)**

| KPI | 목표 수치 | 측정 방법 | 의미 |
| --- | --- | --- | --- |
| **초안 시작 가능 여부** | 초안 템플릿 10건(평가용 업체 10개 × RAG 1순위 공고) 모두 생성 + 필수 입력 항목 반영률 100% (근거: 템플릿 삽입 방식이라 누락이 없어야 정상) | 공고서 PDF에서 추출한 평가항목과 업체 프로필의 기본 정보·실적·인력이 템플릿에 빠짐없이 들어갔는지 자동 검사 (추출 실패 항목은 `[확인 필요]`로 들어갔는지 확인) | 추천 공고에서 바로 제안서 작성을 시작할 수 있는가 |
| **초안 근거성** | 업체 프로필에 없는 사실 기재 0건 + 공고서 원문에 없는 평가항목·배점 기재 0건 (근거: 제안서의 허위·과장 기재는 감점이나 제재로 이어질 수 있어 허용하지 않음) | 템플릿의 사실 항목(실적명, 금액, 기간, 인원, 보유 자격)을 업체 프로필과, 평가항목명·배점을 공고서 PDF 원문 청크와 대조 | 담긴 내용이 실제 업체·공고 정보에 근거하는가 |

**2차 목표 지표**

| 지표     | 목표 수치                | 비고                                    |
| ------ | -------------------- | ------------------------------------- |
| 검증 통과율 | 재작성 2회 이내 통과율 90% 이상 (근거: 재작성 루프 비용 상한으로 팀 설정) | 자동 검증 루프(기능 4)는 2차 목표이므로, 이 지표는 이후 적용 |

**측정 일정**: Phase 4(7-8주차)에 KPI 측정. 각 지표는 정량 데이터로 기록하고 최종 보고서에 반영.

### 필수 구현 (1차, 8주 안에 완성)

**기능 1: 기업 맞춤 공고 추천 및 분석 (메인 기능)**

적합 공고를 찾는 시간을 줄여 검토 범위를 넓히기 위해 필요하다. 공고 500건을 아래 3단계로 줄여 나간다 (4장 '적합 공고 정의').

| 단계 | 방식 | 처리 | 결과 |
| --- | --- | --- | --- |
| ① 하드 필터 (Eligibility) | 룰 | 공고서 PDF 보유, 업종 불일치, 참가 제한 불충족, 지역 제한 불충족, 예산 범위 불일치 공고 제외 (마감일 필터는 테스트라 미적용) | 업체별 후보 공고 + 공고별 제외 사유 |
| ② 소프트 점수 (Suitability) | 룰 | 업종 세부 분류 일치, 공고명 ↔ 업체 역량 키워드 겹침, 예산 ↔ 업체 실적 규모 유사도, 계약방식 선호로 0-100점 | 상위 10건 |
| ③ RAG 추천 (Ranking) | 검색 + LLM | 상위 10건의 공고서 PDF만 청킹·임베딩해 업체 역량과 관련된 내용을 검색하고, LLM이 순위와 근거 생성 | 10건의 순위 + 근거 3-4가지 |

출력은 공고 목록(제목, 예산, 마감일) + 순위 + 룰 점수(0-100) + 추천 근거 3-4가지(각 근거의 출처: 공고서 인용 또는 필드 값) + 하드 필터 통과 내역이며, React 화면의 표·카드로 보여준다. 공고 500건 전체를 LLM으로 읽지 않고 룰로 10건까지 줄인 뒤 RAG를 적용하므로, 비용과 실행 시간이 업체당 공고 10건 분량으로 고정되고 앞 단계 결과는 재현 가능하다.

**기능 2: 담당자 승인 기반 공고 선택**

최종 의사결정 권한을 담당자에게 부여해 AI 과신을 방지하고 비즈니스 판단을 우선하기 위해 필요하다. 추천 결과를 담당자가 React 화면에서 검토한 후 제안서를 작성할 공고 1건을 선택하는 Human-in-the-loop 방식으로 구현된다. 출력은 선택된 공고 ID 및 상세정보이다.

**기능 3: 제안서 초안 템플릿 생성**

추천된 공고에서 제안서 작성이 바로 시작될 수 있다는 연결성을 보여주기 위해 필요하다 (목표: KPI '업무 시간 단축 50%'). 완성된 제안서가 아니라 담당자가 이어서 작성할 **초안 템플릿**을 만든다. 모든 섹션은 **고정 템플릿에 입력값을 삽입**하는 방식이다. 공고 평가항목·배점은 정형 필드에 없고 공고서에만 있으므로, 선택 공고의 PDF 청크에서 RAG 검색 후 LLM으로 구조화 추출(JSON)한다. LLM은 이 추출에만 쓰고 본문 문장은 생성하지 않는다.

| 구성 | 삽입하는 입력값 | 남기는 자리 |
| --- | --- | --- |
| 회사소개 | 업체 프로필: 회사명, 설립연도, 역량 키워드, 인증, 과거 실적 | 회사 비전·차별화 포인트 `[확인 필요]` |
| 수행방안 | 공고서에서 추출한 평가항목을 목차로, RAG 추천 근거의 관련 업체 근거(역량·실적)를 항목별로 | 항목별 수행 방안 본문 `[확인 필요]` |
| 추진일정 | 공고서의 과업기간, 고정 단계(착수·분석 / 수행 / 완료·보고) | 단계별 기간 `[확인 필요]` |
| 조직구성 | 업체 보유인력(역할별 인원) | 투입 인력·역할 분담 `[확인 필요]` |
| 평가기준 대응표 | 공고서에서 추출한 평가항목·배점, 대응 섹션, 관련 업체 근거 | 추출 실패·근거 없는 항목은 `[확인 필요]` |

출력은 **HTML 초안 템플릿(섹션 4개 + 평가기준 대응표)** 이며, React 화면에서 미리보기로 확인한 뒤 `.html` 파일로 다운로드해 담당자가 이어서 작성한다.

**범위 명확화**: 기능 1(추천)에 품질 투자를 집중한다. 기능 3은 초안 템플릿 생성까지이며, 본문 서술과 최종 편집은 담당자 책임이다. 시간이 남으면 그 이후에 제안서 생성 품질을 조금씩 높인다(확장).

### 확장 구현 (2차 목표, 향후 진행)

**기능 4: 자동 검증 루프 (미포함)**

검증 Agent가 생성된 제안서 초안을 자동으로 점검하여 필수 항목 누락, 자격요건 불일치 등을 발견한다. 미흡 시 작성 Agent에 재작성을 지시하는 자동 루프를 구성한다. 다만 재작성 로직과 종료 조건 설계가 복잡하기 때문에 1차에는 기본 기능 3개에 집중하고 2차 목표로 미룬다.

## 6. 기대 효과 및 핵심 가치 제안

### 1단계: 시간 효율성 - 공고 검토 및 제안서 초안 시간 단축

공고 분석·자격 매칭·초안 작성은 Agent가 맡고, 담당자는 선택과 최종 검토만 수행한다. 담당자 최종 검토 시간은 그대로 두고 앞 단계의 수작업을 줄이는 구조다.

| 단계                | 기존          | 개선 후                  |
| ----------------- | ----------- | --------------------- |
| 공고 분석 + 자격 매칭 검토  | 담당자 수작업     | Agent 자동 분석 + 담당자 확인  |
| 제안서 초안 골격 작성      | 담당자 수작업     | Agent 초안 템플릿 생성 + 담당자 본문 작성 |
| 담당자 최종 검토         | 담당자         | 담당자 (변화 없음)           |

**단축 효과 산출**: 대표 공고 3건을 수작업 vs 서비스로 각각 수행해 단계별 시간을 기록하고, 단축률과 월 처리 가능 건수(담당자 실제 업무시간 ÷ 1건당 소요시간)를 Phase 4에 산출한다.

### 2단계: 의사결정 품질 - 객관적 근거 기반 판단

시스템이 제시하는 추천 근거 + 자격요건 분석 + 평가기준 대응 정보를 통해, 담당자의 주관적 판단 의존도를 줄이고 일관된 선택 기준을 확보한다. 또한 자격 미달 공고를 사전에 걸러 불필요한 제안서 작성 시간을 절감한다. 최종 판단 권한은 사람이 유지하되, 판단에 필요한 객관적 정보는 AI가 제공하는 구조로 운영된다.

### 3단계: 품질 표준화 - 제안서 골격의 일관성

공고 평가항목에 맞춘 초안 템플릿을 제공해 필수 항목 누락을 줄이고 (목표: 필수 입력 항목 반영률 100%), 템플릿에 들어가는 사실은 모두 기업 프로필에 근거하게 한다 (목표: 프로필에 없는 사실 기재 0건). 담당자 경험과 무관하게 같은 골격에서 작성을 시작하며, 기존 템플릿 복사 대비 공고 요구사항 맞춤도를 높인다.

### 4단계: 수주 기회 극대화 - 업체의 실질적 메리트

#### ❓ 질문: "왜 우리 회사가 이 서비스를 꼭 써야 하나?"

| 상황            | 현재 상태                             | AI 어시스턴트 도입 후                         | 비즈니스 임팩트                            |
| ------------- | --------------------------------- | ------------------------------------- | ----------------------------------- |
| **적합 공고 발견** | 시간 제약으로 일부 공고만 검토  | 시간 단축으로 검토 가능 공고 확대          | 놓치는 적합 공고 감소 → **수주 기회 증가**         |
| **제안서 품질**    | 초안 완성도가 담당자에 따라 편차 발생 | 공고 평가항목에 맞춘 초안 템플릿 제공 → 휴먼에러 최소화         | 필수 항목 누락으로 인한 감점 예방 → **낙찰 가능성 향상** |
| **제출 건수**     | 수작업 시간에 묶여 제출 건수 제한                       | 같은 인력으로 더 많은 공고 대응                        | 같은 품질의 제안을 더 많이 제출 → **수주 기회 확대**  |
| **담당자 역할 변화** | 공고 검토·자격 확인·초안 작성에 대부분의 시간 소진      | 전략적 판단(입찰 여부 검토, 제안서 고도화)에 집중 | 담당자 역할 업그레이드 → **수주 전략 고도화 가능**     |

#### 🎯 핵심 메리트: 세 가지 시너지

1. **양(Quantity)**: 같은 인력으로 대응 가능한 공고 수를 늘려 기회비용을 줄인다.

2. **질(Quality)**: 공고별 맞춤형 초안과 자격요건 검토로 필수 항목 누락을 줄인다.

3. **판단(Decision)**: 객관적 근거를 제공하여 자격·역량이 맞는 공고만 선별 제출한다.

**결론**: "검토 시간 단축(양) + 의사결정 품질 향상(판단 기준) + 제안서 일관성(품질)"의 결합으로 단순 제출 수량 증대를 넘어 **수주율 자체를 향상**할 수 있는 환경 조성

## 7. 범위 및 제약사항

### 1차 구현 범위 (8주)

**필수 구현**: 실제 용역 공고 500건을 대상으로 업체별 적합 공고 추천(하드 필터 → 소프트 점수 → RAG 순위·근거, 메인 기능) → 담당자 선택 → 제안서 HTML 초안 템플릿 생성까지의 전 과정 검증

**미포함**: 검증 Agent의 자동 재작성 루프(2차 목표)

### In Scope (이번 8주에 직접 구현 & 검증)

데이터: 공공데이터포털 '조달청_나라장터 입찰공고정보서비스'의 용역 공고 500건(2026-05 공고분)을 파일로 내려받아 사용하고, 그중 첨부 공고서 PDF를 보유한 공고(437건)만 추천 대상으로 삼는다. 룰이 사람 라벨 없이 500건을 처리하고 라벨은 상위 10건에만 붙이므로, 라벨링 부담 없이 실제 규모에 가까운 데이터로 검증할 수 있다. 업체 데이터는 실제 고객사를 대신해 가상 업체 JSON 50건(업종·중소기업 여부·소재지·참여 가능 금액·역량 키워드·실적·인력 포함)으로 구성. (초기 10건으로 파이프라인을 검증한 뒤 50건으로 확장)

기술 아키텍처: Supervisor 패턴 기반 구조 구현. 하드 필터·소프트 점수(룰 모듈) -> RAG 추천 Agent -> 제안서 템플릿 모듈로 이어지는 파이프라인을 LangGraph로 조율. 제안서는 Agent가 아닌 템플릿 모듈(고정 템플릿 + 입력값 삽입, 평가항목 추출에만 LLM 사용)로 생성. 담당자의 공고 선택 단계는 Human-in-the-loop으로 설계 (제안서 확정 HITL은 LLM 생성을 도입하는 확장 단계에서 추가).

UI 및 배포: **React**로 데모 화면을 구성하고, 백엔드는 **LangGraph Server**로 그래프를 API로 노출한다. React는 LangGraph SDK로 실행·중단(HITL)·재개를 호출한다. Docker 환경에서 실행 가능하도록 구성.

측정 및 검증: 평가용 업체 10개 × 상위 10건(100조합, 3단계 라벨)과 하드 필터 샘플 대조 결과로 추천 KPI(정확도, 자격 필터 정확성, 근거 설명 가능성)를 우선 측정하고, 시간 단축 효과와 초안 템플릿 KPI(시작 가능 여부, 근거성)를 함께 측정.

### Out of Scope (이번에는 하지 않음)

API 통합: 조달청 공고 API 연계, 실시간 연동, 자동 수집 스케줄링(크론 작업)은 고도화 단계에서 개발. 이번에는 공공데이터포털에서 내려받은 정적 파일(500건)로 기능 검증에 집중.

마감일 필터: 테스트 데이터가 2026-05 공고분이라 기준일 기준 마감(`bidClseDt`) 필터는 적용하지 않음. API 연계 시 함께 적용.

HWP 공고서: 공고서가 HWP·HWPX로만 있는 공고는 하드 필터에서 제외. HWP 파싱은 확장 단계.

입찰 제출 및 예측: 최종 제안서를 나라장터에 자동 제출하는 기능과 낙찰가 예측 모델은 범위 밖.

문서 변환: Word(.docx)·HWP·PDF 변환은 범위 밖. 1차 결과물은 HTML 파일로 한정.

완성형 제안서: 수행방안 본문 서술, 화면 내 섹션 편집기는 범위 밖. 시스템은 초안 템플릿까지 제공하고 본문 작성은 다운로드 후 담당자가 수행.

프로덕션 준비: 보안(인증, 암호화), 성능 최적화(캐싱, 로드 밸런싱), 모바일 지원은 이번 PoC 단계에서는 고려하지 않음.

자동 검증 루프: 검증 Agent의 자동 재작성 로직(기능 4)은 2차 목표이며, 이번에는 포함하지 않음.

### 제약사항

데이터 보안: 실제 고객사의 기업 정보나 제안서 사본은 보안상 사용 불가능하므로, 가상의 기업 프로필과 샘플 제안서로 대체.

공고 데이터 한계: 500건 중 첨부 공고서에 PDF가 있는 공고는 437건(HWP만 17건, 첨부 없음 46건)이며 PDF 보유 공고만 추천 대상이다. 지역 제한 필드(`rgnLmtBidLocplcJdgmBssNm`)에는 제한 지역명이 아니라 판단 기준(예: '본사또는참여지사소재지')만 있으므로, 해당 공고(PDF 보유 45건)는 공고서를 보고 제한 시·도를 수동 매핑한다. 업종 제한의 상세 업종 코드도 이 파일에 없어 공공조달분류(`pubPrcrmntClsfcNo`)·대분류로 비교한다.

기술 선택: LLM은 생성형 LLM API 1종으로 고정(모델 간 비교 테스트는 별도). 텍스트 임베딩은 오픈소스 모델(BGE-M3)을 사용해 의존성 최소화. LLM은 RAG 순위·근거 생성과 평가항목 추출에만 사용하고, 필터·점수는 룰로 처리.

HTML 출력 안전성: LLM이 생성한 HTML을 화면에 그대로 렌더링하면 스크립트 삽입(XSS) 위험이 있으므로, 허용 태그만 남기는 sanitize 처리 후 표시.

제안서 품질 보증: AI가 생성한 초안의 최종 품질 판정과 수정은 반드시 담당자(사람)가 수행해야 함. 시스템은 필수 입력 항목을 빠짐없이 반영한 초안 템플릿을 제공하는 수준 (KPI 목표와 동일).

일정 경직성: 8주(하루 1-2시간) 일정 내에 기능 1-3은 반드시 완성해야 하며, 기능 4(자동 검증)는 2차 목표로 미룸.

개인정보 보호: 나라장터 공고에 포함된 발주처 담당자 연락처, 제안서에 나타나는 직원명·연락처·이메일 등 개인식별정보(PII)는 시스템에 저장하지 않거나 마스킹 처리. 실제 고객사 정보를 사용하지 않고 가상 데이터로만 검증하므로, 프로토타입 단계에서는 개인정보 유출 위험을 최소화. 향후 실제 환경에 배포할 경우 개인정보보호법 준수 체계(암호화, 접근 제어, 감사 로그)를 별도로 구축해야 함.
