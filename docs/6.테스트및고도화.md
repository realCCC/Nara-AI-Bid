## **주요 문제 해결 및 기술 리서치 (테스트 단계)**

5번 PoC 이후 테스트 과정에서 발견된 한계와 병목을 해결하기 위해 리서치하고 적용한 방법을 기록합니다.

| **이슈 구분** | **문제 상황 및 원인** | **리서치 및 해결 과정 (Reference & Solution)** |
| --- | --- | --- |
| **품질/검색** | 역량 키워드 문자열 일치(S2)만으로는 '행사'와 '북페스티벌·엑스포·콘퍼런스'처럼 표현이 다른 공고를 놓침 | **리서치:** Hybrid Search(Dense + BM25)와 RRF(Reciprocal Rank Fusion) 조사<br>**적용:** BGE-M3 dense 검색 + kiwipiepy 형태소 BM25 + 룰 점수 순위를 RRF(k=60)로 합침. 임베딩을 못 쓰면 BM25만 쓰는 `keyword_fallback` 경로로 자동 전환 |
| **품질/점수** | BGE-M3 코사인 값이 업체마다 0.40~0.66으로 달라 고정 임계값으로 의미 점수를 만들 수 없음 | **리서치:** 업체별 분포 기반 정규화 검토<br>**적용:** 업체 키워드↔전체 공고 443건 코사인 분포의 백분위(50%→0점, 97%→1점)로 선형 변환. 단일 최대값 대신 상위 3개 키워드 평균을 써서 노이즈 감소 (실측 AUC 0.84→0.86). S2는 문자열 일치와 의미 점수 중 큰 값 |
| **품질/리랭크** | Cross-encoder(bge-reranker-v2-m3) 순서만 쓰면 룰 점수를 무시함 (실측: 룰 57.8점 공고가 3위) | **리서치:** 리랭커와 1차 검색 순위의 결합 방식 조사<br>**적용:** 상위 15건만 리랭크하고, 리랭크 순위와 기존 RRF 순위를 다시 RRF로 합침. 리랭커 로드 실패 시 생략하고 기존 순서 유지 |
| **품질/환각** | RAG 순위를 LLM 한 번의 판단에 의존 → 순위 근거를 다시 확인할 장치가 없음 | **리서치:** Self-Correction·Reviewer Agent 패턴 조사<br>**적용:** 상위 5건을 재평가하는 **검증 서브에이전트** 노드 추가. 출력에 없는 공고ID·누락·중복이 있으면 결과를 버리고 원순위 유지 (재시도 없이 1회) |
| **사용자 의도** | 같은 업체라도 이번에 찾는 분야·예산·지역이 다른데 추천 조건에 반영할 방법이 없음 | **리서치:** LangGraph `interrupt` 기반 HITL 설계 재검토<br>**적용:** 추천 전 **객관식 인터뷰(HITL ⓪)** 추가. 답변을 가중치(+0.15)·추가 필터(I1)·지역 가점(+5점)·유사 표현 확장으로 변환. 건너뛰면 기본값 |
| **속도/지연** | CPU에서 BGE-M3로 공고 443건을 임베딩하면 첫 계산에 약 2~3분 소요 | **리서치:** 임베딩 캐시 전략 조사<br>**적용:** `(모델명, 문장)` 해시를 키로 벡터를 `data/emb_cache.npz`에 저장. PDF 청크 임베딩은 기본 off(`CHUNK_EMBEDDING=0`)로 두고 키워드 겹침 검색 유지 |
| **보안/가드레일** | 인터뷰 답변·API 입력이 그대로 그래프에 들어가면 잘못된 값이나 다른 업체 작업에 접근 가능 | **적용:** 인터뷰 답변은 문항별 허용 값만 남기는 화이트리스트 처리, `thread_id` 소유 업체 확인(404), 이미 답한 인터뷰 재요청 차단(409) |

## 2. 성능 및 비용 최적화

### 2-1. 처리 시간 (실측)

| 추천 Worker, `semantic` | 42초 | BGE-M3·리랭커 모델 로드 포함, 공고 벡터는 캐시 사용 |
| 그래프: 인터뷰 문항 생성 | 3.8초 | LLM 1회 (업체별 주력 분야·유사 표현) |
| 그래프: 인터뷰 답변 → 추천·RAG·검증 | 61.8초 | 5번 PoC 추천 61.6초와 비슷 (검색·리랭크·검증 단계를 추가했지만 총 시간은 유지) |
| 그래프: 선택 → 초안 | 2.0초 | 5번 PoC 4.7초 |

### 2-2. 최적화 내용

| 항목 | 내용 |
| --- | --- |
| 기존 병목 | CPU에서 BGE-M3로 공고 443건을 임베딩하면 첫 계산 약 2~3분, 추천마다 반복하면 사용 불가 |
| 개선 전략 | 결과가 바뀌지 않는 계산은 모두 캐시 |
| 적용 기술 | ① 공고 벡터 디스크 캐시(`data/emb_cache.npz`, 키 = 모델명+문장 SHA-1) ② 업체별 검색 문장 캐시(같은 프로필이면 같은 문장 → 재실행해도 후보가 같음) ③ 인터뷰 문항 캐시 ④ 인터뷰 문항 생성을 별도 노드(`prepare_interview`)로 분리 → `interrupt` 재개 때 노드가 다시 실행돼도 LLM을 또 부르지 않음 |
| 선택적 기능 | PDF 청크 임베딩(`CHUNK_EMBEDDING=1`)은 CPU에서 추천 1회에 수 분이 걸려 기본 off, 리랭크는 상위 15건만 |
| LLM 호출 수 | 추천 1회당 최대 4회: 인터뷰 문항(캐시)·검색 문장(캐시)·RAG 순위(실패 시 최대 2회 재시도)·검증(재시도 없음) + 초안 단계 평가항목 추출 1회 |
| 개선 결과 | 캐시가 있으면 `semantic` 경로가 모델 로드 포함 42초, 그래프 추천 총 시간은 PoC 수준(약 62초) 유지 |

## 3. 예외 처리 및 가드레일

| 항목 | 내용 |
| --- | --- |
| 차단 대상 | ① 허용되지 않은 인터뷰 답변 ② 다른 업체의 작업 접근 ③ 재요청으로 그래프 상태가 꼬이는 경우 ④ LLM이 만든 없는 공고ID·근거 ⑤ 낙찰 확률 예측·최종 입찰 결정 같은 범위 밖 답변 |
| 탐지 방식 | ① 문항별 허용 값 화이트리스트(모르는 문항·값·중복 제거) ② `thread_id`의 업체ID와 로그인 업체 비교 ③ 그래프 `next` 상태 확인 ④ Pydantic 스키마 + 후보 공고ID 집합 대조 + 원문 대조 ⑤ 프롬프트 금지 규칙 |
| 대응 로직 | ① 버리고 기본값("전체") ② 404 ③ 409 "이미 답변한 인터뷰입니다" ④ 결과 폐기 후 룰 순위·원순위 유지 ⑤ 프롬프트에서 금지 |
| LLM 제안 정제 | 인터뷰 주력 분야 키워드는 업체 역량 키워드 안에서만, 유사 표현은 2~10자·공백 없는 단어만 허용하고 '사업·용역·운영' 같은 넓은 단어 제외 |
| 폴백 경로 | LLM 키 없음 → 룰 순위(`rule_only`) / 임베딩 미설치·실패 → BM25(`keyword_fallback`) / 리랭커 실패 → 리랭크 생략 / 검증 실패 → 원순위 / 형태소 분석기 실패 → 공백 분리 |
| 테스트 결과 | 폴백·검증 실패 경로 단위 테스트 전부 통과 (아래 5번 참고) |
| 미검증 | 프롬프트 인젝션(공고 PDF 안에 지시문이 들어 있는 경우 등) 테스트는 아직 하지 않음 |

## 4. 기타 문제 해결 사례

| 이슈 | 원인 | 해결 |
| --- | --- | --- |
| 인터뷰를 모두 건너뛰면 그래프가 재개되지 않음 | `Command(resume={})`처럼 빈 dict를 넘기면 LangGraph가 인터럽트 ID 매핑으로 해석 | 재개 값을 항상 `{"answers": {...}}` 형태로 감쌈 |
| 테스트용 가짜 벡터가 실제 캐시에 섞일 위험 | 임베딩 캐시가 모듈 전역 + 디스크 파일 | 테스트 fixture에서 캐시 경로를 임시 폴더로 바꾸고 전역 캐시 초기화 |
| 인터뷰 확장어가 LLM 판단을 흐림 | 확장어를 업체 프로필에 직접 넣으면 LLM이 업체 실제 역량으로 오해 | 확장 프로필은 키워드 일치(S2)·BM25·청크 검색에만 쓰고, LLM에는 원래 프로필 전달 |
| Windows 콘솔에서 데모 스크립트 출력 오류 | 출력 문자열의 `—`(U+2014)를 cp949로 인코딩하지 못함 (`UnicodeEncodeError`) | 실행 시 `PYTHONIOENCODING=utf-8` 설정 (스크립트 자체 수정은 다음 단계) |
| 패키지 이름이 역할을 드러내지 않음 | E2E 단계에서 `frontend/`와 나란히 둘 서버 코드가 `app/`에 있음 | `app/` → `backend/`로 이동, 설정·스크립트·테스트·`langgraph.json` 경로 갱신 |
